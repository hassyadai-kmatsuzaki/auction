## 0. このドキュメントの位置づけ

### なぜ本番ミラーのステージングが必要か

本番事故の大半は **「ローカル(Docker)で動いた → 本番(EC2)で動かない」** の構成差から来る。

過去事故と memory に記録されているもののうち、ステージングがあれば防げた / 早期検知できたケース:
- `REVERB_PORT=8080` 誤指定で全件 unsold（[memory: project_reverb_port_pitfall.md]）
- `storage/logs` 権限事故（root 所有 → ec2-user worker 全滅、[memory: feedback_no_sudo_artisan.md]）
- カウントダウン Job のログ書き込み権限事故（[memory: project_countdown_log_permission_fragility.md]）
- 入札ロック順序のデッドロック（[memory: project_bid_lock_order.md]）

これらは **OS / supervisor / 権限 / TLS / Reverb 配線** に起因する。Docker でローカル動作確認しても再現しない。
本番と **同じ AL2023 + 同じ supervisor + 同じ Redis 経路** を用意し、リリース前の最終確認を必ずそこで行う。

### 3層の役割分担

| 層 | 用途 | 本番との差 |
|---|---|---|
| **ローカル** (Docker) | 機能開発、単体テスト、UI 確認 | 大（OS, プロセス管理, ネットワーク経路） |
| **ステージング** (EC2 native) | 結合確認、負荷試験、リリース前最終検証 | 小（スペック・ドメイン・データのみ） |
| **本番** (EC2 native) | 本物 | — |

ステージングは **「本番のクローン、ただしスペックは最小、データは匿名化」** が原則。

> **現状（2026-05-01 時点）**: ステージング用の **EC2 / RDS / ElastiCache / ALB はすでに作成済み**。
> 残り作業は **既存 EC2 へのパッケージ・アプリ配置 / nginx 設定 / supervisor 設定の本番ミラー化 / Route53 + ACM / `.env` 設定 / 動作確認**。

### 2.1 ネットワーク（STEP 1, 2）

**選択肢**:
- **(推奨)** 本番 VPC とは **完全に分離した VPC** を作る → 誤接続事故を物理的に防ぐ

```bash

cd /var/www/auction
```

### 2.5 nginx（STEP 6 後段）

本番手順と **完全に同一**:

```nginx
# /etc/nginx/conf.d/auction.conf
server {
    listen 80 default_server;
    server_name medaka-auction.com;
    root /var/www/auction/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }
    location ~ \.php$ {
        fastcgi_pass unix:/run/php-fpm/www.sock;
        fastcgi_index index.php;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }
    client_max_body_size 100M;
}

# WebSocket 専用 proxy（本番と同じ）
server {
    listen 8080;
    server_name medaka-auction.com;
    location / {
        proxy_pass http://127.0.0.1:6001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

> ⚠️ **`REVERB_PORT=8080` 誤指定の罠**（memory: project_reverb_port_pitfall.md）: 8080 は WebSocket **専用 proxy**。Reverb 自体は **6001** で動く。`.env` の `REVERB_PORT` は **6001**（broadcast がサーバ→Reverb で接続するため）、フロントの `VITE_REVERB_PORT` は **443**（クライアントが ALB の HTTPS 経由で接続）。

### 2.6 ALB（STEP 7, 9）

> ✅ **2026-05-01 時点：ALB は作成済み**。本節は **既存 ALB が本番と同等構成か** の確認手順を扱う。

#### 2.6.1 既存 ALB の確認

```bash
# ALB の詳細を取得
aws elbv2 describe-load-balancers \
  --names <ステージングALB名> \
  --query 'LoadBalancers[0].{ARN:LoadBalancerArn,DNS:DNSName,Scheme:Scheme,VpcId:VpcId}' \
  --output table

# リスナー一覧
aws elbv2 describe-listeners \
  --load-balancer-arn <ALB_ARN> \
  --query 'Listeners[].{Port:Port,Protocol:Protocol,Cert:Certificates[0].CertificateArn}' \
  --output table

# ターゲットグループとヘルスチェック
aws elbv2 describe-target-groups \
  --load-balancer-arn <ALB_ARN> \
  --query 'TargetGroups[].{Name:TargetGroupName,Port:Port,Protocol:Protocol,HealthPath:HealthCheckPath}' \
  --output table

# アイドルタイムアウト（WebSocket 切断防止のため 3600 秒必須）
aws elbv2 describe-load-balancer-attributes \
  --load-balancer-arn <ALB_ARN> \
  --query "Attributes[?Key=='idle_timeout.timeout_seconds'].Value" --output text
```

期待構成:

| リスナー | ポート | プロトコル | ターゲット |
|---|---|---|---|
| API | 443 | HTTPS | EC2:80（php-fpm 経由） |
| WebSocket | 443 | HTTPS | EC2:8080（nginx → 6001 Reverb プロキシ） |

**重要設定**:
- アイドルタイムアウト = **3600秒**（WebSocket 切断防止 — 親手順書 §11.5 と同じ）
- ターゲットグループのヘルスチェック = `/api/healthcheck` 想定
- スティッキーセッション = **無効**（API は stateless / WS は ALB が固定ルーティングしない）

#### 2.6.2 タイムアウトが 3600 でなかった場合の修正

```bash
aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn <ALB_ARN> \
  --attributes Key=idle_timeout.timeout_seconds,Value=3600
```

### 2.7 ACM / Route53（STEP 8 + 親手順書 STEP 13）

旧本番ドメイン `medaka-auction.com` を **本ステージング ALB に向ける**（親手順書 STEP 13 の方針）。

**Route53 ホストゾーン `medaka-auction.com`**:

| レコード | タイプ | 値 |
|---|---|---|
| `medaka-auction.com` | A (Alias) | ステージング ALB |
| `www.medaka-auction.com` | A (Alias) | ステージング ALB |

旧本番が向いていた A レコードがあれば、必ず先にステージング ALB に切り替えてから、旧本番側の DNS 紐付けを解除する（瞬断防止のため、TTL を事前に短縮: 60秒）。

**ACM 証明書**（東京リージョン、ALB 用）:

- `medaka-auction.com`
- `www.medaka-auction.com`（SAN として同じ証明書に含める）
- DNS 検証推奨（自動更新可能）

旧本番で発行していた ACM 証明書は失効させず、そのままステージング ALB に流用しても良い（東京リージョンの場合）。
親手順書 STEP 13-2 にも「旧ドメインの ACM 証明書を開発環境用に再設定」と記載あり。

### 2.9 Supervisor（STEP 11）— 既存設定との突合と再構成

> ⚠️ **重要**: 本ステージング EC2 には過去の supervisor 設定が残っている可能性がある。
> 本番手順書（INFRA-2026-001 STEP 11）との **差分を必ず突合し**、不一致があれば本番準拠に揃える。
> 古いままの supervisor で動かすと、本番では再現しない事象がステージングで発生し、逆に「本番事故をステージングで検出できなかった」事故にもなる。

#### 2.9.1 既存設定の取得・棚卸し

```bash
# 既存の supervisor 設定ファイルを全て確認
sudo ls -la /etc/supervisord.d/ /etc/supervisor/conf.d/ 2>/dev/null

# 各ファイルの中身
sudo find /etc -name "*.ini" -o -name "*.conf" 2>/dev/null | xargs grep -l "queue:work\|reverb" 2>/dev/null
sudo cat /etc/supervisord.d/auction.ini 2>/dev/null
sudo cat /etc/supervisor/conf.d/*.conf 2>/dev/null

# 現在の起動状態
sudo supervisorctl status
```

#### 2.9.2 本番との差分チェックリスト

以下の表で各 program について **項目ごとに突合**。1つでも差分があれば 2.9.3 で再構成。

| program | 必須コマンド/オプション | 重要パラメータ |
|---|---|---|
| `auction-queue-countdown` | `queue:work redis --queue=countdown --sleep=1 --tries=1 --timeout=7200` | `numprocs=1` (本番通常時も1) / `stopwaitsecs=7200` / `user=ec2-user` |
| `auction-queue-default` | `queue:work redis --queue=default --sleep=3 --tries=3 --timeout=300 --max-jobs=1000 --max-time=3600` | `numprocs=1` / `user=ec2-user` |
| `auction-queue-notify` | `queue:work redis --queue=notifications --sleep=3 --tries=3 --timeout=120 --max-jobs=1000 --max-time=3600` | `numprocs=1`（本番は2、ステージングは1）/ `user=ec2-user` |
| `auction-queue-notify-priority` | `queue:work redis --queue=notifications-priority --sleep=1 --tries=3 --timeout=60` | `numprocs=1` / `user=ec2-user` |
| `auction-reverb` | `reverb:start --host=0.0.0.0 --port=6001` | `numprocs=1` / `user=ec2-user` / `stopwaitsecs=10` |

**よくある差分（要修正パターン）**:
- ❌ `command` が `php artisan ...` のフルパスでない（`/usr/bin/php /var/www/auction/artisan ...` でないと PATH 依存で起動失敗する）
- ❌ `user=root` のまま → memory `feedback_no_sudo_artisan.md` の事故再現条件
- ❌ `--timeout` が `retry_after`（14400）と整合していない（特に countdown は 7200 必須）
- ❌ `stopwaitsecs` が小さすぎる（countdown は最大 4 時間動くので 7200 必須）
- ❌ `auction-queue-notify-priority` の program 自体がない（本番手順書 v1.0 で追加された5番目）
- ❌ `auction-reverb` の port が `6001` 以外（memory `project_reverb_port_pitfall.md` の事故再現条件）
- ❌ `redirect_stderr=true` が無く stderr が消える設定

#### 2.9.3 本番ミラーへの再構成

突合で差分があった場合、`/etc/supervisord.d/auction.ini` を **既存ファイルをバックアップしてから** 以下に **完全置換**:

```bash
# 既存をバックアップ
sudo cp /etc/supervisord.d/auction.ini /etc/supervisord.d/auction.ini.bak.$(date +%Y%m%d-%H%M%S)
# あるいは旧 conf 配置の場合
sudo cp -r /etc/supervisor/conf.d /etc/supervisor/conf.d.bak.$(date +%Y%m%d-%H%M%S)
```

その上で本節 §2.9.4 の ini を `/etc/supervisord.d/auction.ini` に配置。

## 8. コスト管理

ステージングは **常時稼働で月 $30〜50**。

節約したい場合の選択肢:

- **A. 24時間稼働**: 月 $30–50。リリース直前に毎日触れるなら推奨
- **B. 開発時間のみ稼働**: EC2 / RDS / ElastiCache を朝起動・夜停止 → 月 $10–15。EventBridge スケジューラで自動化可能
- **C. 必要な時だけ立てる**: Terraform / CloudFormation で「up / down」コマンド化、月 $5 未満（ALB と Route53 のみ常設）

第一回開催前は **A** で運用、開催後は **B or C** に切り替えるのが現実的。

## 9. 緊急時のフォールバック（ステージング障害）

ステージングが死んでもリリースを止めない手順:

1. **本番との差分が小さい変更のみ**: ステージング検証を skip して本番に出す（リスク受容）
2. **構成変更を含む変更**: ステージング復旧まで本番デプロイ凍結
3. **判断基準**: 変更ファイルが PHP/JS のロジックのみ → skip OK / `.env` / supervisor / nginx / migration → skip 不可

## 11. スケールアップ・ダウン 手動 runbook（本番・ステージング共通）

> 本書では Lambda / EventBridge による自動スケーリングは採用せず、**管理者が手動で実行する** 方針とする（要件: 障害時に「自動切替が裏目に出る」リスクを避ける）。
> 将来 Lambda 化したくなった場合、§11.5 に骨子だけ残す。

### 11.1 スケールアップする「タイミング」

| タイミング | 実行者 | 完了希望 |
|---|---|---|
| オークション開催 **2 時間前** までにスケールアップ完了 | オペレーター | 開始 1 時間前には全リソース available |
| オークション終了 **30 分以降** にスケールダウン開始 | オペレーター | 終了 1 時間後に通常モード復帰 |

**前提**: ライブ中（`auctions.status='live'`）にスケール変更は **絶対に行わない**（DB / Cache が一瞬切れる経路あり）。
オークションが scheduled 状態か finished 状態でのみ実施。

### 11.2 スケールアップ手順（通常 → オークション時）

#### A. EC2: t3.small → t3.large

```bash
# 1) 現在のインスタンス ID を取得
INSTANCE_ID=$(aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=<本番EC2のNameタグ>" \
  --query 'Reservations[0].Instances[0].InstanceId' --output text)
echo $INSTANCE_ID

# 2) 停止
aws ec2 stop-instances --instance-ids $INSTANCE_ID
aws ec2 wait instance-stopped --instance-ids $INSTANCE_ID

# 3) インスタンスタイプ変更
aws ec2 modify-instance-attribute \
  --instance-id $INSTANCE_ID \
  --instance-type "{\"Value\":\"t3.large\"}"

# 4) 起動
aws ec2 start-instances --instance-ids $INSTANCE_ID
aws ec2 wait instance-running --instance-ids $INSTANCE_ID

# 5) 起動確認
aws ec2 describe-instances --instance-ids $INSTANCE_ID \
  --query 'Reservations[0].Instances[0].{Type:InstanceType,State:State.Name,IP:PublicIpAddress}'
```

> ⚠️ 起動後、SSH で以下を必ず確認:
> ```bash
> ssh ec2-user@<staging-host>
> sudo supervisorctl status   # 全 RUNNING を確認
> php /var/www/auction/artisan auctions:check-config --strict
> sudo chown -R ec2-user:ec2-user /var/www/auction/storage/logs
> ```

#### B. RDS: db.t3.micro → db.t3.medium + Multi-AZ ON

**所要時間**: 15〜30 分（変更適用に時間がかかる）。**開催 2 時間前までに完了させる**。

```bash
RDS_ID="<ステージングRDS識別子>"

# 1) 変更適用（即時反映で Multi-AZ は別途）
aws rds modify-db-instance \
  --db-instance-identifier $RDS_ID \
  --db-instance-class db.t3.medium \
  --multi-az \
  --apply-immediately

# 2) ステータスが modifying → available に戻るまで待機
aws rds wait db-instance-available --db-instance-identifier $RDS_ID

# 3) 確認
aws rds describe-db-instances --db-instance-identifier $RDS_ID \
  --query 'DBInstances[0].{Class:DBInstanceClass,MultiAZ:MultiAZ,Status:DBInstanceStatus}'
```

> **本番では** db.t3.medium へのスケールアップ時にパラメータグループも `prod-mysql8-event` に切り替える運用が親手順書に記載されている。同じ運用がステージングでも必要なら指示書に従う。

#### C. ElastiCache: cache.t3.micro → cache.t3.medium + Replica 追加

**所要時間**: 20〜40 分。

```bash
CACHE_ID="<ステージングCache識別子>"

# 1) ノードタイプ変更（即時）
aws elasticache modify-cache-cluster \
  --cache-cluster-id $CACHE_ID \
  --cache-node-type cache.t3.medium \
  --apply-immediately

# 2) 完了待ち
aws elasticache wait cache-cluster-available --cache-cluster-id $CACHE_ID

# 3) Replica 追加が必要な場合（ReplicationGroup 構成のとき）
# レプリケーショングループ化されていない場合は事前にグループ作成必要
aws elasticache increase-replica-count \
  --replication-group-id <ReplicationGroupId> \
  --new-replica-count 1 \
  --apply-immediately
```

#### D. Supervisor: numprocs を増やす

EC2 の SSH 内で:

```bash
# /etc/supervisord.d/auction.ini を編集して numprocs を本番オークション時の値に
# - auction-queue-countdown: numprocs=1 → 5
# - auction-queue-default:   numprocs=1 → 2
# - auction-queue-notify:    numprocs=1 → 2
# それ以外は据え置き

sudo vi /etc/supervisord.d/auction.ini
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status
```

#### E. ALB（変更不要）

ALB は通常モードでもオークションモードでも同じ ALB を使う。スケールしない。
**アイドルタイムアウト 3600 秒** が維持されていることだけ再確認。

#### F. スケールアップ完了チェックリスト

```bash
# 全部 OK なら本番開催可能
sudo -u ec2-user php /var/www/auction/artisan auctions:check-config --strict
sudo supervisorctl status | grep -v RUNNING && echo "FAIL" || echo "OK"
aws rds describe-db-instances --db-instance-identifier <RDS_ID> \
  --query 'DBInstances[0].{Class:DBInstanceClass,MultiAZ:MultiAZ}'
aws elasticache describe-cache-clusters --cache-cluster-id <Cache_ID> \
  --query 'CacheClusters[0].{Type:CacheNodeType}'
aws ec2 describe-instances --instance-ids <EC2_ID> \
  --query 'Reservations[0].Instances[0].InstanceType'
```

### 11.3 スケールダウン手順（オークション時 → 通常）

**オークション終了から最低 30 分は据え置き**（残務処理・落札通知配信・指値レコード後処理が完全終了するまで）。

#### A. Supervisor: numprocs を戻す

```bash
ssh ec2-user@<staging-host>
sudo vi /etc/supervisord.d/auction.ini
# numprocs を全て 1 に戻す
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status
```

#### B. ElastiCache: Replica 削除 → ノードタイプ縮小

```bash
# Replica を 0 に戻す
aws elasticache decrease-replica-count \
  --replication-group-id <ReplicationGroupId> \
  --new-replica-count 0 \
  --apply-immediately

aws elasticache wait cache-cluster-available --cache-cluster-id <Cache_ID>

# ノードタイプ縮小
aws elasticache modify-cache-cluster \
  --cache-cluster-id <Cache_ID> \
  --cache-node-type cache.t3.micro \
  --apply-immediately

aws elasticache wait cache-cluster-available --cache-cluster-id <Cache_ID>
```

#### C. RDS: Multi-AZ OFF → ノードタイプ縮小

```bash
# Multi-AZ オフ + ノードタイプ縮小（一括）
aws rds modify-db-instance \
  --db-instance-identifier <RDS_ID> \
  --db-instance-class db.t3.micro \
  --no-multi-az \
  --apply-immediately

aws rds wait db-instance-available --db-instance-identifier <RDS_ID>
```

#### D. EC2: t3.large → t3.small

```bash
aws ec2 stop-instances --instance-ids <EC2_ID>
aws ec2 wait instance-stopped --instance-ids <EC2_ID>

aws ec2 modify-instance-attribute \
  --instance-id <EC2_ID> \
  --instance-type "{\"Value\":\"t3.small\"}"

aws ec2 start-instances --instance-ids <EC2_ID>
aws ec2 wait instance-running --instance-ids <EC2_ID>
```

#### E. スケールダウン後チェック

EC2 起動後 SSH で:

```bash
sudo supervisorctl status     # 全 RUNNING
sudo -u ec2-user php /var/www/auction/artisan auctions:check-config --strict
sudo chown -R ec2-user:ec2-user /var/www/auction/storage/logs
```

### 11.4 失敗時のロールバック

| 失敗ケース | 対処 |
|---|---|
| RDS modify がエラー | `aws rds describe-events --source-identifier <RDS_ID> --source-type db-instance` でログ確認。`InsufficientDBInstanceCapacity` ならアベイラビリティゾーン変更 or 時間を空けて再試行 |
| EC2 起動後 supervisor が UP しない | `sudo journalctl -u supervisord -n 100` / `sudo tail /var/log/supervisor/*.log`。よくあるのは storage/logs 権限事故 → `chown -R ec2-user:ec2-user storage/logs` |
| ElastiCache Replica 追加失敗 | ReplicationGroup 化されていない可能性。一旦放置して通常運用、後日 ReplicationGroup へ移行 |
| ALB ヘルスチェック Unhealthy | EC2 内で `curl http://localhost/api/healthcheck`。500 系ならアプリログ、接続不可なら php-fpm / nginx 再起動 |

スケール変更を **元のサイズに戻す** 場合は §11.3 の同じ手順を実行。RDS の Multi-AZ オン → オフは追加ダウンタイムが発生するので、**変更前提のオークションが直近にないか確認** してから実施。

### 11.5 将来の自動化（参考、今は採用しない）

Lambda + EventBridge スケジュールで自動化する場合の骨子:

```
EventBridge cron(0 8 * * MON,WED,FRI ?) → Lambda(auction-scale-up)
  ├─ AWS SDK で modify-instance-attribute / modify-db-instance / modify-cache-cluster
  └─ SSM Run Command で EC2 内の supervisorctl update

EventBridge cron(0 23 * * MON,WED,FRI ?) → Lambda(auction-scale-down)
  └─ 同上の逆操作
```

ただし下記リスクで現状は手動運用とする:
- **Multi-AZ 切り戻しの所要時間が読めない** → cron で固定時刻発火だと開催に間に合わない可能性
- **オークション延長時に自動ダウンが走る** → 最終商品の落札直前に Cache が縮む事故
- **失敗検知 → 通知 → 介入** のフローを構築する工数が、月数回の手動運用コストを上回る

採用する場合は **DryRun フラグ付き** で投入し、最低 1 ヶ月並行運用して挙動を検証してから本番化する。
