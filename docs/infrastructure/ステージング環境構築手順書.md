## 0. このドキュメントの位置づけ

### なぜ本番ミラーのステージングが必要か

本番事故の大半は **「ローカル(Docker)で動いた → 本番(EC2)で動かない」** の構成差から来る。

過去事故と memory に記録されているもののうち、ステージングがあれば防げた / 早期検知できたケース:
- `REVERB_PORT=8080` 誤指定で全件 unsold（[memory: project_reverb_port_pitfall.md]）
- `storage/logs` 権限事故（root 所有 → ec2-user worker 全滅、[memory: feedback_no_sudo_artisan.md]）
- カウントダウン Job のログ書き込み権限事故（[memory: project_countdown_log_permission_fragility.md]）
- 入札ロック順序のデッドロック（[memory: project_bid_lock_order.md]）

これらは **OS / supervisor / 権限 / TLS / Reverb 配線** に起因する。Docker でローカル動作確認しても再現しない。
本番と **同じ AL2023 + 同じ supervisor + 同じ Redis 経路** を用意し、リリース前の最終確認を必ずそこで行う。

### 3層の役割分担

| 層 | 用途 | 本番との差 |
|---|---|---|
| **ローカル** (Docker) | 機能開発、単体テスト、UI 確認 | 大（OS, プロセス管理, ネットワーク経路） |
| **ステージング** (EC2 native) | 結合確認、負荷試験、リリース前最終検証 | 小（スペック・ドメイン・データのみ） |
| **本番** (EC2 native) | 本物 | — |

ステージングは **「本番のクローン、ただしスペックは最小、データは匿名化」** が原則。

## 2. 構築手順（本番手順書との差分のみ）

[AWS_インフラ構築作業指示書.md](./AWS_インフラ構築作業指示書.md) を **そのままなぞる** のが基本。本ドキュメントでは **明示的に変える箇所だけ** を列挙する。

### 2.1 ネットワーク（STEP 1, 2）

**選択肢**:
- **(推奨)** 本番 VPC とは **完全に分離した VPC** を作る → 誤接続事故を物理的に防ぐ
- (節約) 本番 VPC のサブネットをステージング用に切り出す → セキュリティグループで分離

**セキュリティグループ命名規則**: `auction-staging-*`（本番は `auction-prod-*`）。混在させない。

### 2.2 RDS / ElastiCache（STEP 3, 4）

本番手順と同じ手順、ただし:
- **Multi-AZ オフ**
- **Replica なし**
- パラメータグループは **本番と同じものをコピー**（同名で `-staging` 付与）
- スナップショット復元から作る場合: 本番から最新スナップショットを取り、復元後に **個人情報マスキング SQL を必ず実行**（§6 参照）

### 2.3 S3（STEP 5）

専用バケット名: `auction-staging-media` 等。本番バケットには絶対書き込まない。
バケットポリシーは本番と同等の設定に。

### 2.4 EC2（STEP 6）

#### 2.4.1 AMI とパッケージ

本番手順と **完全に同一**:

```bash
sudo dnf update -y
sudo dnf install -y git nginx python3-pip
sudo dnf install -y php8.2-fpm php8.2-mysqlnd php8.2-mbstring php8.2-xml \
                    php8.2-zip php8.2-gd php8.2-intl php8.2-bcmath \
                    php8.2-opcache php8.2-pecl-redis6 php8.2-common \
                    php8.2-pdo php8.2-sodium

# Composer
curl -sS https://getcomposer.org/installer | php
sudo mv composer.phar /usr/local/bin/composer

# Node.js 20.x
curl -fsSL https://rpm.nodesource.com/setup_20.x | sudo bash -
sudo dnf install -y nodejs

# Supervisor
sudo pip3 install supervisor
```

#### 2.4.2 アプリ配置

```bash
sudo mkdir -p /var/www/auction
sudo chown ec2-user:ec2-user /var/www/auction
cd /var/www/auction

# ステージングは develop ブランチを使う（本番は main）
git clone -b develop git@github.com:<org>/<repo>.git .
sudo -u ec2-user composer install --no-dev --optimize-autoloader
sudo -u ec2-user npm ci
sudo -u ec2-user npm run build

# 本番と同じ権限設定（memory: feedback_no_sudo_artisan.md 参照）
sudo chown -R ec2-user:ec2-user /var/www/auction
sudo chmod -R 775 /var/www/auction/storage /var/www/auction/bootstrap/cache
```

> ⚠️ **`storage/logs` の権限事故対策**: デプロイ後に必ず `sudo chown -R ec2-user:ec2-user /var/www/auction/storage/logs` を実行。`sudo` で `php artisan` を打つと `storage/logs` が root 所有で残り、その後 ec2-user の worker が write 失敗 → 全滅する事故が起きる。`artisan` は **必ず `sudo -u ec2-user`** で叩く。

### 2.5 nginx（STEP 6 後段）

本番手順と **完全に同一**:

```nginx
# /etc/nginx/conf.d/auction.conf
server {
    listen 80 default_server;
    server_name staging.<本番ドメイン>;
    root /var/www/auction/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }
    location ~ \.php$ {
        fastcgi_pass unix:/run/php-fpm/www.sock;
        fastcgi_index index.php;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }
    client_max_body_size 100M;
}

# WebSocket 専用 proxy（本番と同じ）
server {
    listen 8080;
    server_name staging.<本番ドメイン>;
    location / {
        proxy_pass http://127.0.0.1:6001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

> ⚠️ **`REVERB_PORT=8080` 誤指定の罠**（memory: project_reverb_port_pitfall.md）: 8080 は WebSocket **専用 proxy**。Reverb 自体は **6001** で動く。`.env` の `REVERB_PORT` は **6001**（broadcast がサーバ→Reverb で接続するため）、フロントの `VITE_REVERB_PORT` は **443**（クライアントが ALB の HTTPS 経由で接続）。

### 2.6 ALB（STEP 7, 9）

本番手順と同じ。リスナー:
- **HTTPS 443** → EC2:80 (HTTP API)
- **HTTPS 443** → EC2:8080 (WebSocket、`/app/*` パスベース or 独自ホスト名)

**ALB アイドルタイムアウト = 3600秒**（WebSocket 切断防止）— ここは本番と必ず同じにする。

### 2.7 ACM / Route53（STEP 8）

`staging.<本番ドメイン>` で証明書発行＋Route53 Aレコードを ALB に向ける。

### 2.8 環境変数（STEP 10）

ステージング用 `.env`（本番との差分のみ抜粋）:

```bash

APP_DEBUG=false                  # 本番と同じ（事故再現性のため）
APP_URL=https://staging.<本番ドメイン>

# Redis（ステージング専用 ElastiCache）

REDIS_PORT=6379
REDIS_PASSWORD=<ステージング専用>

# Queue / Cache / Session — 全て redis（本番と同じ）

REVERB_HOST=127.0.0.1            # ★ 本番と同じ。サーバ→Reverb はループバックで接続
REVERB_PORT=6001                 # ★ 8080 ではない
REVERB_SCHEME=http               # サーバ間はhttp、ALBで TLS 終端
VITE_REVERB_APP_KEY="${REVERB_APP_KEY}"
VITE_REVERB_HOST=staging.<本番ドメイン>
VITE_REVERB_PORT=443
VITE_REVERB_SCHEME=https

# メール — ステージングは本送しない

MAIL_FROM_ADDRESS=noreply@staging.<本番ドメイン>

# LINE 通知 — テスト用チャネル
LINE_CHANNEL_ACCESS_TOKEN=<テスト用Bot>
LINE_CHANNEL_SECRET=<テスト用>
# もしくは無効化:

# S3 — ステージング専用バケット

AWS_DEFAULT_REGION=ap-northeast-1

# OpenAI — レート枯渇対策で別キー推奨（あれば）

```

設定反映:

```bash

sudo -u ec2-user php artisan config:clear
```

## 3. 動作確認チェックリスト（リリース前必須）

```bash
# 1) 設定検証コマンド
sudo -u ec2-user php /var/www/auction/artisan auctions:check-config --strict
# → exit code 0 / "All checks passed." を確認

# 2) supervisor 全プログラム RUNNING
sudo supervisorctl status | grep -v RUNNING && echo "FAIL" || echo "OK"

# 3) Redis 疎通

# 5) Reverb ヘルスチェック（ローカルから）
curl -i http://127.0.0.1:6001/app/<REVERB_APP_KEY>

# 6) WebSocket 経由疎通（外部から）
wscat -c "wss://staging.<本番ドメイン>/app/<REVERB_APP_KEY>"
```

## 4. ローカル開発との関係

| 何をどこで | ローカル(Docker) | ステージング(EC2) | 本番(EC2) |
|---|---|---|---|
| 機能開発 | ◎ | × | × |
| UI 単体確認 | ◎ | △ | × |
| 結合テスト | ○ | ◎ | × |
| 負荷試験（300名） | × | ◎ | × |
| WebSocket 切断シナリオ | △ | ◎ | × |
| supervisor 死活確認 | × | ◎ | × |
| 本番デプロイ手順リハーサル | × | ◎ | × |
| Redis LRU eviction 試験 | × | ◎ | × |

ローカル開発は今まで通り Docker で進め、**「ステージング → 本番」へのデプロイは必ずセット** で動かすのが新しい運用ルール。

## 5. リリース前運用フロー

```
[develop ブランチに PR マージ]
   ↓
[GitHub Actions / 手動] develop → ステージングへ自動デプロイ
   ↓
[ステージング] auctions:check-config --strict が 0 で通ること
   ↓
[ステージング] 主要シナリオの結合テスト（入札・指値・落札・流札）
   ↓
[ステージング] 必要なら N=30〜100 の負荷試験（load-tests/）
   ↓
[ステージング] 24時間以上ノーアラートで稼働
   ↓
[main ブランチへマージ → 本番デプロイ]
```

**新ルール**: ステージングを通さない本番デプロイは禁止。
hotfix 等やむを得ないケースは「ステージングと本番に同時デプロイ → 5分後にステージングで動作確認 → 異常あればロールバック」の手順を踏む。

## 6. データ運用（本番 → ステージング）

### 6.1 スナップショット復元手順

```bash
# 本番 RDS から最新スナップショットを作成
aws rds create-db-snapshot \
  --db-instance-identifier auction-prod \
  --db-snapshot-identifier auction-prod-$(date +%Y%m%d)

# ステージング側で復元（既存ステージングDBは削除してから）
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier auction-staging \
  --db-snapshot-identifier auction-prod-YYYYMMDD \
  --db-instance-class db.t3.micro \
  --no-multi-az
```

### 6.2 個人情報マスキング（必須）

復元直後に **必ず実行**:

```sql
-- メールアドレスをマスク
UPDATE users SET email = CONCAT('staging+', id, '@example.com');

-- 電話番号をダミーに
UPDATE users SET phone = NULL;
UPDATE shipping_addresses SET phone = NULL;

-- LINE ID をクリア
UPDATE users SET line_user_id = NULL;

-- Stripe customer ID をクリア
UPDATE users SET stripe_customer_id = NULL;
UPDATE subscriptions SET stripe_subscription_id = NULL WHERE stripe_subscription_id IS NOT NULL;

-- パスワードを共通テストパスワードに（bcrypt 'StagingTest123!'）
UPDATE users SET password = '$2y$12$xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx';

-- 配送先住所を匿名化
UPDATE shipping_addresses SET
  postal_code = '0000000',
  prefecture = 'ステージング県',
  city = 'ステージング市',
  address_line1 = 'staging-' || id,
  address_line2 = NULL;
```

これを Laravel コマンド化しておくと安全:

```bash
sudo -u ec2-user php artisan staging:mask-personal-data
```

`app/Console/Commands/MaskPersonalData.php` として実装し、`APP_ENV=production` のときは早期 abort する保険を入れる。

### 6.3 推奨頻度

- **月1回** スナップショット復元 + マスキング
- 大きな機能リリース前は **直近スナップショット** を別途取り直す

## 7. CI/CD（推奨、リリース後に整備）

GitHub Actions の `deploy-staging.yml`:

```yaml
on:
  push:
    branches: [develop]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: SSH deploy to staging
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.STAGING_HOST }}
          username: ec2-user
          key: ${{ secrets.STAGING_SSH_KEY }}
          script: |
            cd /var/www/auction
            git fetch origin develop
            git reset --hard origin/develop
            composer install --no-dev --optimize-autoloader
            npm ci
            npm run build
            php artisan config:cache
            php artisan route:cache
            php artisan view:cache
            php artisan migrate --force
            sudo chown -R ec2-user:ec2-user storage/logs bootstrap/cache
            sudo supervisorctl restart auction-queue-countdown auction-queue-default auction-queue-notify auction-queue-notify-priority auction-reverb
```

> ⚠️ supervisor restart はライブ非開催時のみ。ステージングはライブをぶつけないよう運用時間を分ける（e.g. 平日昼=デプロイOK、週末オークション時間帯=デプロイ凍結）。

## 8. コスト管理

ステージングは **常時稼働で月 $30〜50**。

節約したい場合の選択肢:

- **A. 24時間稼働**: 月 $30–50。リリース直前に毎日触れるなら推奨
- **B. 開発時間のみ稼働**: EC2 / RDS / ElastiCache を朝起動・夜停止 → 月 $10–15。EventBridge スケジューラで自動化可能
- **C. 必要な時だけ立てる**: Terraform / CloudFormation で「up / down」コマンド化、月 $5 未満（ALB と Route53 のみ常設）

第一回開催前は **A** で運用、開催後は **B or C** に切り替えるのが現実的。

## 9. 緊急時のフォールバック（ステージング障害）

ステージングが死んでもリリースを止めない手順:

1. **本番との差分が小さい変更のみ**: ステージング検証を skip して本番に出す（リスク受容）
2. **構成変更を含む変更**: ステージング復旧まで本番デプロイ凍結
3. **判断基準**: 変更ファイルが PHP/JS のロジックのみ → skip OK / `.env` / supervisor / nginx / migration → skip 不可
