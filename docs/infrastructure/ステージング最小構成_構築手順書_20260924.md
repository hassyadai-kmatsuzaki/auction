## 0. この構成の考え方

前回（9/9）の本番ミラーは負荷試験の器だったので ALB・Multi-AZ RDS・ElastiCache・負荷発生機まで揃えた。今回は接続試験だけなので、**GMO 側の登録項目を満たす最小限**に絞る。

| GMO の登録項目 | 満たし方 |
|---|---|
| 開発環境の固定 IP（Q6、本番と別 IP 必須） | EC2 に Elastic IP を直接付ける（NAT も ALB も無し。アウトバウンドの送信元 = EIP） |
| リダイレクト URI（Q11、HTTPS） | nginx + Let's Encrypt（certbot）で TLS 終端 |
| 通知先 URL（Q16、HTTPS） | 同上 |

| 項目 | 前回（本番ミラー） | **今回（最小）** | 理由 |
|---|---|---|---|
| EC2 | c6i.2xlarge → t3.small | **t3.small × 1** | 試験は API を数回叩くだけ |
| 起動元 | 本番 AMI クローン | **本番 AMI クローン**（同じ） | OS/PHP/nginx/supervisor を一から入れない |
| RDS | スナップショット復元・Multi-AZ | **db.t3.micro を新規（空 DB → migrate）** | 個人情報のマスキング工程が丸ごと不要になる |
| Redis | ElastiCache | **EC2 内のローカル Redis** | 課金ゼロ。キューと cache が動けば十分 |
| ALB / ACM | あり | **なし**（nginx で 443） | ALB 月額とターゲットグループの手間を省く |
| S3 | auction-staging-media | **auction-staging-media**（残っていれば流用） | メディア機能は試験対象外だが誤って本番バケットに書かないため |
| Reverb / WebSocket | あり | **supervisor で 1 本だけ起動**（外部公開しない） | フロントが繋ぎに行くだけ。試験には無関係 |
| データ | 本番の匿名化コピー | **空 + 管理者 1 名 + テスト用落札データ** | 個人情報を持ち込まない |

**概算コスト**: t3.small ≈ $17/月 + db.t3.micro ≈ $15/月 + EBS/EIP 数ドル。試験の合間は EC2 を stop してよい（EIP は残す。stop 中の EIP は ≈ $3.6/月）。

## 3. AWS リソース作成（コンソール）

所要 30 分（AMI 待ち含む）

```text
【1. 本番の AMI を取る（本番は止まらない）】
EC2 → インスタンス → i-03110f40eb631a471（auction-prod-app-01）→ アクション → イメージとテンプレート → イメージを作成
  イメージ名: auction-prod-clone-20260924 ／ 「再起動しない」に**必ずチェック** → 作成。5〜10 分で「利用可能」。
  ※ 既に auction-prod-clone-2026* が残っていて 9/16 以降のものなら流用してよい（AMI → 作成日を確認）。

【2. セキュリティグループを 3 つ作る（EC2 → セキュリティグループ → 作成。VPC は本番と同じ）】
a. staging-bootstrap-isolated（残っていれば流用）
   インバウンド: なし
   アウトバウンド: TCP 443 のみ 0.0.0.0/0（Session Manager・パッケージ取得用）。3306/6379 は入れない。
   → クローン起動直後に本番の .env のまま worker/scheduler が動き出しても、本番 DB/Redis に届かないようにする隔離用。
b. auction-staging-sg-ec2
   インバウンド: TCP 80 0.0.0.0/0（certbot の HTTP-01 検証と HTTPS への転送）／ TCP 443 0.0.0.0/0
   アウトバウンド: すべて
   ※ 22 は開けない（Session Manager を使う）。8080 も開けない（WebSocket は外部公開しない）。
   ※ 本番の auction-sg-ec2 は**流用しない**（本番 RDS/Redis の SG が auction-sg-ec2 からの接続を許可しているため）。
c. auction-staging-sg-rds
   インバウンド: TCP 3306 ソース = auction-staging-sg-ec2
   アウトバウンド: 既定

【3. RDS（空の MySQL）】RDS → データベースの作成 → 標準作成
   エンジン MySQL 8.0（本番 database-1 と同じマイナー）／ テンプレート「無料利用枠」または「開発/テスト」
   DB インスタンス識別子 auction-staging ／ マスターユーザー名 〈本番 .env の DB_USERNAME と同じにすると sed が楽〉／ パスワード 〈新規生成、控える〉
   db.t3.micro ／ gp3 20GB ／ ストレージ自動スケーリング OFF ／ Single-AZ
   VPC 本番と同じ ／ サブネットグループ 本番と同じ ／ パブリックアクセス なし ／ SG = auction-staging-sg-rds
   追加設定: 最初のデータベース名 〈本番 .env の DB_DATABASE と同じ〉／ 自動バックアップ 1 日 ／ 削除保護 OFF ／ パラメータグループは default.mysql8.0 でよい
   → 10〜15 分で「利用可能」。エンドポイントを控える。

【4. Elastic IP】EC2 → Elastic IP → 割り当て（タグ Name = auction-staging-eip）。**この値が GMO に申告する開発環境の固定 IP（Q6）**。控える。

【5. S3（メディアの誤書き込み防止）】
   S3 → auction-staging-media が残っているか確認。無ければ作成（東京、パブリックアクセスブロックは本番 auction-media-prod と同じ）。
   IAM → ロール → auction-ec2-role → インラインポリシーに auction-staging-media への s3:GetObject / PutObject / DeleteObject / ListBucket があるか確認。無ければ追加（9/9 に追加済みのはず）。

【6. EC2 起動】EC2 → AMI → auction-prod-clone-20260924 → AMI からインスタンスを起動
   名前 auction-staging-app-01 ／ t3.small ／ VPC 本番と同じ ／ サブネット = 本番と同じ**パブリック**サブネット ／ パブリック IP の自動割り当て 無効（EIP を付けるため）
   セキュリティグループ = **staging-bootstrap-isolated だけ** ／ IAM インスタンスプロファイル = auction-ec2-role（本番と同じ）／ キーペア 〈U-5、無ければ「なし」〉／ ストレージは AMI 既定
   起動後: Elastic IP → auction-staging-eip → 関連付け → auction-staging-app-01。
   3 分待って Session Manager で接続できることを確認。

【7. Route53】ホストゾーン medaka-ichiba.com → レコード作成
   staging.medaka-ichiba.com  A  〈EIP〉  TTL 60（エイリアスではなく通常の A）。前回の ALB 向けエイリアスが残っていたら**上書き**。
   CloudShell で確認: dig +short staging.medaka-ichiba.com   期待: 〈EIP〉

【報告形式】AMI ID / EC2 インスタンス ID とプライベート IP / EIP / RDS エンドポイント / SG 3 つの ID / dig の結果
```

## 4. クローンをステージングに切り替える（Session Manager、隔離 SG のまま）

所要 15 分。**この手順が終わるまで SG を付け替えない。**

```text
【8. 本番向けプロセスを止める】
sudo supervisorctl stop all; sudo systemctl disable --now supervisord; sudo supervisorctl status || true
crontab -l -u ec2-user 2>/dev/null; sudo crontab -l 2>/dev/null
   期待: すべて STOPPED（または supervisor 停止）。crontab に schedule:run があれば `crontab -r -u ec2-user` で消す（本番は supervisor の auction-scheduler が正で、crontab は無いはず）。

【9. .env をステージング値へ】
cd /var/www/auction && sudo cp .env .env.prod-clone-backup-$(date +%F)
sudo -u ec2-user sed -i 's/^APP_ENV=.*/APP_ENV=staging/; s/^APP_DEBUG=.*/APP_DEBUG=false/' .env
sudo -u ec2-user sed -i 's#^APP_URL=.*#APP_URL=https://staging.medaka-ichiba.com#; s#^FRONTEND_URL=.*#FRONTEND_URL=https://staging.medaka-ichiba.com#; s/^SESSION_DOMAIN=.*/SESSION_DOMAIN=staging.medaka-ichiba.com/' .env
sudo -u ec2-user sed -i 's/^DB_HOST=.*/DB_HOST=〈RDS エンドポイント〉/; s/^DB_DATABASE=.*/DB_DATABASE=〈DB 名〉/; s/^DB_USERNAME=.*/DB_USERNAME=〈マスターユーザー〉/; s/^DB_PASSWORD=.*/DB_PASSWORD=〈パスワード〉/' .env
sudo -u ec2-user sed -i 's/^REDIS_HOST=.*/REDIS_HOST=127.0.0.1/; s/^REDIS_PASSWORD=.*/REDIS_PASSWORD=null/; s/^REDIS_SCHEME=.*/REDIS_SCHEME=tcp/; s/^REDIS_PERSISTENT=.*/REDIS_PERSISTENT=false/' .env
grep -q '^REDIS_SCHEME=' .env || echo 'REDIS_SCHEME=tcp' | sudo -u ec2-user tee -a .env
sudo -u ec2-user sed -i 's/^VITE_REVERB_HOST=.*/VITE_REVERB_HOST=staging.medaka-ichiba.com/' .env
sudo -u ec2-user sed -i 's/^MAIL_MAILER=.*/MAIL_MAILER=log/; s/^AWS_BUCKET=.*/AWS_BUCKET=auction-staging-media/' .env
sudo -u ec2-user sed -i 's/^LINE_LOGIN_CHANNEL_ID=.*/LINE_LOGIN_CHANNEL_ID=/; s/^LINE_LOGIN_CHANNEL_SECRET=.*/LINE_LOGIN_CHANNEL_SECRET=/; s/^LINE_MESSAGING_CHANNEL_ACCESS_TOKEN=.*/LINE_MESSAGING_CHANNEL_ACCESS_TOKEN=/; s/^ENE_WEBHOOK_SECRET=.*/ENE_WEBHOOK_SECRET=/; s/^SQUARE_ACCESS_TOKEN=.*/SQUARE_ACCESS_TOKEN=/' .env
grep -E '^(APP_ENV|APP_DEBUG|APP_URL|FRONTEND_URL|SESSION_DOMAIN|DB_HOST|DB_DATABASE|REDIS_HOST|REDIS_SCHEME|REDIS_PERSISTENT|VITE_REVERB_HOST|MAIL_MAILER|AWS_BUCKET|LINE_LOGIN_CHANNEL_ID|LINE_MESSAGING_CHANNEL_ACCESS_TOKEN|ENE_WEBHOOK_SECRET|SQUARE_ACCESS_TOKEN)=' .env
   期待: DB_HOST に auction-staging、REDIS_HOST=127.0.0.1、外部連携のキーが空。本番のホスト名・トークンが 1 つでも残っていたら止めて報告。
   ※ APP_KEY は本番と同じでよい（変えると暗号化済みデータと GMO トークンの復号ができなくなる。ここでは新規 DB なので影響なし）。
sudo -u ec2-user php artisan config:clear
   （config:cache はコード配置後の手順 5 でまとめて行う）

【10. SG を付け替える】コンソール: EC2 → auction-staging-app-01 → セキュリティグループを変更 → auction-staging-sg-ec2 を付け、staging-bootstrap-isolated を外す。
   以後、アウトバウンドが全開になる（本番 RDS/Redis には SG で到達不可）。

【報告形式】supervisorctl status ／ grep の全行 ／ SG 付け替え後のスクリーンショット
```

## 6. HTTPS（Let's Encrypt）

```text

sudo dnf install -y python3 augeas-libs

sudo nginx -t && sudo systemctl reload nginx
echo "0 0,12 * * * root /opt/certbot/bin/python -c 'import random; import time; time.sleep(random.random() * 3600)' && certbot renew -q" | sudo tee -a /etc/crontab
```

## 7. フロントのビルド（任意・後回し可）

## 8. GMO 接続試験（方針書 §6.3 の当てはめ）

前提: U-3（client_id / client_secret）受領済み、GMO 側に 新 EIP（Q6）・Q11・Q16・Q21/22 が登録済み。

```text
【18. 認可】
cd /var/www/auction && sudo -u ec2-user php artisan gmo-aozora:auth-url
   → 表示された URL を口座保有者がブラウザで開き、GMO 開発環境にログイン・認可。/admin/settings?gmo_aozora=connected に戻れば成功。
   error&reason=invalid_state → 10 分を過ぎた（URL を作り直す）。reason=invalid_client → client_id/secret。reason=invalid_grant → redirect_uri が Q11 の登録値と不一致。
sudo -u ec2-user php artisan tinker --execute='echo json_encode(App\Models\GmoAozoraToken::first()?->toStatusArray(), JSON_PRETTY_PRINT), PHP_EOL;'
   期待: expires_at が約 30 日先、scope に 4 つ。

【19. 4 スコープ疎通（GMO 側のログ確認対象）】
sudo -u ec2-user php artisan gmo-aozora:test-connection
   期待: 5 行すべて OK（口座 / 振込状況 / 総合振込状況 / 振込入金口座一覧 / 入金明細）。NG の行は status と error をそのまま報告。
   ※ 送金系（/transfer/request 等）は叩かない。GMO_AOZORA_TRANSFER_ENABLED=false のままにする。

【20. Webhook】
管理画面 → 設定 → 外部連携 → 「GMOあおぞら Webhook の生データをログに残す」ON → 「GMOあおぞら 入金通知を受け付ける」ON
curl -s -X POST -H 'Content-Type: application/json' -d '{"start":true}' -H "Authorization: Bearer 〈管理者トークン〉" https://staging.medaka-ichiba.com/api/admin/gmo-aozora/webhook/subscribe
   （または管理者でログインしたブラウザの開発者ツールから同 API を叩く）
GMO 開発環境で振込入金口座へテスト入金 → 数十秒後:
sudo -u ec2-user php artisan tinker --execute='echo App\Models\GmoDepositNotification::count(), PHP_EOL; print_r(App\Models\GmoDepositNotification::latest()->first()?->only(["message_id","va_id","deposit_amount","status","unmatched_reason"]));'
   期待: 1 件以上、status は unmatched(no_va または va_unassigned)（落札データが無いので消込はされない。到達確認としては十分）。
grep 'GMO Aozora webhook' storage/logs/laravel-$(TZ=Asia/Tokyo date +%F).log | tail -5
   期待: raw receive [debug] の行。basic auth mismatch / signature mismatch が出ていたら Q21/22 か client_secret を見直す。
試験が終わったら「生データをログに残す」を OFF に戻す。

【報告形式】toStatusArray の JSON ／ test-connection の表 ／ 通知件数と最新 1 件 ／ ログの該当行
```

## 10. 運用と片付け

- **使わない期間**: EC2 を stop（EIP は残す）。RDS も stop 可能（7 日で自動起動するので長期なら都度 stop）。
- **再開**: EC2 start → Session Manager で `sudo supervisorctl status` と `curl -s https://staging.medaka-ichiba.com/api/health`。EIP を付けたままなので IP と DNS は不変。
- **証明書**: crontab の certbot renew が自動更新。EC2 を 60 日以上 stop したままにすると失効するので、再開時に `sudo certbot renew` を手で流す。
- **完全撤去**: EC2 終了 → RDS 削除（最終スナップショット不要）→ SG 3 つ削除 → Route53 の A レコード削除。**EIP は GMO 側の登録が生きている間は残す。**
- **本番 AMI**: 構築完了後に auction-prod-clone-20260924 を登録解除し、スナップショットも削除してよい（数 GB の課金）。

## 11. 本番ミラー版との使い分け

| やりたいこと | 使う構成 |
|---|---|
| 外部連携の接続試験（GMO / E-NE / LINE） | **本書（最小）** |
