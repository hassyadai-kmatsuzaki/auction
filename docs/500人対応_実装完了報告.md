### P0 #5: Item 価格更新に lockForUpdate() 追加 ✅

- **対象ファイル**: `app/Services/CountdownService.php` — `handlePriceIncrement()`
- **問題**: `$item->current_price` をロックなしで読み書き。500人同時接続時に価格増分の20〜30%が消失
- **修正内容**:
  - `Item::lockForUpdate()->find($item->id)` で悲観ロック付きの最新価格を取得
  - `$freshItem->status !== 'live'` の再チェックを追加（ロック取得中にステータスが変わるケースを考慮）
  - 呼び出し元の `$item->current_price` をロック後の値に同期
- **影響範囲**: `handlePriceIncrement()` → `handleImmediatePriceIncrement()` からの呼び出しにも自動適用
- **リスク**: ロック待ちで tick 処理が 数ms 遅延する可能性あり（Redis ops で相殺されるため問題なし）

### P0 #6: BidParticipant::participate() をアトミックUPSERTに変更 ✅

- **対象ファイル**: `app/Models/BidParticipant.php` — `participate()`
- **問題**: `updateOrCreate()` の check-then-act パターンで、500人同時実行時にユニーク制約違反エラー（5〜10%）
- **修正内容**:
  - `updateOrCreate()` → `upsert()` に変更（`INSERT ... ON DUPLICATE KEY UPDATE`）
  - ユニークキー `['item_id', 'user_id']` を明示
  - 更新対象カラムを明示（`is_active`, `activated_at`, `deactivated_at`, `ip_address`, `user_agent`, `updated_at`）
  - upsert 後に `where()->first()` で最新のモデルインスタンスを返却
- **前提**: マイグレーション `2024_01_16_100004` で `unique(['item_id', 'user_id'], 'uk_item_user')` が定義済み
- **影響範囲**: JoinBidAction, LeaveBidAction 等で `BidParticipant::participate()` を呼び出す全箇所

### P0 #7: BidLimitPrice オーファンレコード対策 ✅

- **対象ファイル**: `app/Services/CountdownService.php` — `checkBidLimits()`
- **問題**: `markAsTriggered()` の楽観ロックで false が返った場合、レコードが孤児化してユーザーが指値を再設定できなくなる

  - ログ出力を追加（`BidLimit orphan cleanup`）
- **影響範囲**: `checkBidLimits()` のみ。`markAsTriggered()` 自体は変更なし（楽観ロックのロジックは正しい）

### P0 #9: ResumeAuctionAction を Cache::increment() に変更 ✅

- **対象ファイル**: `app/Actions/Auction/ResumeAuctionAction.php`
- **問題**: 世代番号の `Cache::get()` → `+1` → `Cache::put()` が非アトミック。複数管理者の同時 resume で同一世代番号が発行され、重複ジョブが起動
- **修正内容**:
  - `Cache::get() + 1` + `Cache::put()` → `Cache::increment()` に変更
  - キーが存在しない場合の初期化を `Cache::has()` + `Cache::put(0)` で明示的に処理
  - `Cache::increment()` は Redis のアトミック `INCR` コマンドに直接マッピングされる
- **影響範囲**: `ResumeAuctionAction::execute()` のみ

### P0 #10: CountdownTick ブロードキャスト間引き + クライアント側補間 ✅

- **問題**: 0.5秒間隔の tick が 500人 × 6レーン = 6,000msg/sec のブロードキャスト負荷を生成
- **設計判断**: TICK_INTERVAL は 0.5秒を維持（フリーズ0.1秒刻み対応のため）。ブロードキャスト頻度のみ間引く
- **修正内容（バックエンド）**:
  - `CountdownService` に `BROADCAST_INTERVAL = 1.0` 定数を追加
  - `tick()` (bidding): `fmod(remaining, BROADCAST_INTERVAL) < 0.001` で整数秒境界のみブロードキャスト → **2 tick に1回**
  - `tickPreBid()`: 同様に1秒間隔に間引き
  - `tickFreeze()`: **間引きなし**（0.5秒毎にブロードキャスト）— 0.1秒刻みの精度を維持
  - `TICK_INTERVAL` は 0.5秒のまま（内部カウントダウン精度を維持）
- **修正内容（フロントエンド）**:
  - 新規フック `useInterpolatedCountdown.ts` を作成
    - サーバーの tick（bidding/pre_bid は1秒間隔）受信時のタイムスタンプをベースに `requestAnimationFrame` でローカル補間
    - サーバー値受信時に即時補正（ドリフト防止）
    - `Math.ceil()` で整数表示（1秒刻み）
    - freeze フェーズ・停止中は補間スキップ（サーバーから0.5秒毎に届くため不要）
  - `LaneCard.tsx`: `CountdownChip` と `PreBidOverlay` に補間済みの値を渡すよう変更
- **影響範囲**: 
  - バックエンド: `CountdownService.php`（tick/tickPreBid に間引きロジック追加）
  - フロントエンド: `LaneCard.tsx`（補間フック使用）、`useInterpolatedCountdown.ts`（新規）
- **パフォーマンス効果**:
  | フェーズ | 変更前 | 変更後 | 備考 |
  |---------|--------|--------|------|
  | bidding | 6,000 msg/sec | **3,000 msg/sec** | 大半の時間を占める |
  | pre_bid | 6,000 msg/sec | **3,000 msg/sec** | |
  | freeze | 6,000 msg/sec | 6,000 msg/sec | 据え置き（短時間のため影響小） |
- **UX影響**: なし（bidding/pre_bid はクライアント補間、freeze はサーバー0.5秒tickがそのまま届く）
- **フリーズ精度**: 0.1秒刻み対応を維持。0.5秒フリーズも正確に動作
