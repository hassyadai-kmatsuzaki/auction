## 1. 概要

エスクローは「落札成立 → 入金確認 → 出品者へ支払いリリース」の 3 段階に加え、返金・紛争（dispute）を扱う仕組みです。WonItem ごとに 1 件の `EscrowTransaction` レコードが対応し、入金から出品者口座への精算に至るまで管理者主導で状態を遷移させます。

### 1.1 用語

| 用語 | 定義 |
|---|---|
| EscrowTransaction | 落札ごとに作成されるエスクロー取引レコード |
| Buyer | 落札者（`buyer_id` = `users.id`） |
| Seller | 出品者（`seller_id` = `users.id`） |
| Dispute | 紛争。商品未着・破損などのクレームを記録する状態 |

## 2. データモデル

### 2.1 escrow_transactions テーブル

| カラム | 型 | 説明 |
|---|---|---|
| `id` | PK | 主キー |
| `won_item_id` | FK → won_items (cascade) | 落札レコード |
| `buyer_id` | FK → users | 落札者 |
| `seller_id` | FK → users | 出品者 |
| `amount` | unsigned integer | 取引金額（円） |
| `status` | enum | `awaiting_payment` / `payment_held` / `released_to_seller` / `refunded` / `disputed` |
| `paid_at` | timestamp, nullable | 入金確認日時 |
| `released_at` | timestamp, nullable | 出品者へのリリース日時 |
| `refunded_at` | timestamp, nullable | 返金日時 |
| `notes` | text, nullable | 返金理由・紛争内容を記録 |
| `created_at` / `updated_at` | timestamps | |

インデックス: `[buyer_id, status]`, `[seller_id, status]`

## 3. 状態遷移

```
落札確定
  │
  ▼
awaiting_payment ─────(confirmPayment)─────▶ payment_held
                                                │
                                                ├─(releaseToSeller)─▶ released_to_seller
                                                │
                                                └─(refund)─────────▶ refunded
  │                                             ▲
  └──(openDispute)──▶ disputed ─(refund)────────┘
```

### 3.1 遷移条件

| 遷移 | 元状態 | 結果状態 | 制約 |
|---|---|---|---|
| `confirmPayment()` | `awaiting_payment` | `payment_held` | WonItem.payment_status = `paid` に同期更新 |
| `releaseToSeller()` | `payment_held` | `released_to_seller` | WonItem.delivery_status = `completed` に同期更新 |
| `refund(reason)` | `payment_held` / `disputed` | `refunded` | reason 必須 / WonItem.payment_status = `refunded` |
| `openDispute(reason)` | 任意 | `disputed` | reason を `notes` に記録 |

### 3.2 不変条件

- `payment_held` 以外から `release` は不可（409）
- `refund` は `payment_held` または `disputed` からのみ可（それ以外は 409）
- 全遷移は `DB::transaction()` でラップされ、WonItem との状態同期を保証

## 4. API エンドポイント

ルートプレフィックス: `/api/admin/escrow`
認可: 管理者のみ（`auth:sanctum` + admin role）

| メソッド | パス | ハンドラ | 責務 |
|---|---|---|---|
| GET | `/` | `EscrowController@index` | 一覧（status フィルタ・ページネーション 20件） |
| POST | `/{id}/confirm-payment` | `EscrowController@confirmPayment` | 入金確認 → `payment_held` |
| POST | `/{id}/release` | `EscrowController@release` | 出品者へリリース → `released_to_seller` |
| POST | `/{id}/refund` | `EscrowController@refund` | 返金 → `refunded`（`reason` 必須） |
| POST | `/{id}/dispute` | `EscrowController@dispute` | 紛争記録 → `disputed`（`reason` 必須） |

### 4.1 リクエスト例

#### 入金確認

```http
POST /api/admin/escrow/123/confirm-payment HTTP/1.1
Authorization: Bearer {admin_token}
```

#### 返金

```http
POST /api/admin/escrow/123/refund HTTP/1.1
Authorization: Bearer {admin_token}
Content-Type: application/json

{ "reason": "商品破損のため返金" }
```

## 5. サービスメソッド

`EscrowService` は全エスクロー操作の中核。各メソッドは `DB::transaction()` 内で WonItem の同期更新と監査ログ出力を行います。

| メソッド | シグネチャ | 動作 |
|---|---|---|
| `createFromWonItem(WonItem)` | `→ EscrowTransaction` | WonItem から金額・buyer/seller を取得して `awaiting_payment` で作成 |
| `confirmPayment(EscrowTransaction)` | `→ void` | status 遷移 + `paid_at = now()` + WonItem.payment_status = `paid` |
| `releaseToSeller(EscrowTransaction)` | `→ void` | 状態チェック後、`released_at` をセット + WonItem.delivery_status = `completed` |
| `refund(EscrowTransaction, string $reason)` | `→ void` | `refunded_at` セット + WonItem.payment_status = `refunded` + `notes` に reason 記録 |
| `openDispute(EscrowTransaction, string $reason)` | `→ void` | `notes` に reason 記録（状態チェックなし） |

### 5.1 例外

| 例外 | 発生条件 |
|---|---|
| `RuntimeException` | `createFromWonItem` で buyer/seller の FK が取得不可 |
| `ConflictHttpException` (409) | 不正な状態遷移（例: `awaiting_payment` から `release`） |
| `ValidationException` (422) | `refund` / `dispute` で `reason` 未指定 |

## 6. WonItem との連携

### 6.1 自動生成

- `FinalizeBidAction::finalizeAsSold()` で WonItem が作成される際の処理は [FinalizeBidAction.php](../../../app/Actions/Bid/FinalizeBidAction.php) を参照
- 現状の実装では **EscrowTransaction は FinalizeBidAction から直接生成されない**。`EscrowService::createFromWonItem()` を別途呼び出す設計
- 落札後の運用: 管理画面で WonItem 一覧から手動でエスクロー作成、または将来的にイベントリスナで自動化予定

### 6.2 状態同期マトリクス

| EscrowTransaction.status | WonItem.payment_status | WonItem.delivery_status |
|---|---|---|
| `awaiting_payment` | `pending` | `pending` |
| `payment_held` | `paid` | `pending` |
| `released_to_seller` | `paid` | `completed` |
| `refunded` | `refunded` | （変更なし） |
| `disputed` | （変更なし） | （変更なし） |

## 7. 監査ログ・通知

### 7.1 監査ログ

`Log::channel('audit')` に以下のカテゴリで記録 ([CloudWatch監視設定手順書](../../infrastructure/CloudWatch監視設定手順書.md) で監視):

| カテゴリ | 記録項目 |
|---|---|
| `ESCROW_PAYMENT_CONFIRMED` | escrow_id, amount, buyer_id |
| `ESCROW_RELEASED` | escrow_id, amount, seller_id |
| `ESCROW_REFUNDED` | escrow_id, amount, buyer_id, reason |
| `ESCROW_DISPUTED` | escrow_id, reason |

### 7.2 通知

エスクロー操作と連動して送信される通知（`NotificationService` 経由）:

| イベント | 対象 | Mail | LINE |
|---|---|---|---|
| 入金確認 (`confirmPayment`) | 買い手 | `PaymentConfirmedMail` | `payment_confirmed` Flex |
| 入金確認 (`confirmPayment`) | 出品者 | `SellerPaymentReceivedMail` | `payment_received` Flex |
| 返金 (`refund`) | 買い手 | （未実装 / 必要に応じて追加） | （未実装） |

> 現在の実装では `EscrowService` 内から直接通知を呼ばず、外部（管理画面のフローまたは Webhook）から `NotificationService` を呼ぶ設計。通知の自動連動は今後の改善ポイント。

## 9. 運用上の注意点

1. **Square 連携なし**: 現状の `EscrowService` は Square API を直接呼びません。落札代金の決済は別途、年会費 Square Subscription とは独立。エスクロー金額の実際の入出金は銀行振込前提
2. **手動運用**: 入金確認・リリース・返金は全て管理者の手動操作。自動化（銀行 API 連携など）は対象外
3. **冪等性**: `confirmPayment` などは状態チェックで二重実行を防止しているが、UI 側でも重複クリック防止を入れること
4. **返金後の WonItem**: `refund` 後の WonItem は `payment_status=refunded` となり、領収書・請求書の再発行はブロックされる
5. **dispute → refund の流れ**: dispute は記録のみで自動アクションはなし。返金が必要な場合は別途 `refund` を呼ぶ
