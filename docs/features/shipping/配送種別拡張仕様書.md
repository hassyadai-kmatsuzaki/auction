## 0. 背景と目的

### 0.1 現状

現在の配送料計算 [ShippingCalculatorService.php](src/app/Services/ShippingCalculatorService.php) は**メダカ前提の単一ロジック**。

- 袋サイズ (S/M/L/KA) と匹数レンジは `bag_specs` テーブルにハードコード相当で 1 セットしか持たない
- 箱詰め混載ルールは [ShippingCalculatorService.php:316-322](src/app/Services/ShippingCalculatorService.php#L316-L322) に**PHPコード内ハードコード**
- `items` テーブルには `species_name`（文字列）があるだけで、配送計算ロジックとの紐付けはない

### 0.2 目的

1. **メダカ以外の種別でも自動計算できるようにする**（第1弾: 水草 / 金魚、将来: 随時追加）
2. **「その他」種別は手動送料入力**で逃げられるようにする
3. **種別が混在しても、全て自動計算ロジックを持つ種別どうしなら自動計算する**（例: メダカ + 水草）。「その他」が1件でも混ざった発送単位は全体を手動扱いにする
4. 種別ごとのパラメータ（袋サイズ / 数量レンジ / 重量 / 混載ルール）を**DB マスタで管理**し、コード変更なしで種別追加できるようにする

### 0.3 計算方針まとめ（コア仕様）

| 発送単位に含まれる種別 | 計算方針 |
|---|---|
| メダカのみ | 自動（メダカのマスタで計算） |
| 水草のみ / 金魚のみ / 他の自動種別のみ | 自動（その種別のマスタで計算） |
| 複数の自動種別の混在（例: メダカ + 水草） | **自動**（種別ごとに袋・箱を詰めて合算 or 混載して合算） |
| 「その他」を1件でも含む | **手動**（管理者が送料を直接入力） |

### 0.4 非目標（今回はやらないこと）

- 運賃表（`shipping_rates`）の種別化 — 運賃は宅配業者基準（箱サイズ×地域）のままで種別非依存
- 資材マスタ（`packing_materials`）の種別化 — 箱サイズ基準のままで種別非依存
- 箱サイズ自体の追加（80/100/140 のまま。追加は別案件）

## 1. 用語

| 用語 | 定義 |
|---|---|
| 種別 (species type) | 配送計算ルールセットの単位。初期値は「メダカ」「水草」「金魚」「その他」 |
| 自動計算種別 | 袋・箱・混載ルールを DB に持ち、自動で送料を算出する種別。`calculation_mode = auto` |
| 手動計算種別 | 自動計算対象外で、管理者が送料を直接入力する種別 = 「その他」のみ。`calculation_mode = manual` |
| 混合（状態） | 1 発送単位に複数の自動計算種別の商品が含まれる**状態**。種別ではなく、計算時の条件判定で扱う。全てが自動計算種別であれば自動計算を継続する |
| 発送単位 | 同一オークション × 同一落札者 の WonItem 集合（現行の計算単位と同じ） |

## 2. 種別の設計

### 2.1 種別マスタ（新規テーブル）

テーブル名: `species_types`

| カラム | 型 | 説明 |
|---|---|---|
| id | bigint PK | |
| code | string(32) unique | `medaka` / `aquatic_plant` / `goldfish` / `other` / 将来拡張 |
| name | string(64) | 表示名「メダカ」「水草」「金魚」「その他」 |
| calculation_mode | enum(`auto`, `manual`) | `auto`=袋・箱ベース自動計算 / `manual`=手動入力 |
| is_mixable | boolean | 混合発送時に他の auto 種別と**同一箱**に詰めてよいか。false の場合、その種別だけで別箱を立てる |
| sort_order | int | 表示順 |
| is_active | boolean | |
| created_at / updated_at | | |

初期シード:

| code | name | calculation_mode | is_mixable | 備考 |
|---|---|---|---|---|
| medaka | メダカ | auto | 運用判断 | 現行ロジックの移行先 |
| aquatic_plant | 水草 | auto | 運用判断 | マスタ投入後に稼働 |
| goldfish | 金魚 | auto | 運用判断 | マスタ投入後に稼働 |
| other | その他 | manual | — | これを含む発送単位は全体が手動計算 |

> **「混合」は種別レコードではなく、発送単位内に複数の auto 種別が混在する状態を指す**。種別マスタに `mixed` レコードは作らない。全員 auto ならそのまま自動計算が続行される。

### 2.2 商品 (Item) への紐付け

- `items.species_type_id` (FK → species_types.id, nullable) を追加
- 既存の `items.species_name` は**表示用テキスト**として残す（削除しない）
- マイグレーションで既存データは全件 `medaka` にバックフィル

### 2.3 オークション出品時のUI（出品者画面）

出品フォーム（既存の商品登録画面）に「種別」セレクトボックスを追加：

- 初期値: `medaka`（`species_types.is_default = true` のレコード。後述 §2.5 参照）
- `is_active = true` の `species_types` を `sort_order` 順で表示
- 必須項目
- 既存の `species_name`（テキストの品種名「楊貴妃」「三色ラメ」等）は**残す**。種別（カテゴリ）とは別レイヤーの情報

### 2.4 管理者の生体管理画面（既存機能拡張）

[Admin/ItemController](src/app/Http/Controllers/Admin/ItemController.php) で扱っている生体一覧 / 詳細 / 更新に、種別の表示・変更機能を追加：

- **一覧** (`index`): 「種別」列を追加し、種別でフィルタ可能にする
- **詳細** (`show`): 種別を表示
- **更新** (`update`): 管理者が `species_type_id` を変更可能（出品者が設定ミスした場合の訂正用）
  - 種別変更時は **その発送単位の未承認送料（`shipping_approved_at = null` のもの）を自動再計算**。承認済みの場合は警告を出して変更不可にする（§4.6 と整合）
- 監査ログに `species_type_id` の変更履歴を残す

### 2.5 管理者による種別マスタ管理画面（新規）

`/admin/masters/species-types` を新設し、管理者が種別マスタを CRUD できるようにする。**メダカも含めて全てマスタ上で管理**し、コードデプロイなしで運用可能にする。

#### 2.5.1 画面構成

- 一覧ページ: `species_types` 全レコードを `sort_order` 順で表示。code / name / calculation_mode / is_active / is_mixable を列表示
- 新規作成 / 編集モーダル:
  - 必須: `code`（半角英数とアンダースコア。保存後は変更不可）/ `name` / `calculation_mode`
  - 任意: `is_mixable` / `sort_order` / `is_active` / `is_default`
- 削除: **論理削除のみ**（`is_active = false` に倒す）。実レコードは保持（過去の WonItem が参照しているため）
- 並び替え: ドラッグで `sort_order` を更新

#### 2.5.2 calculation_mode 切替時の挙動

| 現値 → 新値 | 動作 |
|---|---|
| auto → manual | 既存の袋・箱マスタは保持。以降の新規発送から手動化 |
| manual → auto | 袋・箱マスタが未投入なら保存時に警告。`bag_specs` が 0 件の状態で auto は選べない |

#### 2.5.3 袋・箱・混載マスタの編集画面

種別マスタ詳細ページ内にタブで束ねて、その種別の袋・箱・混載ルールを編集できるようにする：

- **袋タブ** (`bag_specs`): 袋サイズ / min_qty / max_qty / weight_kg の行を CRUD
- **箱タブ** (`box_capacities`): 箱サイズ × 袋サイズ × max_count の表を CRUD
- **混載制約タブ** (`bag_mix_restrictions`): 禁止ペアを CRUD

種別が `manual` の場合、これらのタブは非表示にする。

#### 2.5.4 追加カラム

`species_types` に次を追加（§2.1 の表を補強）：

| カラム | 型 | 説明 |
|---|---|---|
| is_default | boolean | 出品フォームの初期値に使う種別を 1 レコードだけ `true` にする。DB 制約で unique partial index を推奨 |

#### 2.5.5 権限

- 種別マスタの編集は**スーパー管理者ロールのみ**（既存の `admin` ロールを使うか、新規 `admin_master` ロールを用意）
- 一般管理者は閲覧のみ

#### 2.5.6 API

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/admin/masters/species-types` | 一覧 |
| POST | `/admin/masters/species-types` | 新規作成 |
| PATCH | `/admin/masters/species-types/{id}` | 更新 |
| DELETE | `/admin/masters/species-types/{id}` | 論理削除（`is_active=false`）|
| GET/POST/PATCH/DELETE | `/admin/masters/species-types/{id}/bag-specs` 等 | 種別配下の袋・箱・混載マスタ CRUD |

#### 2.5.7 出品者用 API

出品フォームでセレクトを描画するため、出品者向けに読み取り専用の API を追加：

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/seller/species-types` | `is_active=true` の一覧を返す（`code`, `name`, `sort_order`, `is_default`） |

## 3. 袋・箱マスタの種別化

### 3.1 bag_specs の種別化

現行: `bag_size` (S/M/L/KA) unique
変更後: `(species_type_id, bag_size)` で unique

| カラム | 型 | 備考 |
|---|---|---|
| species_type_id | bigint FK | 新規 |
| bag_size | string | 種別内でユニーク（S/M/L/KA 以外も許容） |
| min_qty / max_qty | int | 種別ごとに異なる匹数レンジ |
| weight_kg | decimal(4,1) | |

**マイグレーション**: 既存 bag_specs 全行に `species_type_id = (medaka の id)` を付与。

### 3.2 box_capacities の種別化

現行: `(box_size, bag_size)` unique
変更後: `(species_type_id, box_size, bag_size)` unique

金剛で袋→箱の入数が違うなら、`species_type_id=kongou` の行を追加するだけで対応できる形にする。

### 3.3 混載制約マスタ（新規テーブル）

現行: [ShippingCalculatorService.php:316-322](src/app/Services/ShippingCalculatorService.php#L316-L322) でコード内ハードコード
変更後: テーブル `bag_mix_restrictions` に外出し

| カラム | 型 | 説明 |
|---|---|---|
| species_type_id | bigint FK | どの種別のルールか。null なら全種別共通 |
| box_size | int | 対象の箱サイズ |
| bag_size_a | string | 禁止ペアの片側 |
| bag_size_b | string | 禁止ペアの片側 |

初期シード（メダカの既存ルールを移行）:

| species | box | a | b |
|---|---|---|---|
| medaka | 100 | S | M |
| medaka | null(全箱) | KA | M |
| medaka | null(全箱) | KA | L |

> 金剛のルールは運用側でヒアリング後に投入。

### 3.4 運賃表・資材マスタ

`shipping_rates` / `packing_materials` / `prefecture_regions` は**変更しない**。運賃・資材費は箱サイズと地域のみで決まるため種別非依存。

## 4. 計算ロジック変更

### 4.1 現行コードの抽象化

[ShippingCalculatorService.php](src/app/Services/ShippingCalculatorService.php) を次のように再構成する：

```
ShippingCalculatorService              ← エントリーポイント (既存シグネチャ維持)
  ├─ resolveStrategy(items): Strategy  ← 種別を見て戦略を選ぶ
  ├─ AutoCalculationStrategy           ← 現行ロジックを種別パラメータで駆動
  └─ ManualCalculationStrategy         ← 手動（計算せず null/0 を返し、手動入力待ち状態にする）
```

ファイル配置案:
- `src/app/Services/Shipping/ShippingCalculatorService.php`（既存を移動 or そのまま）
- `src/app/Services/Shipping/Strategy/AutoCalculationStrategy.php`
- `src/app/Services/Shipping/Strategy/ManualCalculationStrategy.php`
- `src/app/Services/Shipping/Strategy/MixedCalculationStrategy.php`

### 4.2 種別判定ロジック

入力 `items` から発送単位内の **ユニークな species_type 集合** を求めて分岐：

| 集合 | 採用戦略 | 備考 |
|---|---|---|
| 単一の `auto` 種別のみ（例: `{medaka}` / `{aquatic_plant}` / `{goldfish}`） | **Auto(その種別)** | 現行メダカ単独の結果と一致する |
| 複数の `auto` 種別が混在（例: `{medaka, aquatic_plant}`） | **Mixed (全自動)** | §4.4。`other` を含まない限り自動計算は続行する |
| `other` を 1 件でも含む | **Manual** | 発送単位全体を手動扱いにする |

ポイント: **自動か手動かの分岐は「その他が含まれるかどうか」だけ**。複数種別の混在そのものは手動化の理由にならない。

### 4.3 Auto 戦略（現行ロジックの一般化）

現行 [determineBagsForQuantity()](src/app/Services/ShippingCalculatorService.php#L94-L138) / [fitsInBox()](src/app/Services/ShippingCalculatorService.php#L300-L326) を**種別パラメータ受け取り型**に変える：

- BagSpec は `species_type_id` で絞り込む
- box_capacities も `species_type_id` で絞り込む
- 混載制約は `bag_mix_restrictions` を参照（§3.3）
- ハードコード条件（100号のS+M、KA+M/L）は削除し、全てマスタ参照に置き換える

**リグレッション保証**: メダカ単独の計算結果は現行と完全一致する必要がある（§8 テスト参照）。

### 4.4 Mixed 戦略（複数の auto 種別が同一発送単位に存在）

このケースでも**最終的には 1 つの `total_shipping_fee` を返す自動計算**である。実装方針は **「種別別に袋詰めし、箱詰めは `is_mixable` フラグで同一箱への混載可否を判定」**:

1. 種別ごとに `determineBags()` を実行し、袋リストを種別タグ付きで生成
2. 箱詰めフェーズで、同一箱に入れられる袋を次の条件で決定
   - 同一箱内の全袋の `species_type.is_mixable = true` → 同一箱に混載OK
   - いずれかが `is_mixable = false` → その種別は**専用箱**で詰める
3. 各箱には「その箱に入っている袋の種別」の box_capacities と bag_mix_restrictions を適用する
   - 異なる種別の袋が同一箱に入る場合は、双方の制約の**厳しい方**を適用（AND）
4. 運賃・資材費は従来どおり箱サイズ × 地域 × 資材マスタで算出
5. 結果の `species_breakdown` に種別別小計を出し、合算値を `total_shipping_fee` とする

**リリース初期の推奨運用**: `is_mixable` を全種別 `false` にしておけば、「種別ごとに別箱を立てて合算するだけ」のシンプルなモードに退化する。同梱での値引きが運用上不要なら、この単純モードのまま本番投入して良い。後から運用者判断で `is_mixable=true` に切り替えれば同梱最適化が有効になる。

### 4.5 Manual 戦略

- `total_shipping_fee = null`、`shipping_breakdown = { mode: "manual", reason: "その他種別のため手動入力" }` を返す
- `WonItem.shipping_fee_auto = null`、`shipping_calculated_at = now()`
- 管理者画面で**手動入力必須**フラグが立つ（§5）

## 5. 管理画面・API 変更

### 5.1 落札者画面

- 自動計算種別のみ（単一 or 複数種別の混在）の発送単位: 現行どおり「送料を計算」ボタンで確定。複数種別の場合は**種別別小計＋合計**を表示
- 「その他」を含む発送単位: 送料計算ボタンは**非活性**。「管理者による送料確定をお待ちください」と表示

### 5.2 管理者画面

- WonItem 一覧に「種別」列を追加
- 詳細画面に「送料手動入力」フォームを追加
  - 手動扱いの WonItem は入力必須
  - 自動扱いでも管理者が上書き可（既存の `shipping_adjustment_reason` 必須ルールを踏襲）
- 承認フロー（`shipping_approved_at`）は現行どおり

### 5.3 API

現行ルートのリクエスト/レスポンスは維持。レスポンスに以下を追加：

```jsonc
{
  "calculation_mode": "auto" | "manual" | "mixed",
  "species_breakdown": [
    { "species_type": "medaka", "quantity": 120, "subtotal_fee": 1320 },
    { "species_type": "kongou", "quantity": 10,  "subtotal_fee":  900 }
  ],
  // 既存フィールドは維持
  "bags": [...], "boxes": [...],
  "shipping_cost": 2220, "packing_material_cost": 900,
  "total_shipping_fee": 3120
}
```

手動の場合は `bags`/`boxes` を空配列、`total_shipping_fee` を `null` で返す。

## 6. データモデル変更サマリ

### 6.1 新規テーブル

- `species_types` (§2.1 + §2.5.4 で `is_default` 追加)
- `bag_mix_restrictions` (§3.3)
- `species_type_audit_logs`（任意）: `species_type_id` / 変更者 / 変更前後の JSON / 変更日時。マスタ変更履歴の監査用

### 6.2 既存テーブルの変更

| テーブル | 変更 |
|---|---|
| items | `species_type_id` (FK, nullable→後に required) 追加 |
| bag_specs | `species_type_id` 追加、unique を `(species_type_id, bag_size)` に変更 |
| box_capacities | `species_type_id` 追加、unique を `(species_type_id, box_size, bag_size)` に変更 |
| won_items | `calculation_mode` (enum auto/manual/mixed) 追加（履歴保持用） |

### 6.3 マイグレーション順序

1. `species_types` 作成＋初期シード (medaka, aquatic_plant, goldfish, other)
2. `items.species_type_id` 追加、既存全件を medaka にバックフィル
3. `bag_specs` / `box_capacities` に `species_type_id` 追加、既存行を medaka に紐付け、unique 貼り直し
4. `bag_mix_restrictions` 作成＋メダカのルール投入
5. `won_items.calculation_mode` 追加
6. **コード上はまだ medaka のみを参照** → 結果が完全一致することを検証（§8.1）
7. サービスコードをマスタ参照に切替
8. 金剛のマスタデータを投入（運用作業）

各マイグレーションはロールバック可能に書き、本番反映前にステージングで `migrate:fresh --seed` → E2E ゴールデン実行。

## 9. リリース計画

1. **Phase 1**: マスタ新設＋バックフィル（メダカのみで動作確認、§6.3 の 1〜6）
2. **Phase 2**: 戦略パターン化＋リグレッションテスト緑化
3. **Phase 3**: 出品フォームに種別セレクト追加（medaka のみ `is_active=true` の状態でリリース）／管理者生体管理画面に種別カラム追加
4. **Phase 4**: 管理者種別マスタ画面 `/admin/masters/species-types` を公開（§2.5）。CRUD と袋・箱・混載マスタ編集 UI
5. **Phase 5**: 「その他」種別を `is_active=true` に切替、手動計算フローを UI 含めて解禁
6. **Phase 6**: 水草・金魚のマスタを運用側で投入し、セレクト選択肢に追加（混在ケースは自動で動く）
7. **Phase 7**: 将来種別追加は**運用作業のみ**で完結（管理画面からマスタ投入 → 即反映、コードデプロイ不要）

Phase 1-2 は無停止でリリース可（挙動変化なし）。Phase 3 以降は段階的に機能フラグで制御。
