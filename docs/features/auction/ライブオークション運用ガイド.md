**対象読者**: 運営・カスタマーサポート・出品者対応・経営判断者

## 1. 1分でわかるオークションの仕組み

### 1.1 登場人物

- **管理者（オペレーター）**: 「スタート！」を押す人
- **参加者（ビッダー）**: スマホ・PCで参加する人（最大300名想定）
- **出品者**: 商品を出す人（ライブ中は基本見るだけ）
- **システム**: バックエンドが自動でカウントダウン・価格上昇・落札確定を処理

### 1.2 「レーン」という概念

普通のオークションは「司会者が1個ずつ競り上げる」が、本システムは **複数レーンを並行進行** できる。

```
┌── レーン1 ──┐  ┌── レーン2 ──┐  ┌── レーン3 ──┐
│ 商品A 競り中│  │ 商品E 競り中│  │ 商品I 競り中│
│   ↓        │  │   ↓        │  │   ↓        │
│ 商品B 待機  │  │ 商品F 待機  │  │ 商品J 待機  │
│ 商品C 待機  │  │ 商品G 待機  │  │ 商品K 待機  │
│ 商品D 待機  │  │ 商品H 待機  │  │ 商品L 待機  │
└────────────┘  └────────────┘  └────────────┘
```

各レーンが独立に競りを進める。参加者画面ではタブでレーン切替可能。

## 2. オークションの状態遷移

```
[draft]      出品準備中
  ↓
[scheduled]  開始日時セット済み・受付中
  ↓
[preparing]  当日、出品物確定済み
  ↓ ←★管理者が「スタート」ボタンを押す
[live]       競り進行中  ←─┐
  ↓                        │ 一時停止/再開
[finished]   全商品終了    └─[paused]
```

## 3. 「スタート」を押すと何が起きるか

```
管理者：「スタートボタン」を押す
   │
   ▼
[システム内部の動き]
1. 全商品をレーンに振り分ける
   （プレミアム商品は優先的に配置）

2. 「あと10秒で開始します！」を全員の画面に表示
   ┌──────────────────────────┐
   │   開始まで 10秒...       │
   └──────────────────────────┘

3. 10秒経過 → 各レーンの最初の商品をライブ表示

4. 「オークションが開始されました」を全員に通知
   （LINE通知・メール通知も同時送信）

5. 各レーンでカウントダウン開始
```

**重要**: スタートを押した後、10秒間はキャンセル不可。

## 4. 競り1回の流れ（最重要）

商品1つに対する基本サイクルは **「3つのフェーズ」** を持つ。

### フェーズ1: 入札開始待機（pre_bid）

```
┌─────────────────────────────────────────┐
│  【次の商品】メダカ ラメ系 5匹           │
│  開始価格 1,000円                        │
│                                          │
│      入札開始まで 5秒...                 │
│                                          │
│   [入札ON] ← まだ押せない（グレーアウト）│
└─────────────────────────────────────────┘
```

- **目的**: 商品切替直後の誤タップ防止
- **長さ**: デフォルト5秒（オークション設定で変更可）
- **入札ボタン**: 押せない（フロント＆サーバ両方で拒否）

### フェーズ2: 入札受付（bidding）

```
┌─────────────────────────────────────────┐
│  メダカ ラメ系 5匹                       │
│  現在価格 1,000円                        │
│                                          │
│      残り 3.0秒                          │
│      入札中: 0人                         │
│                                          │
│   [入札する] ← 押せる！                  │
└─────────────────────────────────────────┘
```

- **長さ**: 価格帯ごとに設定（例: 1万円以下は3秒、10万円以上は5秒など）
- 0.5秒ごとに残り秒数が更新される（WebSocket でリアルタイム）

#### このフェーズでの結末（v1.1 単方向入札仕様）

商品に **指値（事前上限価格）** が登録されているかどうかで動作が変わる。

**A. 指値が1件以上登録されている商品**

| 押下のタイミング | 結果 |
|---|---|
| 1人目が押した瞬間 | 即座に価格上昇＋フェーズ3（freeze）へ。**押下者が落札権利者** として確定（指値ホルダーが別にいる場合は指値ホルダー優先） |
| 既に他者が落札権利者（active）の状態で押下 | **無視される**。再押下は次の価格枠で有効に |
| 0秒到達時に active=0 | 流札 |
| 0秒到達時に active=1 | その人が落札 |

**B. 指値が1件も登録されていない商品（従来動作）**

| 残り秒数が0になった時の入札者数 | 結果 |
|---|---|
| **0人** | 流札（unsold） → 次の商品へ |
| **1人** | その人が落札 → 次の商品へ |
| **2人以上** | 価格上昇 → フェーズ3（freeze）へ。**最後に押した人** が落札権利者 |

> なぜ動作が違う？ — 指値ありの商品は「自動的に価格を吊り上げる仕組み」が既にあるので、人が1人押しただけでも公平に競り上げを開始してよい。指値なしの商品は1人だけの参加で開始価格落札を成立させるため、2人目を待つ。

### フェーズ3: 凍結（freeze）

```
┌─────────────────────────────────────────┐
│  メダカ ラメ系 5匹                       │
│  現在価格 1,100円 ← 100円アップ！        │
│                                          │
│      凍結中... 1.5秒                     │
│      入札中: 1人（あなた・最高入札者）   │
│                                          │
│   [最高入札者] ← 押せない（金色固定表示）│
└─────────────────────────────────────────┘
```

- **目的**: 価格上昇直後の連打誤タップ防止
- **長さ**: 価格帯ごとに設定（短いもので0.5秒、長くて2秒程度）
- **入札ボタン**: 全員押せない（落札権利者は「最高入札者」表示で固定）
- v1.1 単方向入札: **このフェーズで自分から降りる動線はない**（権利者・非権利者問わず）

### フェーズが終わるとどうなる？

```
凍結 終了 → 入札受付フェーズに戻る → 価格はそのまま、新しい押下を待つ
　　　　　　　他の人が押せば、その人が新権利者・前権利者は自動離脱
　　　　　　　誰も押さなければ、現権利者が0秒到達で落札
```

**v1.1 ポイント**:
- 価格は「次の押下が来るまで」上がらない（指値あり商品では1押し＝1サイクル、指値なしでは2押し＝1サイクル）
- 権利者は次の価格枠で他の誰かに権利を譲る／逃げ切って落札 のいずれか
- 自分の意思で降りる動線は無いので、**入札する＝最後まで戦う覚悟** の意思表示

## 5. シナリオ別の動き（v1.1 単方向入札仕様）

### 5.1 指値なし商品（従来動作）

```
時刻 T=0
　商品X 1,000円　残り3秒　入札中=0人
　　　　　　　　　　　　　　　 ↓
時刻 T=1
　商品X 1,000円　残り2秒　入札中=1人 (Aさん)　← まだ価格は上がらない
　　　　　　　　　　　　　　　 ↓
時刻 T=2
　商品X 1,000円　残り1秒　入札中=2人 (Aさん, Bさん)
　　　　　　　　　　　　　　　 ↓ ※2人目のBさんが押した瞬間に発動
　　　　　　　　　　　　　　　 価格1,100円に上昇／Aさんは自動離脱
　　　　　　　　　　　　　　　 freeze 1.5秒
時刻 T=3.5
　商品X 1,100円　残り3秒　入札中=1人 (Bさん)　← biddingに復帰
　　　　　　　　　　　　　　　 ↓
時刻 T=6.5
　残り0秒・入札中=1人 (Bさん) → 落札確定！
```

### 5.2 指値あり商品（v1.1 で動作変更）

前提: 商品Yに別途 Cさんが「上限 50,000 円」の指値を登録済み

```
時刻 T=0
　商品Y 1,000円　残り3秒　入札中=0人
　　　　　　　　　　　　　　　 ↓
時刻 T=0.1
　Aさんが押す（残り2.9秒）
　　　　　　　　　　　　　　　 ↓ ※指値あり商品なので1人目発動
　　　　　　　　　　　　　　　 価格1,100円に上昇／freeze 1.5秒
　　　　　　　　　　　　　　　 落札権利者 = Cさん（最高指値ホルダー）
　　　　　　　　　　　　　　　 ※Aさんは指値より低い手動入札なので auto-left
時刻 T=0.15
　Bさんが押す（残り2.85秒）　← Aさんの押下から0.05秒後の滑り込み
　　　　　　　　　　　　　　　 ↓
　　　　　　　　　　　　　　　 freeze cache が既に書き込まれている → "誤タップ防止中"
　　　　　　　　　　　　　　　 で弾かれて 無視。bid_events に "ignored" 記録
時刻 T=1.6
　freeze 終了 → bidding 復帰　商品Y 1,100円　残り3秒　入札中=1人 (Cさん)
　　　　　　　　　　　　　　　 ↓ Bさんは次の押下で参戦できる
時刻 T=2.5
　Bさんが押す → 1人目発動 → 価格1,200円／freeze／権利者 Cさん（指値が優位）
　…以下、Cさんの指値 50,000 円に到達するまで自動的に競り上がる
```

### 5.3 落札権利者になった後の挙動（重要）

**v1.1 では落札権利者になった後、もう一度ボタンを押しても何も起こらない**（ボタンは「最高入札者」表示で disabled）。

旧仕様では「もう一度押すと OFF（離脱）」だったため、誤って降りてしまう事故が起きうる動線になっていた。
v1.1 ではサーバー側でも `is_active=false` のリクエストを 403 で拒否しているため、二重防御になっている。

**ポイント**:
- 入札ボタンは **押す＝戦う宣言**。降りる動線は無い
- 自分以外の誰かが押せば、そこで自動的に権利が譲られる（auto-left）
- 自分が逃げ切れば落札（次の0秒到達時に唯一のactiveなら確定）

## 6. 指値（じさし）= 上限価格設定

参加者は **事前 or ライブ中** に「いくらまでなら出す」を設定できる。

### 動作イメージ

```
Aさんが商品Yに「最大10,000円まで」と指値を設定
　　　　　　　　　　　　 ↓
ライブ中、商品Yの価格が上昇していく
　　1,000 → 2,000 → ... → 9,000円
　　　　　　　　　　　　 ↓
Aさんが入札ON にしてなくても、システムが自動で「Aさんは入札中」と判定
　　　　　　　　　　　　 ↓
価格が10,000円を超える瞬間 → 「指値発動」 → Aさんを自動で離脱
　　　　　　　　　　　　 ↓
Aさんに「上限価格に達したため離脱しました」をLINE/画面で通知
```

**設定の特典**:
- 自分が画面を見ていなくても、上限まで自動で競り続ける
- 上限を超えたら自動で諦める（=払いきれない金額に達しない）

**注意点**:
- 同一商品に複数人が指値を入れると、最高指値の人が優位になる
- 指値が複数いる場合、システムが「2番目に高い指値の次の単位」まで自動で価格を引き上げる
- 指値ホルダーが2人以上残っていると、最高指値の人が落札権利者として残る

### 7.1 参加者の画面でできること

| 機能 | いつ使う | システムの裏で動くもの |

| お気に入り一覧確認 | いつでも | DB読込 |

| 商品検索 | 競り中も可 | DB検索 |
| AIレコメンド | 競り中も可 | レコメンドサービス問い合わせ |

### 7.2 管理者の画面でできること

| 機能 | 説明 |
|---|---|

## 8. システムが「自動で」やっていること

参加者・管理者が何もしなくても、**裏側で常に動いているもの**:

### 8.1 リアルタイム配信（WebSocket / Reverb）

```
0.5秒ごとに全員の画面に「残り秒数」「現在価格」「入札人数」を送信
　　↑
　　0.5秒に1回、各レーンから1メッセージずつ
　　12レーンなら 24メッセージ/秒、参加者300人なら 7,200メッセージ/秒の配信
```

### 8.2 カウントダウンジョブ（バックグラウンド）

```
ライブ開始時に1本だけ起動するワーカー
　　↑
　　1オークション = 1ジョブ（最長4時間動く）
　　0.5秒ごとに全レーンを1回ずつ tick
　　商品終了→次商品移行も全部このジョブが行う
```

### 8.3 死活監視（毎分）

```
1分に1回、システムが「カウントダウンジョブが生きてるか」をチェック
　　↑
　　最後の心拍が30秒以上前 = 死亡判定
　　→ 自動で新ジョブを起動（既存ジョブは自発的に終了する世代管理）
```

### 8.4 自動通知

| タイミング | 通知内容 | 送信先 |
|---|---|---|
| オークション開始時 | 「○○オークションが始まりました」 | 全参加者・出品者（LINE/メール） |
| 指値発動時 | 「上限価格に達したため離脱しました」 | 該当ユーザー（LINE） |
| 落札時 | 「○○を落札しました」 | 落札者（LINE/メール） |
| お気に入り商品が高騰 | 「お気に入りが残り○分」 | 該当ユーザー（LINE） |
| 開催前日 18:00 | 「明日○○が開催されます」 | 全関係者（LINE/メール） |

## 9. キュー・Redis・データベース：どこで何が動いているか

```
┌─────────────────────────────────────────────────────┐
│             ユーザーの操作・画面更新                 │
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ Web サーバ（Laravel）                                │
│ - 入札・お気に入り・指値の API を受ける              │
│ - 同時に来た入札を Redis で1件ずつ整列処理           │
└─────────────────────────────────────────────────────┘
        ↓                     ↓                  ↓
┌──────────────┐  ┌──────────────────┐  ┌──────────────────┐
│ MySQL (DB)   │  │ Redis            │  │ Reverb (WS)      │
│ - 入札履歴   │  │ - 入札ロック5秒  │  │ - 全員に          │
│ - 落札確定   │  │ - カウントダウン │  │   リアルタイム    │
│ - 商品/価格  │  │   状態1時間保持  │  │   配信            │
│ - 永続データ │  │ - ハートビート   │  │                  │
└──────────────┘  └──────────────────┘  └──────────────────┘
                       ↑
┌─────────────────────────────────────────────────────┐
│ バックグラウンドワーカー（Supervisor が常駐管理）     │
│ - countdown ワーカー: カウントダウンジョブを実行     │
│ - default ワーカー: メール送信・通知などの軽作業     │
│ - notifications ワーカー: LINE 送信専用              │
└─────────────────────────────────────────────────────┘
```

### キューに入る vs 入らない

| 処理 | キューに入る？ | 理由 |
|---|---|---|
| 入札ON/OFF | 入らない（同期） | 即時応答が必要 |
| 価格上昇判定 | 入らない（カウントダウンジョブ内で同期） | 0.5秒の精度が必要 |
| 落札確定 | 入らない（カウントダウンジョブ内で同期） | データ整合性が最優先 |
| LINE通知 | **入る**（notifications キュー） | 失敗してもオークションは止めない |
| メール送信 | **入る**（default キュー） | 同上 |
| 動画変換 | **入る**（default キュー） | 重い処理は非同期 |
| カウントダウン本体 | **入る**（countdown キュー） | 1ジョブで4時間継続実行 |
| 死活監視 | crontab（毎分）→ 入らない | 軽量チェック |

### Redis（メモリ上のキャッシュ）に持つもの

- カウントダウンの残り秒数（**永続不要、消えても tick 経由で復旧可能**）
- 入札中の「処理中ロック」（5秒で自動消滅）
- ハートビート（最後の更新時刻、4時間TTL）
- ジョブの世代番号

> **DB に書くもの = 失っちゃダメな永続データ**
> **Redis に書くもの = 速さ重視で、消えても復旧できるもの**

## 10. 不正・誤動作からどう守られているか

| 不安 | 対策 |
|---|---|
| 「2人同時にONタップしたら？」 | Redis で1件ずつ順番に処理（先勝ちで残りは即お断り） |
| 「ボタン連打したら多重入札？」 | DB で「入札中=1回」しか持たない設計（連打しても意味なし）。v1.1 では active になった時点でボタン自体が disabled |
| 「最高入札者になった後に誤って降りる事故」（v1.1 改善） | **OFF/離脱動線を完全廃止**。フロントは active で disabled、サーバーも `is_active=false` を 403 拒否。二重防御 |
| 「ネットが切れたら？」 | サーバ側の状態が真。再接続時に状態を再取得して同期 |
| 「サーバが落ちたら？」 | カウントダウンジョブが死んだ場合 60 秒以内に自動再起動 |
| 「価格上昇直後の誤タップ」 | freeze（凍結）フェーズで入札不可（フロント・サーバ両方で拒否）。さらに freeze cache 反映前に滑り込んだタップも JoinBidAction の existing-active-winner ガードで弾く（指値あり商品） |
| 「商品切替直後の誤タップ」 | pre_bid（待機）フェーズで入札不可 |
| 「悪意ある大量リクエスト」 | API 側にレート制限を設定済み（入札 4回/秒、指値 2回/秒、お気に入り 60回/分）。超過すると 429 エラー。 |

## 11. オペレーター（管理者）が知っておくべきこと

### 11.1 開始前チェックリスト

- [ ] **`php artisan auctions:check-config --strict`** を実行し、`All checks passed.` を確認（queue/cache/Redis/Reverb 設定の自動検証）
- [ ] `supervisorctl status` で全プロセス RUNNING を確認
- [ ] `php artisan queue:failed` で失敗ジョブが残っていないか確認
- [ ] Reverb のポートが 6001 で正しく動いているか確認
- [ ] ログディスク残量（`df -h`）に余裕がある
- [ ] 当日の `auctions:start-scheduled` が動くタイミングを把握
- [ ] 緊急停止用の SSH 接続は事前にテスト

### 11.2 ライブ中に絶対やってはいけないこと

| NG | 理由 |
|---|---|
| `php artisan migrate` を実行 | DB ロック競合で全レーンが止まる |
| `supervisorctl restart all` | カウントダウン中のジョブが kill され、復旧まで5〜30秒の中断 |
| `php-fpm` 再起動 | 進行中の入札 tx が失敗し、参加者にエラーが返る |
| `.env` を変更して `config:cache` を流す | 一部の設定が古いまま新ジョブが起動して挙動不一致 |
| Reverb を再起動 | 全員が WebSocket 切断 → ポーリングフォールバック中は表示遅延 |

### 11.3 やむを得ず再起動する場合の影響

- **queue-countdown ワーカー再起動** → 既存の countdown ジョブは中断 → 60秒以内に MonitorAuctionJobs が新ジョブで復旧 → tick が最大1分スキップ（参加者画面では「残り秒数」が一瞬止まって見える）
- **Reverb 再起動** → 全員が WS 切断 → 約3秒で再接続 → その間の broadcast はロスト（API 取得時に整合回復）
- **php-fpm 再起動** → 実行中の HTTP リクエストが失敗 → 参加者は再タップで復旧

### 11.4 緊急時のアクション

| 状況 | 対応 |
|---|---|
| 「カウントダウンが3秒のまま止まった」 | `tail -f /var/log/supervisor/queue-countdown.log` でエラー確認。`supervisorctl restart queue-countdown` で復旧。1分以内に自動再起動するが、急ぎなら手動で。 |
| 「全員から『入札できない』報告」 | Reverb 確認 → `supervisorctl status reverb`、ログ `/var/log/supervisor/reverb.log` |
| 「特定商品だけ価格が上がらない」 | DB で `bid_participants` の `is_active` カウント、`countdown:lane:{id}` キャッシュ確認 |
| 「落札したのに `won_items` に入ってない」 | `storage/logs/laravel.log` で「Item ... sold」を grep。なければ finalize 失敗の可能性 |

## 12. よくある質問（FAQ）

### Q. 入札ボタンを押した瞬間に「処理中です」と出ました
A. 同一商品で他の参加者の入札処理中（最大数十ms）。再タップで通常成功する。300人同時タップ時は数秒の待機が発生。

### Q. 「既に他のユーザーが落札権利者です」と出ました（v1.1 NEW）
A. 指値あり商品で、ごく僅かな差で他の人が先に押下し落札権利者になった状態。次の価格枠（freeze 終了後）で再度押せば参戦できる。

### Q. 残り秒数が「3.0」のまま止まっています
A. カウントダウンジョブが死んでいる可能性。最大60秒以内に自動復旧する。続くようなら運営連絡。

### Q. 自分が「最高入札者」のはずなのに「入札中ではない」表示
A. 他の人が次の価格枠で押下したことで、自分が auto-left された状態。再タップでON可能。
v1.1 では「最高入札者」ボタンが押せなくなっているので、表示が「入札する」（押せる）に切り替わっていれば降ろされた合図。

### Q. 「最高入札者」になったのに、もう一度押せないんですが（v1.1 仕様）
A. **これが正しい挙動です**。v1.1 から落札権利者になった人は自分から降りられません。誤って離脱しないよう、ボタン自体が disabled 表示に固定されます。
権利が譲られるのは「他の人が押した瞬間」または「価格が指値に到達して指値ホルダーが優先される瞬間」のみ。

### Q. 指値を入れたのに発動していません
A. 価格が上限を超えていない or オークションがまだ live 状態でない。`bid_limit_prices` テーブルの `is_triggered` フラグで確認可能。

### Q. オークション中に商品を追加できますか
A. 技術的には可能だが、推奨しない（lane 割当が崩れる）。事前確定が原則。

### Q. 同時に何人まで参加できる？
A. 設計目標は300名。それ以上は要負荷検証。詳細は [300名負荷リスク評価](./300名負荷リスク評価とレビュー指摘.md) を参照。

## 13. 用語集

| 用語 | 意味 |
|---|---|
| ライブ（live） | オークションが進行中の状態 |
| レーン（lane） | 並行進行する競りの帯。1レーン = 1つの司会者枠と思えばよい |
| 入札（v1.1〜） | 「この価格で買う意思あり」の宣言。**ON 一方向**で降りられない。連打は意味なし |
| 落札権利者 | 現在価格を提示している唯一の人。次の0秒到達まで誰も押さなければ落札 |
| auto-left | 他の人が次の価格で押した時に、前の権利者が自動的に離脱されること（システム経由のみ） |
| pre_bid | 商品切替後の待機時間（5秒程度） |
| bidding | 入札受付フェーズ（カウントダウン中） |
| freeze | 価格上昇後の凍結フェーズ（誤タップ防止） |
| 指値（さしね） | 「いくらまでなら出す」の上限金額 |
| カウントダウンジョブ | バックグラウンドで0.5秒ごとに全レーンを進めるワーカー |
| ハートビート（heartbeat） | カウントダウンジョブの「生きてます」信号 |
| 世代（generation） | ジョブの版数。新しいジョブが起動すると番号が +1 され、古いジョブは自発終了 |
| Redis | 速さ重視のメモリ DB。カウントダウン状態などを保持 |
| Reverb | Laravel の WebSocket サーバ。リアルタイム配信担当 |
| Supervisor | バックグラウンドプロセスを常駐管理するソフト |
