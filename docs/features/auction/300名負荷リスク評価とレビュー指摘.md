## 2. 🔴 Critical-1: 入札系 API に throttle が一切ない

### 現状

`routes/api.php` の参加者ルートには **`throttle` ミドルウェアが定義されていない**:

```php
// routes/api.php:411-415
Route::middleware('check.subscription:bid')->group(function () {
    Route::post('/bids', [ParticipantBidController::class, 'toggle']);
    Route::post('/bid-limits', [ParticipantBidLimitController::class, 'store']);
    Route::delete('/bid-limits/{itemId}', [ParticipantBidLimitController::class, 'destroy']);
});
```

ファイル全体（517行）で `throttle` の文字列が **0 ヒット**。
Laravel 11 の `bootstrap/app.php` でも未設定。RouteServiceProvider も使っていない。

### リスク

| 攻撃ベクター | 結果 |
|---|---|
| 1人の悪意ユーザーが `/bids` を秒間1万回叩く | php-fpm が枯渇、全員のレスポンスが遅延 |
| `/favorites/toggle` の連打 | DB の `favorites` テーブルへの write 集中 |
| `/bid-limits/{itemId}` の DELETE 連打 | DB write 集中＋ログスパム |
| ボット連打で `bid_inflight:item:X` lock を 5 秒占有 | 他者の入札が「処理中です」エラー連発 |

### 対策案

**優先順位1（必須）**: 認証済みユーザーごとのリクエスト制限を入れる。

```php
// 入札系: 1秒に2回まで（連打抑制 + 通常操作は許容）
Route::middleware(['check.subscription:bid', 'throttle:bid_per_user'])->group(function () {
    Route::post('/bids', [ParticipantBidController::class, 'toggle']);
    Route::post('/bid-limits', [ParticipantBidLimitController::class, 'store']);
    Route::delete('/bid-limits/{itemId}', [ParticipantBidLimitController::class, 'destroy']);
});
```

`bootstrap/app.php` の `withRouting` 内で:

```php
RateLimiter::for('bid_per_user', function (Request $request) {
    return Limit::perSecond(2)->by($request->user()?->id ?? $request->ip());
});

RateLimiter::for('favorite_per_user', function (Request $request) {
    return Limit::perMinute(60)->by($request->user()?->id ?? $request->ip());
});
```

**優先順位2**: グローバル throttle（IP 単位）も併用。

```php
RateLimiter::for('global_api', fn (Request $r) => Limit::perMinute(300)->by($r->ip()));
```

**優先順位3**: AWS WAF レート制限ルール（`docs/infrastructure/AWS_WAF_DDoS対策設定手順書.md` 参照）を有効化。

### 注意

- 入札ボタンの「ON状態維持」は **押し続ける必要がない**（DB 上で 1 row 持つだけ）ので、
  通常ユーザーは秒間2回 throttle で十分。
- ただし `bid_inflight` lock 待ちでクライアント側がリトライする場合があるので、
  クライアント側で「処理中エラー時の自動リトライは1回まで」のガードも入れる。

## 3. 🔴 Critical-2: Reverb の outbound 帯域・接続数

### 現状

[useAuctionSocket.ts:86-225](../../../resources/ts/hooks/useAuctionSocket.ts) で `auction.{id}.live` を全員が購読。
[CountdownService::tick](../../../app/Services/CountdownService.php) は **0.5秒ごと、全レーンで** broadcast(CountdownTick) を発行。

### 計算

```
N レーン × 2 tick/秒 = 2N msg/秒（auction.{id}.live チャンネル）
300名が購読 → サーバ outbound = 300 × 2N msg/秒
12レーンの場合 = 7,200 msg/sec
1メッセージ ≈ 300 byte（CountdownTick の payload）として、約 2.1 MB/sec
```

加えて:
- 入札ON/OFF 連打 → BidderUpdated ブロードキャスト（イベント数は緩いが100req/秒なら 30,000msg/sec）
- 価格上昇 → PriceUpdated（頻度は低いが auto_left_user_ids 含むので payload 大）

### 既知の Reverb 仕様

- 単一プロセスで動かす場合、outbound は CPU 1 コア律速
- `config/reverb.php` の `scaling` モードを ON にすると Redis pub/sub で複数プロセス分散可能
- ただし scaling ON でも broadcast latency が 50〜100ms 程度上昇する報告あり

### リスク

| シナリオ | 結果 |
|---|---|
| Reverb 単プロセスで 7,200msg/sec を捌けない | broadcast 遅延 → 残り秒数表示がガクガク |
| クライアント側で WS 受信処理が追いつかない | ブラウザのメモリ膨張 → タブクラッシュ |
| Reverb プロセスが詰まって死ぬ | フロントは API ポーリングフォールバックに切替（仕様上） |

### 対策案

**優先順位1（事前検証必須）**: 本番同等構成で **負荷試験**。

`load-tests/` にツールがあるはず（プロジェクトルートに `load-tests` ディレクトリ確認済）→ 流す。

**優先順位2**: tick イベントを減らす設計検討:

- 現状: 0.5秒ごとに `CountdownTick` をフル payload で送信
- 案A: tick payload に price と active_count を含めているので、`PriceUpdated` を廃止して tick 1本に統合（payload 重複削減）
- 案B: 残り秒数の表示はクライアント側でローカル減算 → サーバからの tick は 1秒に1回 or freeze/phase切替時のみに
- 案C: Differential update — 変更された値だけ broadcast

**優先順位3**: Reverb scaling 有効化＋プロセス複数化（`REVERB_SCALING_ENABLED=true`）。
ALB の sticky session 設定確認。

### 影響度

- 7,200 msg/sec が捌けない場合、UI 表示が乱れる程度。**入札本体は API で動いているので、落札可否は影響しない**
- ただし参加者は「カウントダウンが正しく見えない」と感じる → クレーム源

## 4. 🔴 Critical-3: 指値の自動入札が JoinBidAction をバイパス

### 現状

新商品が live になる時、[ProcessAuctionCountdownJob.php:151-161](../../../app/Jobs/ProcessAuctionCountdownJob.php#L151-L161) で:

```php
$setBidLimitAction->activatePendingBidLimits($lane->currentItem);
if ($activated >= 2) {
    $countdownService->adjustPriceByBidLimits($freshItem, $lane->auction, $lane, false);
}
```

`activatePendingBidLimits` の中身は確認していないが、おそらく `BidParticipant::participate()` を直接呼ぶ実装。
これは **JoinBidAction の lock 順序プロトコルを通らない**:

- `bid_inflight:item:X` Redis lock を取らない
- `items.lockForUpdate()` を取らない
- pre_bid フェーズ判定を通らない

### リスク

#### 3-1. pre_bid 中の price 変動

新商品が `pre_bid` フェーズに入った直後、自動入札 → `adjustPriceByBidLimits` が走る。
ここで価格が `start_price` から上昇する。

`startPreBidCountdown` で計算した `bid_countdown_seconds` は **start_price 基準** なので、
価格が上昇したのに pre_bid 終了時に古い秒数で `bidding` フェーズが始まる。
（tick L257-264 で「金額帯テーブル対応の同期」があるが、起動直後の1tick 分はズレる）

**影響度**: 軽微（0.5秒のズレ）だが、参加者から見ると「pre_bid 中に価格が変わった」と気づかれる。

#### 3-2. ロック順序プロトコル違反のデッドロック可能性

memory: `project_bid_lock_order.md` で記録された原則は「items 行ロック先取りで子テーブルを直列化」。
`activatePendingBidLimits` が `items` 行ロックを取らず `bid_participants` だけ書き込むと、
同時に走っている `handlePriceIncrement`（items lock 取得済み）と競合してデッドロック。

幸い、`activatePendingBidLimits` は商品 `live` 化の **直後（他に並行処理がない瞬間）** に呼ばれるので、
今のところは問題ない。だが将来「ライブ中の指値追加」を許す改修を入れたら破綻する。

#### 3-3. broadcast(BidderUpdated) の漏れ

`activatePendingBidLimits` が直接 participate を呼ぶ場合、`BidderUpdated::joined` が broadcast されない可能性。
フロントは `active_count` の更新を CountdownTick の active_count フィールドから取得するので致命傷ではないが、
個別ユーザーが「自分が指値で参加状態になった」を即座に画面に反映できない。

### 対策案

**短期**: `activatePendingBidLimits` の実装を読み、上記3点を確認。
broadcast の補完 + items lock 追加 + pre_bid 中の price 上昇を抑制（pre_bid 終了後に adjustPriceByBidLimits を遅延実行）。

**長期**: 自動入札も JoinBidAction 経由に統一する設計改修。
ただし「pre_bid 中なら入札拒否」を JoinBidAction が返すので、
auto-bid 用フラグを引数に足して pre_bid 拒否をスキップさせる必要あり。

## 5. 🔴 Critical-4: DB queue ドライバ使用時の `jobs` テーブル詰まり

### 現状

`config/queue.php` のデフォルト:

```php
'default' => env('QUEUE_CONNECTION', 'database'),
```

本番 `.env` が `QUEUE_CONNECTION=redis` になっていれば良いが、もし `database` のままだと:

- `ProcessAuctionCountdownJob` は `countdown` キューで dispatch
- 4時間動くジョブを `jobs` テーブルから取る → そのレコードが4時間 reserved 状態
- 同時に他のジョブ（LINE 通知、メール）も同じテーブルに突っ込まれる
- queue worker が `SELECT ... FOR UPDATE SKIP LOCKED` する際、reserved レコードを毎回 skip する負荷が積み重なる

### リスク

- **小規模で本番運用するなら DB queue で問題なし**だが、300名規模で `notifications` キューに LINE 送信が秒間数十件入ると、`jobs` テーブルへの insert / select が DB に負担。
- カウントダウンジョブが reserved 状態のまま `retry_after=14400` 秒経過すると、**DB queue ドライバは "abandoned" 判定で再投入する**（参考: Laravel ドキュメント）。
  → 既に動いているジョブと新ジョブが両方走る可能性。
  → MonitorAuctionJobs の generation 制御が効くので致命傷にはならないが、`Cache::add` の lock を取れた1本だけ進む。
  もう1本は早期 return（無駄なワーカープロセス占有）。

### 対策案

**優先順位1**: 本番 `.env` を **必ず** `QUEUE_CONNECTION=redis` に。`config/queue.php` の `redis` 接続には既に `retry_after=14400` が設定済み。

**優先順位2**: `保守マニュアル.md:32` でも「Cache / Queue: Redis (AWS ElastiCache Valkey 8.0) — 3キュー」と明記されている → 設定はされているはずだが、本番開始前に **必ず**:

```bash
ssh prod "cd /var/www/auction && php artisan tinker --execute='echo config(\"queue.default\");'"
# → 'redis' が返ってくることを確認
```

**優先順位3**: queue ワーカーの監視。
`/var/log/supervisor/queue-countdown.log` に `[2026-04-30 10:00:01] ProcessAuctionCountdownJob STARTED` が auction 1本につき 1回しか出ないことを確認。
2回出たら「世代古ジョブの先送り発生」を確認（generation チェックで止まっているはずだが）。

## 6. 🟠 High-1: countdown:lane キャッシュの TTL 3600s 問題

### 現状

`Cache::put($cacheKey, $state, 3600)` が tick 内で毎回呼ばれる
（[CountdownService.php:88,135,176,197,311](../../../app/Services/CountdownService.php) など）。

### リスク

- 1時間以上ポーズ → cache expire → tick 時に `getCountdownState()` が null
- L233-245 で復旧ロジックがあるので「再 startCountdown」される
- ただし **再 startCountdown は `start_price` 基準で countdown 秒数を再計算する** → 進行中の価格上昇が初期化される

具体例:
```
商品X: start_price=1000, 現在価格=5000 (4回上昇済み)、freezeフェーズ中
→ ポーズ1時間
→ cache expire
→ 再 startCountdown(lane) → bid_countdown_seconds が 5000円基準で再計算
→ phase=bidding になり freeze がスキップされる
```

### 対策

- TTL を 14400s（4時間 = ジョブ timeout と同じ）に統一
- もしくは復旧ロジックで「現在の `current_price` を考慮して再計算」する

修正提案:
```php
// CountdownService.php:88 など
Cache::put($this->getCacheKey($lane->id), $cacheData, 14400); // 1h → 4h に
```

## 7. 🟠 High-2: bid_inflight ロックの待ち行列が見えない

### 現状

[JoinBidAction.php:76-79](../../../app/Actions/Bid/JoinBidAction.php#L76-L79):

```php
$bidLock = Cache::lock("bid_inflight:item:{$item->id}", 5);
if (!$bidLock->get()) {
    return BidResultDto::failure('現在他のユーザーの入札を処理中です。少しお待ちください。');
}
```

`Cache::lock()->get()` は即座に false を返す（`block()` を呼んでないので待たない）。

### リスク

- 100人同時タップ → 99人が即エラー → クライアントがリトライ → エラーループ
- フロントが「処理中エラー時に何回リトライするか」のロジックがない場合、ユーザーが手動で何度もタップする → 「OFF」になっていたかと混乱する

### 対策案

**案A**: フロント側で「`bid_inflight 中`」エラーを 100ms 後に1回だけリトライ。
**案B**: サーバ側で `Cache::lock("...", 5)->block(0.3)` を使い、最大 300ms 待ってから諦める。
**案C**: 100人捌いた後の `freeze` 状態がまもなく来ることを伝える UI（「処理中です。1秒後に再トライ」）。

最も実効性が高いのは **案B**。3〜5秒の bid countdown 中に 300人が並ぶことはほぼなく、
通常は数十ms 以内に lock release されるので、300ms 待てばほぼ全員成功する。

## 8. 🟠 High-3: handleCountdownEnd の DB tx と broadcast の順序

### 現状

[CountdownService.php:705-741](../../../app/Services/CountdownService.php#L705-L741):

```php
DB::beginTransaction();
try {
    if ($activeBidderCount === 0) {
        $item->update(['status' => 'unsold']);
    } elseif ($activeBidderCount === 1) {
        $this->finalizeBidAction->execute($item);  // ← ここで broadcast(ItemSold)
    }
    DB::commit();
} catch (\Exception $e) {
    DB::rollBack();
    throw $e;
}
```

`FinalizeBidAction` は L112-120 で `broadcast(ItemSold)` を **トランザクション外** で行うように設計（コメント記載）。
が、現状の実装では `broadcast` 呼び出しのタイミングを完全には保証していない可能性。

### リスク

- broadcast(ItemSold) が DB::commit() より早いタイミングで送信されると、
  クライアントが「落札確定！」を受け取って GET /api/.../live を叩いた時にまだ DB が unsold のまま → 表示不一致
- broadcast(ItemSold) が DB::commit() のロールバック後に送信されると、
  幻の落札通知。

### 対策

`FinalizeBidAction` のコードを確認した上で:

- broadcast を `DB::afterCommit(...)` で囲む
- または `DB::transaction(function () { ... }); broadcast(...);` の順で完全に外出し

確実なのは Laravel の `ShouldBroadcast` イベントに `afterCommit` を仕込むか、
`DB::afterCommit(fn() => broadcast(...))` パターン。

## 11. 🟠 High-6: 同時 broadcast 例外時の挙動

### 現状

各 broadcast は `try/catch` で例外をログするだけで握りつぶしている:

```php
try {
    broadcast(new CountdownTick(...));
} catch (\Exception $e) {
    Log::warning("Broadcast error lane {$laneId}: " . $e->getMessage());
    $this->metrics->broadcastFailure('CountdownTick', $e->getMessage());
}
```

### リスク

- Reverb が瞬断 → 全 broadcast が失敗 → 0.5秒ごとにログが膨らむ（12レーンなら 24件/秒のWARN）
- ログディスクが溢れて laravel.log が書けなくなる
- ログ書込み失敗で Laravel が例外 → tick チェーン停止（memory: `project_countdown_log_permission_fragility.md`）

### 対策

- broadcast 失敗時のログ出力をレート制限（例: 同種エラーは1分に1回だけ書く）
- ログレベルを debug に下げる（Reverb 障害は CloudWatch メトリクスで検知）
- `MetricRecorder::broadcastFailure` だけ呼んで Log は出さない選択肢もあり

## 22. 「既存ロジックは本当にベストか」の総評

### 良くできている部分

1. **ロック順序プロトコル**（items → bid_participants → bid_events）が一貫しており、デッドロック対策が徹底
2. **freeze cache を commit 前に書く設計**（数 ms ウィンドウ問題への対処）が秀逸
3. **ジョブの世代管理（generation）+ heartbeat 監視** で「再起動すれば直る」状態を担保
4. **tick の例外を catch して active カウントは継続**（部分障害の局所化）
5. **指値の保護ロジック**が「最高指値ユーザー＋created_at 早い者勝ち」で公平性を持つ
6. **freeze cache の TTL=3600s なのに heartbeat=14400s の不一致** はあるが、tick で延長されるので運用上は OK

### 改善の余地

1. **API throttle の欠落** — これだけは即座に直さないと開催当日にトラブルの可能性
2. **broadcast 設計の重複** — CountdownTick で全情報送ってるなら PriceUpdated 廃止検討
3. **自動入札の経路分離** — JoinBidAction バイパスは将来の改修で罠になる
4. **DB queue 前提のジョブ設計** — `tries=1` + heartbeat 監視は良いが、初学者が読み解きにくい。コメントで補足

### ベストとは言えないが「実用上は OK」な部分

- **0.5秒間隔 tick** … リアルタイム性を求めると妥当だが、broadcast 量とトレードオフ
- **MonitorAuctionJobs の毎分実行** … 30秒以内の検知は不可。Lambda or EventBridge の 30秒インターバルなら理想
- **複数コマンドのスケジュール（毎分3本）** … 軽量だが将来コマンド増加時に schedule:run 自体が遅延する可能性

### 設計として「ベスト」に近い水準

総合的に、競争性のあるリアルタイムオークションシステムとして **8/10 くらいの完成度**。
残り2点は本番運用で見えてくるタイプ（負荷試験次第）。

第一回オークション開催前に Critical 4 項目を片付ければ、安心してリリースできる水準と評価。
