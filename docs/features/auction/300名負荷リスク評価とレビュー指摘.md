## 1. 対象シナリオ

「300名が同一オークションに参加し、複数レーンで同時にアグレッシブな入札（連打・短時間 ON/OFF・指値多用）を行う」

### 想定数値

| 項目 | 値 |
|---|---|
| 同時参加者 | 300名 |
| レーン数 | 8〜12 |
| 1レーンあたりの商品数 | 30〜80 |
| 1商品あたりの平均カウントダウン | 3〜5秒 |
| アグレッシブ参加者の入札頻度 | 1〜3秒に1回タップ |
| 想定 broadcast 量（修正後） | 12 レーン × 2 tick/秒 × 接続数。pre_bid/freeze は 1 秒粒度に間引き済み |
| 想定 HTTP 入札量（最悪） | 300人 × 1 req/秒 = 300 req/sec（throttle で 1 ユーザー秒4回に制限済み） |

---

## 2. 🔴 残課題-1（検証）: Reverb の outbound 帯域

### 状態

実装側の対策は完了:
- `tickPreBid` / `tickFreeze` の broadcast を 1 秒粒度に間引き（[CountdownService.php](../../../app/Services/CountdownService.php) `shouldBroadcastLowFrequency`）
- 同種 broadcast 失敗ログを 60 秒に 1 回に抑制（`BroadcastFailureLogger`）

ただし **本番同等構成での実測** がまだ行われていない。

### 確認すべきこと

1. **CPU**: Reverb プロセスが 1 コア律速で詰まらないか
2. **帯域**: ALB / NAT / EC2 NIC の outbound に余裕があるか（300人 × 12 レーン規模）
3. **scaling モード**: `REVERB_SCALING_ENABLED=true` で複数プロセス分散したときの latency 変化

### 推奨アクション

- `load-tests/` 配下のスクリプトで **300 ユーザー × 12 レーン** の負荷試験を本番同等構成で実施
- 試験中の Reverb プロセス CPU、ALB metrics、CloudWatch の `BroadcastFailure` カウンタを記録
- 観測結果を CloudWatch ダッシュボードに固定し、毎オークションで突合

### 万が一帯域が足りなかった場合の追加策（保険）

- `bidding` フェーズの tick を 0.5s → 1s に変更（クライアント側のローカル減算で表示は維持可能）
- `CountdownTick` の payload 削減（`active_bidders_count` を別 event に分離するなど）
- 個別レーン購読チャンネル（`auction.{id}.lane.{laneNumber}`）に分割

## 3. 🟡 Medium-1: bid_events テーブルの肥大化

### 状態

監査用に全入札イベントを記録（join / leave / auto_left / win / lose）。
1 オークション 8 レーン × 60 商品 × 平均 4 段階上昇 × 平均 5 人参加 ≒ **数千〜数万行/回**。

### リスク

- 数年運用で数千万行 → JOIN・検索が遅くなる
- アーカイブ機構が現状ない

### 推奨

- 古いイベントを `bid_events_archive` に移すバッチ
- もしくは MySQL 8 のレンジパーティション（月単位）

---

## 4. 🟡 Medium-2: checkBidLimits / adjustPriceByBidLimits の責務分離

### 状態

`handlePriceIncrement` の最後で `checkBidLimits` と `adjustPriceByBidLimits` の両方を呼んでいる。
処理の重複が一部あり、責務境界が曖昧。

### 推奨

- 設計レビューで一本化（`adjustPriceByBidLimits` の中で `checkBidLimits` 相当の処理を統合 / 反対に完全分離）
- 「指値2人＋手動2人」シナリオの単体テスト追加

---

## 5. 🟡 Medium-3: トランザクションと外部システムの分離（設計規約化）

### 状態

`FinalizeBidAction` の broadcast / 通知は `DB::afterCommit` 化済み（2026-04-30 修正）。
`SetBidLimitAction::activatePendingBidLimits` の broadcast も afterCommit 済み。

ただし、コードベース全体ではまだ「broadcast → DB::commit」の順で書かれている箇所が混在している
可能性がある（ライブ中以外のパス含めて全件監査はできていない）。

### 推奨

- `broadcast(...)` を呼ぶ箇所は **必ず `DB::afterCommit` 経由** にする規約をコードレビューで強制
- PHPStan の custom rule で違反を CI 検知できると理想

---

## 6. 🟡 Medium-4: bid_limit_prices の複合インデックス

### 状態

[bid_limit_prices](../../../database/migrations/2026_02_19_135909_create_bid_limit_prices_table.php) は
UNIQUE (`item_id`, `user_id`) のみ。

`adjustPriceByBidLimits` の検索:

```sql
WHERE item_id = ? AND is_triggered = false AND limit_price > ?
ORDER BY limit_price DESC
```

### 推奨

```sql
ALTER TABLE bid_limit_prices ADD INDEX idx_active_limits (item_id, is_triggered, limit_price);
```

第一回開催時に 100〜200 件規模なら不要。1000 件超えてくる規模で効いてくる。

## 8. 「既存ロジックは本当にベストか」の総評（更新版）

### 良くできている部分（変更なし）

1. **ロック順序プロトコル**（items → bid_participants → bid_events）が一貫しており、デッドロック対策が徹底
2. **freeze cache を commit 前に書く設計**（数 ms ウィンドウ問題への対処）が秀逸
3. **ジョブの世代管理（generation）+ heartbeat 監視** で「再起動すれば直る」状態を担保
4. **tick の例外を catch して active カウントは継続**（部分障害の局所化）
5. **指値の保護ロジック**が「最高指値ユーザー＋created_at 早い者勝ち」で公平性を持つ

### 2026-04-30 修正で追加された強み

6. **API throttle**（入札 4req/sec、指値 2req/sec、お気に入り 60req/min）でボット連打を遮断
7. **bid_inflight ロックの 0.3 秒待機** で 100 名同時タップでも 99 名即エラーの連鎖が消滅
8. **`activatePendingBidLimits` のロック順序準拠** で将来のライブ中自動入札パス追加に耐える設計に
9. **broadcast 失敗ログのレート制限** でログディスク埋め事故を予防（過去の Log 権限事故と組合わさった連鎖障害を遮断）
10. **`auctions:check-config` コマンド** で本番設定ミスを開催前に検知できる

### 残る改善余地

1. **broadcast 設計の重複**（CountdownTick で全情報送ってるなら PriceUpdated 廃止検討）— 影響小
2. **`bid_events` の長期肥大化対策**（Medium-1）
3. **`checkBidLimits` と `adjustPriceByBidLimits` の責務境界**（Medium-2）

### 設計として「ベスト」に近い水準

総合的に、競争性のあるリアルタイムオークションシステムとして **9/10 の完成度**（前回 8/10 → 修正で +1）。
残り 1 点は **本番負荷試験で Reverb 帯域を実測した結果次第**。

## 10. 推奨される追加検証項目

開催前に以下のテストを実施推奨:

1. **300 並列の bid 連打負荷試験** — bid_inflight lock の挙動、php-fpm のスレッド枯渇有無、throttle の挙動
2. **WS の outbound 試験** — 1 秒粒度間引き後の Reverb プロセス CPU・帯域
3. **強制 kill -9 シナリオ** — countdown ワーカーを kill した後 60 秒以内に MonitorAuctionJobs が再起動するか
4. **Redis 瞬断シナリオ** — `redis-cli debug sleep 5` で 5 秒間 Redis を止めた後、tick が復旧するか
5. **DB readonly シナリオ** — RDS フェイルオーバー中の入札挙動（429/5xx で fail-fast するか）
6. **指値合戦 50 段階テスト** — safety counter（10000）の挙動
7. **長時間ポーズ（30 分以上）からの再開** — cache TTL = 14400s 化したので問題ないはず、要確認
8. **同時オークション複数本** — countdown ワーカー 1 プロセスで複数 auction が捌けるか
9. **throttle 限界試験** — `bids` 4req/sec を超えた時の 429 メッセージ、フロント挙動

## 11. 対応履歴

### 2026-04-30: 第一回開催前一斉対応（Critical 4 + High 5 + Medium 2 + Low 4）

| # | 項目 | 対応内容 | 主な変更ファイル |
|---|---|---|---|
| Critical-1 | 入札系 throttle | `RateLimiter::for('bids' / 'bid-limits' / 'favorites' / 'participant-general')` を `AppServiceProvider::boot` に追加。`POST /bids` は秒4回、`POST/DELETE /bid-limits` は秒2回、`favorites/toggle/check` は分60回。 | `app/Providers/AppServiceProvider.php`, `routes/api.php` |
| Critical-2 | broadcast 帯域削減 | `tickPreBid` / `tickFreeze` の broadcast を 0.5s → 1s 粒度に間引き（`shouldBroadcastLowFrequency`）。Reverb outbound を半減。bidding は維持。 | `app/Services/CountdownService.php` |
| Critical-3 | 自動入札のロック順序 | `activatePendingBidLimits` を `DB::transaction(items lockForUpdate → BidParticipant::participate → BidEvent::recordJoin)` で囲い、JoinBidAction と同じ順序プロトコルに準拠。broadcast は `DB::afterCommit` 化。 | `app/Actions/Bid/SetBidLimitAction.php` |
| Critical-4 | 設定検証コマンド | `php artisan auctions:check-config` を新設。`queue.default=redis` / `cache.default=redis` / Redis 疎通 / DB 疎通 / `REVERB_PORT≠8080` を検証。`--strict` で警告も失敗扱い。 | `app/Console/Commands/CheckLiveAuctionConfig.php` |
| High-1 | cache TTL 統一 | `CountdownService::CACHE_TTL = 14400` を新設。全14箇所の `Cache::put(..., 3600)` を `self::CACHE_TTL` に置換。 | `CountdownService.php`, `JoinBidAction.php` |
| High-2 | bid_inflight 待機 | `Cache::lock(...)->get()` → `block(0.3)` に変更。300ms 以内に取れれば成功扱いになり、99 人即エラーの連鎖が解消。 | `app/Actions/Bid/JoinBidAction.php` |
| High-3 | ItemSold afterCommit | `FinalizeBidAction::finalizeAsSold` の `broadcast(ItemSold)` と `NotificationService` 呼出を `DB::afterCommit()` でラップ。ネスト tx commit 前の幻通知を防止。 | `app/Actions/Bid/FinalizeBidAction.php` |
| High-4 | 旧 ProcessCountdownJob | `handle()` を deprecated 警告のみのスタブに置換。test も「呼ばれても何もしない」を確認するものに更新。 | `app/Jobs/ProcessCountdownJob.php`, `tests/Unit/Jobs/ProcessCountdownJobTest.php` |
| ~~High-5~~ | safety counter | 取下げ（実コード確認したところ既に 10000、誤指摘） | — |
| High-6 | broadcast ログ抑制 | `App\Logging\BroadcastFailureLogger` を新設。同種エラーは 60 秒に 1 回だけ Log::warning、メトリクスは毎回送信。CountdownService と JoinBidAction の全 broadcast catch を置換。 | `app/Logging/BroadcastFailureLogger.php`, `CountdownService.php`, `JoinBidAction.php` |
| Medium-2 | active count 重複 | `handlePriceIncrement` 内の `count()` + `get()` を `get()->count()` に統合し、`activated_at desc` の追加クエリも `$allActive->sortByDesc(...)` に置換。 | `CountdownService.php` |
| Low-1 | 構造化ログ | `countdown.job.started/skipped_outdated_generation/skipped_lock_held/completed/re_dispatched`、`auction.start_notification.sent/failed` を構造化形式に。CloudWatch Insights でフィルタ可能に。 | `ProcessAuctionCountdownJob.php`, `MonitorAuctionJobs.php` |
| Low-3 | 開始通知失敗の検知 | 通知失敗時に `MetricRecorder::jobFailure('AuctionStartNotification', ...)` を発火。CloudWatch アラートの対象に。 | `ProcessAuctionCountdownJob.php` |
| Low-4 | pre_bid broadcast 頻度 | Critical-2 と同じヘルパーで実装済（1 秒粒度）。 | `CountdownService.php` |
