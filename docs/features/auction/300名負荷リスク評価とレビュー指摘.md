## 1. 対象シナリオ

「300名が同一オークションに参加し、複数レーンで同時にアグレッシブな入札（連打・指値多用・指値なし商品の競り上げ）を行う」

### 想定数値（v1.1 単方向入札仕様で再算定）

| 項目 | 値 | 備考 |
|---|---|---|
| 同時参加者 | 300名 | 設計目標 |
| レーン数 | 8〜12 | |
| 1レーンあたりの商品数 | 30〜80 | |
| 1商品あたりの平均カウントダウン | 3〜5秒 | 価格帯別 |
| 1ユーザー1商品あたりの平均押下回数 | **1〜2回**（旧仕様 4〜6回） | 単方向化により「ON→OFF→ON」が消えた |
| 想定 HTTP 入札量（最悪） | 300人 × **0.5 req/秒** ≒ 150 req/sec（旧仕様の半分以下） | throttle: 1ユーザー秒4回。実質 1ユーザー数秒に1回 |
| 想定 broadcast 量 | 12 レーン × 2 tick/秒 × 接続数（v1.1で変化なし） | pre_bid/freeze は 1 秒粒度に間引き済み |
| `bid_events` 書き込み量（指値なし商品 1サイクル） | 旧 join+leave+auto_left の3〜N行 → **新 join+auto_left の1〜N行** | OFF 経路廃止で leave が消える |
| `bid_events` 書き込み量（指値あり商品 1サイクル） | **join 1行 + ignored M行**（M = 滑り込みタップ数） | NEW: ignored が新発生 |

## 2. 単方向入札仕様（v1.1）による負荷特性の変化

### 2.1 削減された負荷

| 項目 | 旧仕様（v1.0） | 新仕様（v1.1） | 効果 |
|---|---|---|---|
| `POST /api/participant/bids` 回数 | 1人1商品で 4〜6回（ON→OFF→ON…） | **1〜2回**（ON のみ） | **約 1/3 〜 1/4 に削減** |
| `bid_events.leave`（ユーザー操作起因） | 入札サイクルの 1〜2 割 | **0**（ユーザーからの leave 消失） | 監査ログ削減 |
| `BidderUpdated::left`（broadcast） | ユーザー操作起因の発生あり | **0**（自動離脱以外なし） | broadcast 量微減 |
| `LeaveBidAction` 経由の DB tx | 多発 | システム経路（指値到達のみ） | DB 書き込み削減 |

### 2.2 増加する／新規の負荷

| 項目 | 内容 | リスク |
|---|---|---|
| **指値あり商品の1人目発動** | 押下→即 `handleImmediatePriceIncrement` 発火 | 価格上昇イベントが旧仕様より早期に頻発する可能性。`PriceUpdated` broadcast が増える |
| **`bid_events.TYPE_IGNORED`**（NEW） | 既存権利者ありの間に滑り込んだ全押下が記録される | 指値あり商品で滑り込みが多発する場合、ignored ログが累積（§4） |
| **滑り込みガードの追加クエリ**（NEW） | JoinBidAction 内で `BidLimitPrice::exists()` ＋ `forItem()->active()->count()` を毎回実行 | 軽量だがホットパスなので index 確認必要（§5） |

### 2.3 ネット効果

入札ホットパスの DB 書き込み件数（300人 × 60商品 × 1サイクル換算）:

```
旧仕様: 300人 × ~5回/商品 × 60商品 = 90,000 行/オークション (bid_events)
新仕様: 300人 × ~1.5回/商品 × 60商品 = 27,000 行/オークション (bid_events)
       内訳:
         - join         …  18,000 行（押下成功分）
         - ignored      …   ~5,000 行（指値あり商品の滑り込み分）
         - auto_left    …   ~4,000 行（システム経由）
```

**結論**: 新仕様は全体として DB 書き込み 1/3、broadcast 微減、API 量 1/3 の方向。
ただし **`PriceUpdated` 発生頻度** と **`TYPE_IGNORED` ログ累積** という新しい増加要因があるため、ベンチで実測すること。

## 3. 🔴 残課題-1（検証）: Reverb の outbound 帯域

### 状態

実装側の対策は完了:
- `tickPreBid` / `tickFreeze` の broadcast を 1 秒粒度に間引き（[CountdownService.php](../../../app/Services/CountdownService.php) `shouldBroadcastLowFrequency`）
- 同種 broadcast 失敗ログを 60 秒に 1 回に抑制（`BroadcastFailureLogger`）
- v1.1 単方向入札化により `BidderUpdated::left`（ユーザー操作起因）と `bid_events.leave` が消失。broadcast 微減方向

ただし **本番同等構成での実測** がまだ行われていない。
v1.1 で `PriceUpdated` の発生頻度が **増える可能性**（指値あり商品で1人目発動 → サイクル短縮）に注意。

### 確認すべきこと

1. **CPU**: Reverb プロセスが 1 コア律速で詰まらないか
2. **帯域**: ALB / NAT / EC2 NIC の outbound に余裕があるか（300人 × 12 レーン規模）
3. **scaling モード**: `REVERB_SCALING_ENABLED=true` で複数プロセス分散したときの latency 変化
4. **`PriceUpdated` 頻度**: v1.1 指値あり商品で実測（1人目発動が連鎖的に走る場合の上限）

### 推奨アクション

- `load-tests/` 配下のスクリプトで **300 ユーザー × 12 レーン** を本番同等構成で実施
- シナリオに「指値あり商品が混在するレーン」を必ず含める
- 試験中の Reverb プロセス CPU、ALB metrics、CloudWatch の `BroadcastFailure` カウンタを記録
- 観測結果を CloudWatch ダッシュボードに固定し、毎オークションで突合

### 万が一帯域が足りなかった場合の追加策（保険）

- `bidding` フェーズの tick を 0.5s → 1s に変更（クライアント側のローカル減算で表示は維持可能）
- `CountdownTick` の payload 削減（`active_bidders_count` を別 event に分離するなど）
- 個別レーン購読チャンネル（`auction.{id}.lane.{laneNumber}`）に分割

## 4. 🟡 Medium-NEW-1: `bid_events.TYPE_IGNORED` の肥大化

### 状態（v1.1 NEW）

[JoinBidAction §1.2-5c](./ライブオークション技術仕様書.md) の existing-active-winner ガードで、滑り込んだ押下を `BidEvent::recordIgnored` で監査記録するようにした。

指値あり商品で1サイクル中に 100 人が押した場合、**最初の1人 = join、残り 99 人 = ignored** が原則。
ただしフロント側でも該当画面では権利者表示中はボタン disabled なので、実際にサーバまで届く滑り込みはミリ秒単位の競合分のみ。

### リスク

- 1オークションあたり数千 〜 数万行 の `ignored` 行が `bid_events` に蓄積
- 数年運用で数億行レベルまで肥大化する可能性
- 監査用途では `join` / `auto_left` / `win` / `lose` ほどの頻度では参照しない

### 推奨

1. **短期**: そのまま記録（不正検知用）
2. **中期**: `bid_events_archive` への自動移送バッチに `TYPE_IGNORED` を最優先で含める
3. **長期**: `TYPE_IGNORED` だけ別テーブル（`bid_events_ignored`）に切り出し、`bid_events` のホットパスを軽くする

### 観測方法

```sql
-- 1オークションあたりの ignored 件数を確認
SELECT i.auction_id, COUNT(*) as ignored_count
FROM bid_events be
JOIN items i ON i.id = be.item_id
WHERE be.event_type = 'ignored'
GROUP BY i.auction_id
ORDER BY ignored_count DESC;
```

開催ごとにこのクエリを回し、想定（5,000 行 / オークション）から大きく外れたら設計を見直す。

## 5. 🟡 Medium-NEW-2: 滑り込みガードのクエリコスト

### 状態（v1.1 NEW）

JoinBidAction のトランザクション内で:

```sql
-- A: 指値ありか判定
SELECT EXISTS(
  SELECT 1 FROM bid_limit_prices
  WHERE item_id = ? AND is_triggered = false
);

-- B: 既存活発参加者がいるか判定
SELECT COUNT(*) FROM bid_participants
WHERE item_id = ? AND user_id != ? AND is_active = true;
```

を **入札 1 回ごとに発行** する（行ロック取得後）。

### リスク

- 入札回数 × 2 クエリ = ホットパスのクエリ数増
- インデックスが効いていれば各 < 1ms だが、index miss すると O(N) スキャンに

### 確認すべきインデックス

| テーブル | 既存 INDEX | クエリの効率 |
|---|---|---|
| `bid_limit_prices` | UNIQUE (`item_id`, `user_id`) | A は `item_id` 先頭で部分一致 → 効くがフィルタ列の位置に注意 |
| `bid_participants` | `(item_id, is_active)` 既存 §2.2 | B は良好 |

### 推奨

`bid_limit_prices` に `(item_id, is_triggered)` の複合 INDEX を追加すると A が完全に B-tree シーク化できる。
（既存の Medium-4 と統合した複合 `(item_id, is_triggered, limit_price)` でも OK）

### 観測方法

```sql
EXPLAIN SELECT EXISTS(SELECT 1 FROM bid_limit_prices WHERE item_id = 1 AND is_triggered = false);
-- type=ref / key=PRIMARY が出ていれば OK。filtered=100 表示なら追加 INDEX 検討
```

## 11. 既存ロジックの良い設計（v1.1 後の評価）

### 引き続き良くできている部分

1. **ロック順序プロトコル**（items → bid_participants → bid_events）が一貫しており、デッドロック対策が徹底
2. **freeze cache を commit 前に書く設計**（数 ms ウィンドウ問題への対処）が秀逸
3. **ジョブの世代管理（generation）+ heartbeat 監視** で「再起動すれば直る」状態を担保
4. **tick の例外を catch して active カウントは継続**（部分障害の局所化）
5. **指値の保護ロジック**が「最高指値ユーザー＋created_at 早い者勝ち」で公平性を持つ
6. **API throttle**（入札 4req/sec 等）でボット連打を遮断
7. **bid_inflight ロックの 0.3 秒待機** で 100 名同時タップでも 99 名即エラーの連鎖が消滅
8. **broadcast 失敗ログのレート制限** でログディスク埋め事故を予防
9. **`auctions:check-config` コマンド** で本番設定ミスを開催前に検知できる

### v1.1 で追加された強み

10. **入札ボタンの単方向化** により誤離脱事故（落札権利者が誤って降りる）を **構造的に不可能** にした。フロント disable + サーバー 403 の二重防御
11. **指値あり商品の1人目発動** により、競り上がりの開始が早くなり、ユーザー体感の応答性が向上
12. **滑り込み無視ガード** により、freeze cache 反映前のミリ秒競合（数ms ウィンドウ問題）に対する防御層が増えた
13. **`BidEvent::TYPE_IGNORED`** で滑り込みが監査可能になった（不正解析の手がかりが残る）
14. **`LeaveBidAction` のガード削除** により、唯一の active 参加者が指値到達時に正しく離脱できるようになった（旧仕様の潜在バグ修正）

### 残る改善余地

1. **broadcast 設計の重複**（CountdownTick で全情報送ってるなら PriceUpdated 廃止検討）— 影響小
2. **`bid_events` の長期肥大化対策**（§6, §4）
3. **`checkBidLimits` と `adjustPriceByBidLimits` の責務境界**（§7）

### 設計として「ベスト」に近い水準

総合的に、競争性のあるリアルタイムオークションシステムとして **9.5/10 の完成度**（v1.0 の 9/10 → v1.1 で +0.5）。
残り 0.5 点は **本番負荷試験で Reverb 帯域を実測した結果次第**。

## 13. 推奨される追加検証項目

4. **WS の outbound 試験** — 1 秒粒度間引き後の Reverb プロセス CPU・帯域。v1.1 で `PriceUpdated` 頻度が増える可能性に注意
5. **強制 kill -9 シナリオ** — countdown ワーカーを kill した後 60 秒以内に MonitorAuctionJobs が再起動するか
6. **Redis 瞬断シナリオ** — `redis-cli debug sleep 5` で 5 秒間 Redis を止めた後、tick が復旧するか
7. **DB readonly シナリオ** — RDS フェイルオーバー中の入札挙動（429/5xx で fail-fast するか）
8. **指値合戦 50 段階テスト** — safety counter（10000）の挙動
9. **長時間ポーズ（30 分以上）からの再開** — cache TTL = 14400s 化したので問題ないはず、要確認
10. **同時オークション複数本** — countdown ワーカー 1 プロセスで複数 auction が捌けるか
11. **throttle 限界試験** — `bids` 4req/sec を超えた時の 429 メッセージ、フロント挙動
12. **誤離脱の構造的不可能性確認**（v1.1 NEW）— `is_active=true` 中の参加者が `POST /api/participant/bids` に `is_active=false` を送っても 403 が返り、`bid_participants.is_active` が変わらないこと
