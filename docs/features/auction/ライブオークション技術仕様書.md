### 1.2 1リクエストの処理経路（入札ON / 単方向入札仕様）

> v1.1 で `is_active=false`（離脱）リクエストは Controller 層で 403 拒否される。下記は ON 経路のみ。

```
[端末] tap "入札する"
   │
   ▼ POST /api/participant/bids  (auth:sanctum, check.subscription:bid)
[BidController::toggle]   src/app/Http/Controllers/Participant/BidController.php:27
   │
   ├─ is_active=false なら即 403（"入札の取り消しはできません"）
   │
   ▼ DI 注入された JoinBidAction
[JoinBidAction::execute]  src/app/Actions/Bid/JoinBidAction.php
   │
   ├─ 1. item.status / auction.status 確認
   ├─ 2. countdown:lane:{id} cache から phase 判定 (pre_bid/freeze なら拒否)
   ├─ 3. bid_limit_prices で自分の上限価格チェック
   ├─ 4. Cache::lock("bid_inflight:item:{id}", 5)  ← ★ 応用層直列化
   ├─ 5. DB::transaction:
   │       a. items 行ロック → phase 再判定 → 価格再検証
   │       b. 自分が既に active なら冪等成功で早期 return（participate せず recordJoin もしない）
   │       c. is_triggered=false の指値があり、自分以外に active 参加者がいれば
   │          recordIgnored して fail（"既に他のユーザーが落札権利者です"）
   │       d. 通常 participate / recordJoin / activeCount = SELECT COUNT(*)
   │       e. has_active_limits フラグを返却
   ├─ 6. 冪等成功なら broadcast / 価格上昇トリガー全スキップ → 現状状態を返す
   ├─ 7. countdown cache に last_bidder_user_id 書き込み
   ├─ 8. broadcast(BidderUpdated::joined)  ← Reverb へ
   ├─ 9. 発動閾値判定:
   │       - has_active_limits=true（指値あり）→ activeCount >= 1 で発動
   │       - has_active_limits=false（指値なし）→ activeCount >= 2 で発動
   │       閾値到達なら handleImmediatePriceIncrement
   └─ 10. finally: Redis lock release
```

## 2. データモデル

### 2.1 主要テーブル

| テーブル | 役割 | 重要カラム |
|---|---|---|
| `auctions` | オークション本体 | `status` (draft/scheduled/preparing/live/finished/cancelled), `event_date`, `lane_count`, `auction_settings`(JSON) |
| `lanes` | 同時並行レーン | `lane_number`, `current_item_id`, `status` (waiting/active/paused/finished) |
| `items` | 出品商品 | `auction_id`, `lane_id`(任意), `status` (draft/registered/live/sold/unsold/cancelled), `start_price`, `current_price`, `bid_increment` |
| `lane_items` | レーンと商品の紐付け（中間） | `lane_id`, `item_id`, `sequence_order` |
| `bid_participants` | 入札ON/OFF状態 | UNIQUE(`item_id`,`user_id`), `is_active`, `activated_at`, `deactivated_at` |
| `bid_events` | 入札・離脱・自動離脱の履歴（監査用） | `item_id`, `user_id`, `event_type` (`join`/`leave`/`auto_left`), `price`, `created_at` |
| `bid_limit_prices` | 指値（上限価格） | UNIQUE(`item_id`,`user_id`), `limit_price`, `is_triggered`, `triggered_at` |
| `price_events` | 価格変動の履歴 | `item_id`, `old_price`, `new_price`, `event_type` |
| `won_items` | 落札確定 | `item_id`, `user_id`, `final_price`, `won_at` |
| `favorites` | お気に入り | UNIQUE(`user_id`,`item_id`) |

### 2.2 重要インデックス

- `items` : `(auction_id, status, item_number)` … ライブ中商品リスト取得
- `bid_participants` : `(item_id, is_active)` … active カウント高速化
- `bid_limit_prices` : UNIQUE `(item_id, user_id)` … 指値再設定の上書き

### 2.3 ロック順序プロトコル（厳守）

入札・価格上昇・指値発動など `bid_participants` / `bid_events` を触るトランザクションは
必ず **`items` 行ロック → `bid_participants` → `bid_events` の順** で取得する。
逆順をやると FK ロック競合でデッドロックする（過去事故あり）。
詳細は memory: `project_bid_lock_order.md`。

```
                              │
auctions.status:               │
draft ──▶ scheduled ──[start命令]──▶ preparing ──[10秒pre-start]──▶ live ──[finish]──▶ finished
                                                                   │

```

### 3.2 フロアスタート（管理者操作）

**エントリポイント**: `POST /api/admin/auctions/{id}/start`
**コード**: [LiveController::start](../../../app/Http/Controllers/Admin/LiveController.php) (L233-309)

```
1. items を auction にラウンドロビン割当（プレミアム優先）
2. lanes を必要数作成（lane_count から）
3. auctions.status = 'live' / lanes.status = 'active' に更新
4. cache: auction:{id}:start_at = now+10秒、auction:{id}:lanes_to_start = [laneIds]
5. broadcast(AuctionStatusChanged('starting', countdown=10))
6. ProcessAuctionCountdownJob::dispatch($auctionId)  ← queue:countdown へ
```

### 3.3 ProcessAuctionCountdownJob のメインループ

**ファイル**: [ProcessAuctionCountdownJob.php](../../../app/Jobs/ProcessAuctionCountdownJob.php)

| パラメータ | 値 | 意味 |
|---|---|---|
| `$tries` | 1 | 失敗時に再キューしない（generation で別途復旧） |
| `$timeout` | 14400 (4時間) | ジョブ最大実行時間 |
| `TICK_INTERVAL` | 0.5秒 | tick の間隔 |
| `HEARTBEAT_TTL` | 14400秒 | heartbeat キャッシュTTL |
| `maxIterations` | 28800 (4h ÷ 0.5s) | tick 上限 |
| キュー | `countdown` | 専用ワーカー1本で逐次処理 |

**フロー**:
1. **世代チェック**（L87-90）: dispatch 後に generation が進んでいたら即終了
2. **排他ロック**（L92-100）: `countdown_job_lock:auction:{id}` を `Cache::add` で取得（既存PIDがあれば skip）
3. **10秒プレスタート**（L114-189）: `start_at` cache を見て毎秒 `AuctionStatusChanged('starting')` を broadcast → 0秒で各レーンの `startCountdown()` 呼び出し → `AuctionStatusChanged('live')` broadcast → 開始通知メール/LINE
4. **メインループ**（L196-317）: 0.5秒ごと
   - 世代チェック → 古ければ break
   - auction 状態確認（live でなければ break）
   - 全 lane を foreach
     - paused → スキップカウント
     - active → `getCountdownState()` → なければ復旧で再 `startCountdown()` → `tick(laneId)`
   - active=0 かつ paused=0 なら break
   - 10 tick (5秒) ごとに heartbeat 更新
5. **終了処理**（L319-331）: 自世代なら `countdown_job_finished:auction:{id}` を120秒セット、各種 cache を forget

### 3.4 CountdownService::tick の Phase 遷移

**ファイル**: [CountdownService.php](../../../app/Services/CountdownService.php)

```
[新商品 active]
    ▼ startCountdown(lane)  L56
phase=bidding, remaining=bid_countdown_seconds
    │
    │ ※ pre_bid をスキップする経路（startCountdown 直行）。
    │   通常は moveToNextItem→startPreBidCountdown 経由で pre_bid から入る
    │
    ▼ tick (-0.5s) L225
[remaining > 0] → broadcast(CountdownTick)
[remaining = 0] →
   activeCount >= 2 → handlePriceIncrement L431
                          ├─ items lockForUpdate
                          ├─ price 再検証（並行呼出冪等化）
                          ├─ activeCount 再カウント
                          ├─ current_price += increment, PriceEvent 記録
                          ├─ 指値保護ロジック（後述）で他者を deactivate
                          ├─ startFreezeCountdown（commit前にcache書き込み）
                          ├─ commit
                          ├─ broadcast(PriceUpdated)
                          ├─ broadcast(BidderUpdated::left) ※自動離脱発生時
                          ├─ checkBidLimits（指値発動チェック）
                          └─ remainingLimits>=2 なら adjustPriceByBidLimits

   activeCount <= 1 → handleCountdownEnd L705
                          ├─ stopCountdown（cache forget）
                          ├─ DB::tx [activeCount=0 ? unsold : finalize(sold)]
                          ├─ moveToNextItem（tx外でcache書き込み）
                          │     ├─ 次item を live に
                          │     ├─ lane.current_item_id 更新
                          │     ├─ startPreBidCountdown（phase=pre_bid）
                          │     ├─ activatePendingBidLimits（自動入札）
                          │     └─ activated>=2 なら adjustPriceByBidLimits
                          └─ broadcast(LaneItemChanged)

[freeze phase の tick] L374
   - remaining -= 0.5
   - broadcast(CountdownTick phase=freeze)
   - remaining<=0 → phase=bidding に戻して broadcast(CountdownTick phase=bidding)

[pre_bid phase の tick] L319
   - 同上 → 0秒で phase=bidding に遷移
```

### 3.5 価格上昇の発動条件と指値保護ロジック

#### 3.5.1 発動条件（v1.1 単方向入札仕様）

価格上昇＋フリーズの発動 active 数しきい値は商品ごとに動的に決まる。

| 商品の状態 | しきい値 | 効果 |
|---|---|---|
| `is_triggered=false` の指値が **1件以上** ある商品（指値あり） | `activeCount >= 1` | 1人目押下で発動。押下者が落札権利者として確定。後続の滑り込みは JoinBidAction §1.2-5c で `bid_events.event_type='ignored'` 記録のみして拒否 |
| 指値レコードゼロの商品（指値なし） | `activeCount >= 2` | 従来動作。1人だけ参加なら開始価格で `handleCountdownEnd` 経由の落札成立 |

**判定箇所**:
- [JoinBidAction.php](../../../app/Actions/Bid/JoinBidAction.php) — Join 直後の即時発動分岐
- [CountdownService::handleImmediatePriceIncrement](../../../app/Services/CountdownService.php) — 直接呼び出された場合の保険判定
- `handlePriceIncrement` 本体は引数 `$minActiveBidders`（既定 2）でしきい値を受け取り、ロック後再検証時の `freshActiveCount < $minActiveBidders` ガードに反映

**tick 0秒到達経由（指値関係なく従来どおり 2人以上）**:
[CountdownService::tick L308-318](../../../app/Services/CountdownService.php) は `activeCount >= 2 → handlePriceIncrement / activeCount <= 1 → handleCountdownEnd` のまま。`tick` 経路では明示的に `$minActiveBidders=2`（既定値）で呼ばれる。

#### 3.5.2 落札権利者（effectiveHolder）の決定

```
価格上昇後 (newPrice 確定後):
  1. 全 active 入札者を取得（行ロック中）
  2. 有効な指値（is_triggered=false, limit_price>newPrice）を limit_price DESC, created_at ASC で取得
  3. 指値ホルダー = protectedUserIds とする
  4. 各 active 入札者をループ:
     - protectedUserIds に含まれる → 残す
     - 指値ホルダーがいない & lastBidder と一致 → 残す（1回限定）
     - それ以外 → deactivate（自動離脱）
  5. 落札権利者(effectiveHolder) = protected あれば最高指値ユーザー、なければ lastBidder
```

**1人発動ケース（指値あり商品）の振る舞い**:
- 押下者本人だけが active → ループ対象は1人
- その人が指値ホルダーであれば protectedUserIds で保護される
- 指値ホルダーが「他の人」（事前指値登録者）の場合は、押下者は auto-left され、effectiveHolder は指値登録者になる
  - これは「指値による自動入札」のセマンティクス上の正解（指値ユーザーは押されたら自動で価格を引き上げる権利を持つ）
  - 直後の `adjustPriceByBidLimits` で指値発動が連鎖し、最終的に正しい落札権利者へ収束

**重要**: freeze cache の書き込みは **DB::commit() より前**（[handlePriceIncrement の `startFreezeCountdown` 呼び出し](../../../app/Services/CountdownService.php)）。理由は同ファイルコメント参照（行ロック解放とキャッシュ反映の間の数 ms ウィンドウで誤入札を許さない）。
v1.1 ではこの数 ms ウィンドウで滑り込んだ誤入札を、JoinBidAction 側でも `existing-active-winner` ガードによって二重に弾く（保険）。

## 5. WebSocket（Reverb）イベント

### 5.1 接続情報

| 項目 | 値 |
|---|---|
| ドライバ | Reverb |
| サーバ | `0.0.0.0:6001`（`config/reverb.php`） |
| クライアント | Pusher プロトコル互換（Laravel Echo） |
| プロセス管理 | Supervisor（`/etc/supervisor/conf.d/reverb.conf`） |

> **❗ 注意（memory: project_reverb_port_pitfall.md）**
> nginx の port 8080 は WebSocket **専用 proxy**。
> `BROADCAST_HOST` を 8080 に向けるとサーバ→Reverb 接続が Connection reset し、
> 全件 unsold 化する事故が過去発生。`.env` は **6001 を直接** 指定する。

### 5.2 全イベント定義

すべて `auction.{auctionId}.live` チャンネルへ broadcast。

| クラス | broadcastAs | データ | 発火タイミング |
|---|---|---|---|
| `AuctionStatusChanged` | `auction.status` | status, message, countdown_seconds | スタート / pre-start カウント / 終了 |
| `CountdownTick` | `countdown.tick` | lane_id, item_id, remaining, active_count, price, phase | **0.5秒ごと（高頻度）** |
| `BidderUpdated` | `bidder.updated` | item_id, lane_id, active_count, event_type(`joined`/`left`) | 入札ON/OFF / 自動離脱 |
| `PriceUpdated` | `price.updated` | price, active_count, bid_seconds, auto_left_user_ids | 価格上昇時 |
| `LaneItemChanged` | `lane.changed` | lane_id, previous_item, current_item | 商品切替 |
| `ItemSold` | `item.sold` | item_id, winner_id, final_price | 成約確定 |
| `BidLimitReached` | `bid.limit.reached` | item_id, user_id, current_price, limit_price | 指値発動 |

### 5.3 0.5秒間隔 broadcast の負荷見積り

- N レーンのオークション → CountdownTick が `2 × N` 回/秒
- 12 レーンなら 24 イベント/秒、各イベントは数百 byte
- 接続クライアント数 × 24 = Reverb の outbound 帯域
- 300名 × 24msg/s ≈ 7,200 msg/s（数MB/sのオーダー）→ ALB / Reverb スケーリング検討必要

詳細はリスク評価ドキュメント §3。

|---|---|---|
| `countdown:lane:{laneId}` | 14400s (`CountdownService::CACHE_TTL`) | レーンのカウントダウン状態 (phase, remaining, last_bidder_user_id 等) |
| `countdown_job_generation:auction:{id}` | 14400s | ジョブの世代番号（再 dispatch 時に +1） |
| `countdown_job_running:auction:{id}` | timeout+600s | 実行中フラグ |
| `countdown_job_lock:auction:{id}` | timeout+60s | PID 入りの排他ロック（`Cache::add`） |
| `countdown_job_heartbeat:auction:{id}` | 14400s | 最終 tick の Unix ts（5秒ごと更新） |
| `countdown_job_finished:auction:{id}` | 120s | 正常終了マーカー（Monitor が再 dispatch しないように） |
| `auction:{id}:start_at` | プレスタート期間 | プレスタートのターゲット時刻 |

### 6.4 retry_after について

`config/queue.php` で `retry_after = 14400` 秒（4時間）。
**理由**: countdown ジョブは最長 4 時間動く想定。デフォルト 90 秒だと「処理中だがまだ ack していない」と判定され、二重実行される。

ただしこれは **MonitorAuctionJobs（heartbeat 監視）** と独立した安全機構。
heartbeat が30秒以上途絶 → MonitorAuctionJobs が generation+1 して再 dispatch → 古いジョブは次の tick で `isCurrentGeneration()=false` を検出して自発終了。

### 7.1 MonitorAuctionJobs（重要）

**ファイル**: [MonitorAuctionJobs.php](../../../app/Console/Commands/MonitorAuctionJobs.php)

ライブ中の auction を全件取得し、各 auction について:

1. `countdown_job_finished:auction:{id}` キャッシュがあれば skip（直前に正常終了したジョブ）
2. `countdown_job_heartbeat:auction:{id}` を取得 → `now - heartbeat < 30s` なら生存中とみなして skip
3. それ以外（heartbeat なし or 30秒超過）+ active/paused lane が存在 → 死亡判定:
   - 全 cache を forget
   - generation を +1
   - `ProcessAuctionCountdownJob::dispatch($auctionId)` で新ジョブを起動

**`HEARTBEAT_STALE_SECONDS = 30`** （L23）: 30秒間 heartbeat が来なかったら死亡判定。

> **❗ ハートビートTTLとMonitor閾値の関係**
> heartbeat TTL = 14400 秒（4時間）。30秒で stale 判定するので、TTL 切れより前に Monitor が動く。
> 監視周期は毎分なので、最悪 60s 以内に検知 → 復旧 dispatch。

## 8. フロー詳細：典型シナリオ

### 8.1 「100名が同一商品にアグレッシブ入札」のミリ秒挙動（v1.1 単方向入札仕様）

前提: 商品X、開始価格1000円、現在 active=0、phase=bidding

#### 8.1.1 指値あり商品（is_triggered=false の BidLimitPrice が1件以上）

```
T+000ms  100人が一斉に POST /bids
T+010ms  最初の1人 (User A) が Cache::lock 取得成功、残り99人は失敗 → 即時 fail
T+020ms  User A: items.lockForUpdate → phase=bidding / 価格1000円 OK
T+030ms  User A: existing-active-winner ガード通過（自分以外の active なし）
T+040ms  User A: participate → recordJoin → activeCount=1
T+050ms  User A: 指値あり閾値=1 達成 → handleImmediatePriceIncrement 発動
T+050ms  User A: handlePriceIncrement(min=1):
            - 価格 1000→1100、PriceEvent 記録
            - 指値ホルダー判定（A自身が指値者ならprotect、他者なら effectiveHolder=他者で
              A は auto-left）
            - startFreezeCountdown（commit前にcache phase='freeze' 書き込み）
            - DB commit → broadcast(PriceUpdated)
T+080ms  User A: bid_inflight lock release → success レスポンス

T+100ms  失敗した99人がリトライ
         → freeze cache が既に書かれているので JoinBidAction §1.2-2 で全員 fail
            （"誤タップ防止中です。もう少々お待ちください。"）
T+050ms+freezeS  freeze 終了、phase='bidding' に戻る → 次の押下者が新たに 1人目発動
                  → 価格 1100→1200、フリーズ、新権利者…の繰り返し
```

**性能特性**:
- 1サイクルあたり「先着 1 名のみ DB tx を貫通」「残り全員はロック or freeze で短絡」
- DB write は1サイクルにつき items=1 / bid_participants=1 / bid_events=1 / price_events=1
- 旧仕様（2人発動＋auto-left）と比較し、2人目の participate / recordJoin / 後続の deactivate（auto-left）の DB write 3〜N行が **完全に消える**

#### 8.1.2 指値なし商品（BidLimitPrice ゼロ）

```
T+000ms  100人が一斉に POST /bids
T+010ms  User A が lock 取得成功、99人は fail
T+040ms  User A: participate → activeCount=1、閾値=2 未満なので価格上昇しない
T+080ms  User A: success
T+100ms+ 99人がリトライ → 次に lock を取った User B が participate → activeCount=2
         → 閾値=2 達成 → handleImmediatePriceIncrement(min=2)
         → 指値なしなので effectiveHolder = lastBidder = User B（2人目）
         → User A を auto-left
         → 価格 1000→1100、フリーズ、broadcast(PriceUpdated, auto_left=[A])
T+freezeS+ phase='bidding' 復帰 → 通常カウントダウン継続
```

**この挙動は意図された設計**:
- 指値なし商品では「最初の1人で price up しない」ことで開始価格落札の余地を残す
- Redis lock のおかげで 100 リクエストが items 行ロックの DB キューに並ばない
- 単方向化により「ON→OFF→ON」の意思チェーンが消え、bid_events 件数が減る

### 8.2 freeze タイミングの詳細

**目的**: 価格上昇直後の「見間違い & 連打」誤入札を防ぐ。

```
T=0     phase=bidding, remaining=2.0s
T=2.0   tick → remaining=0.0 → activeCount=2 で handlePriceIncrement
        ├─ DB tx: items行ロック → 価格上昇 → bid_participants 整理
        ├─ startFreezeCountdown ← cache に phase='freeze' を ★commit前★ に書く
        ├─ DB commit
        └─ broadcast(PriceUpdated)
T=2.0+  tick で phase='freeze', remaining=2.0s（freeze_countdown_seconds）
T=2.5   tick (-0.5) → broadcast(CountdownTick phase=freeze, 1.5s)
T=3.0   tick (-0.5) → broadcast(CountdownTick phase=freeze, 1.0s)
T=3.5   tick (-0.5) → broadcast(CountdownTick phase=freeze, 0.5s)
T=4.0   tick (-0.5) → remaining=0 → phase=bidding に戻す → broadcast(initial bidding tick)
T=4.0+  通常の bidding カウントダウン
```

**フロントエンド側の挙動**:
- `phase=freeze` の間は入札ボタンを `disabled` にする
- API 側でも JoinBidAction L51-56 で freeze 中の入札は弾く（二重防御）

### 8.3 ❗ pre_bid フェーズ中の自動入札（指値）バイパス

**現状の問題的挙動** ([ProcessAuctionCountdownJob.php:151-161](../../../app/Jobs/ProcessAuctionCountdownJob.php#L151-L161))

最初の商品にも事前指値の自動入札を適用するため、`activatePendingBidLimits` が
`SetBidLimitAction` 経由で **JoinBidAction を経由せずに** `BidParticipant::participate()` を直接呼ぶ。

→ pre_bid phase 中の bid 拒否ロジックを通らない（自動入札なので OK だが、設計として別経路）。
→ `bid_inflight:item` lock も取らない。
→ これ自体は意図された設計（pre_bid 中に指値だけ事前 active 化したい）だが、
  以下の場合は注意:
  - 同じ瞬間にユーザーが手動 ON タップ → JoinBidAction が pre_bid で拒否される（OK）
  - adjustPriceByBidLimits が走るのは pre_bid 終了後ではなく activate 直後 → tick が pre_bid を消化中に price が上がる挙動になる

リスク評価ドキュメント §4 で再掲。

## 11. 既知の挙動と仕様メモ

### 11.1 throttle 設定済み

`AppServiceProvider::boot` で `RateLimiter::for('bids' / 'bid-limits' / 'favorites' / 'participant-general')`
を定義し、`api.php` 側で `throttle:<name>` を書込み系に付与済み。詳細は §4.3。

### 11.2 cache TTL = 14400s（4時間）

`countdown:lane:{id}` の cache は **4 時間** で expire する設計（`CountdownService::CACHE_TTL`）。
ジョブの heartbeat TTL と一致させているので、長時間ポーズ中に cache だけ消えて
freeze スキップ等の整合崩れが起きないようにしている。
正常稼働中は tick 時に毎回 `Cache::put(..., self::CACHE_TTL)` で延長される。

### 11.3 retry_after ≠ tries=1

`ProcessAuctionCountdownJob::tries = 1` なので失敗してもキュー再投入はない。
heartbeat 監視 + generation で復旧する独自プロトコル。

### 11.4 BidParticipant の物理一意性

`UNIQUE(item_id, user_id)` なので、`BidParticipant::participate()` は upsert 実装。
履歴は `bid_events` 側に追記される。

v1.1 単方向入札仕様により **ユーザー操作からの OFF 動線は撤廃** された。
`is_active=true → false` の遷移はシステム経由（`handlePriceIncrement` / 指値到達時の `LeaveBidAction`）のみ。
`is_active=false → true` の遷移は次の価格枠以降のユーザー押下で発生する（同じ row を再度 active 化）。

### 11.5 finalize（成約確定）の経路

成約確定は **`handleCountdownEnd` 内のみ**。
`activeCount == 1` で `FinalizeBidAction` が走り、
`won_items` に レコード作成 → `items.status='sold'` → ItemSold broadcast。
管理者が `LiveController::nextItem` で強制 next すると、
内部で `MoveToNextItemAction` が同等処理を呼ぶ。

### 11.6 単方向入札仕様（v1.1 / 2026-05-01）

| 観点 | 仕様 |
|---|---|
| 入札ボタン | **ON 一方向**。OFF / 離脱動線は廃止 |
| 価格上昇トリガー（指値あり） | **1人目押下で即発動**＋押下者が落札権利者として確定（指値ホルダーがいれば指値ホルダー優先） |
| 価格上昇トリガー（指値なし） | 2人目押下で発動（従来動作）＋ 2人目（lastBidder）が落札権利者 |
| 滑り込み入札 | 指値あり商品で他者が active な間の押下は無視。`bid_events.event_type='ignored'` に監査記録 |
| 自分からの離脱 | 不可（権利者・非権利者問わず）。サーバーは `is_active=false` を 403 拒否 |
| auto-left | システム経路のみ。`handlePriceIncrement` の指値保護整理と、指値到達時の `LeaveBidAction` から呼ばれる |
| BidEvent 種別 | `join` / `leave` / `auto_left` / `ignored` (NEW) / `win` / `lose` / etc. |

**呼び出し関係（v1.1 後）**:
```
ユーザー操作                                     システム
─────────────                                  ─────────────
"入札する" ─▶ JoinBidAction                    
                                               handlePriceIncrement
                                                  └─ deactivate（直接 is_active=false）
                                               adjustPriceByBidLimits
                                                  └─ LeaveBidAction（指値到達ユーザー）
                                               checkBidLimits
                                                  └─ LeaveBidAction（指値到達ユーザー）
                                               
"離脱"   ─▶ BidController で 403 拒否（呼ばれない）
```

`LeaveBidAction` から旧版にあった「最高入札者は離脱できません」ガードは削除済み。
唯一の active 参加者（指値到達直前など）が指値経路で正しく離脱できる必要があるため。

## 12. 改修・運用時の注意

1. **マイグレーション中はライブ禁止** — items / bid_participants / lanes をオンライン変更すると行ロック衝突。
2. **php-fpm 再起動はライブ中禁止** — 進行中の入札 tx が ROLLBACK して状態が乱れる。
3. **supervisor reload も基本ライブ中禁止** — countdown ワーカーが kill されると heartbeat 死 → MonitorAuctionJobs が再起動するが、tick が数秒スキップされる。やむを得ない場合は `supervisorctl restart queue-countdown` のみで他は触らない。
4. **Reverb 再起動は致命的** — 全クライアントが再接続するまで broadcast がロスト。再接続中に成約が走ると、その商品の落札通知をクライアントが受信できない（API 取得時には反映済）。
5. **`.env` 変更後は必ず `config:cache`** — `BROADCAST_HOST` などのキャッシュが古いと WS 経路がずれる。
