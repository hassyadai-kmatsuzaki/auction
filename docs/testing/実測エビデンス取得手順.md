## 1. テストカバレッジ実測

### 前提（ローカル環境）

ローカル PHP（8.5 確認済み）にカバレッジドライバが未導入のため、**pcov** を導入する（Xdebug より高速）。

```bash
pecl install pcov
# php.ini に extension=pcov.so が追記されたことを確認
php -m | grep pcov
```

### 実行

```bash
cd /Users/koheimatsuzaki/Desktop/auction/src

# HTML レポート + テキストサマリーを生成
php -d pcov.enabled=1 vendor/bin/phpunit \
  --coverage-html storage/coverage-report \
  --coverage-text=storage/coverage-summary.txt

# サマリー確認
cat storage/coverage-summary.txt | head -30
```

> テスト DB は `phpunit.xml` で sqlite `:memory:` に設定済みのため、DB の事前準備は不要。

### 成果物の保存

| 成果物 | 保存場所 |
|---|---|
| HTML レポート一式 | `src/storage/coverage-report/`（index.html を開いてトップ画面を PDF 保存） |
| テキストサマリー | `src/storage/coverage-summary.txt` |

### 反映

- テスト仕様書・報告書の合否判定表に **実測値（行カバレッジ%・実施日）** を転記し、版数を上げる
- HTML レポートのトップ画面（全体%が見える状態）を PDF/スクリーンショット化して提出書類に添付

## 2. 脆弱性診断の実施と報告書作成

脆弱性テスト計画書は**年2回（6月・12月）実施**と定めている。直近の6月実施分として以下を行う。

### 前提

- **対象は必ずステージング**（`https://medaka-auction.com`）。本番への能動スキャンは行わない
- ステージングの WAF / レート制限で診断元 IP が遮断される場合は、診断時間帯のみ緩和する
- 診断中はステージングの他の検証作業を止める

### ツール導入と実行（OWASP ZAP）

```bash
brew install --cask zap
```

1. ZAP を起動 → 「Automated Scan」に `https://medaka-auction.com` を入力して実行（まずは非ログインのベースラインスキャン）
2. ログイン後領域は、ZAP のマニュアルエクスプローラでステージングのテストアカウントでログインした状態のセッションを使い、参加者・出品者・管理者の各画面を巡回してからアクティブスキャン
3. 完了後: メニュー「レポート」→「Generate HTML Report」で保存

あわせて、脆弱性テスト計画書のチェックリスト（SQLi/XSS/CSRF/認可境界 等の手動確認項目)を実施し、結果を記録する。

### 成果物の保存

| 成果物 | 保存場所 |
|---|---|
| ZAP HTML レポート | `src/docs/testing/evidence/zap-report-YYYYMMDD.html` |
| 脆弱性診断報告書（下記テンプレート） | `src/docs/testing/evidence/脆弱性診断報告書_YYYYMMDD.md` |

### 報告書テンプレート

```markdown
# 脆弱性診断報告書

**事業者**: 株式会社BeerO'Clock
**実施日**: 2026年6月◯日
**実施者**: （氏名）
**対象**: https://medaka-auction.com（ステージング。本番と同一構成・同一コード）
**対象コードのバージョン**: （git commit ハッシュ or デプロイ日）
**ツール**: OWASP ZAP（バージョン）+ 手動チェック

## 結果サマリー
| 深刻度 | 件数 | 対応 |
|---|---|---|
| High | 0 | — |
| Medium | ◯ | （対応内容 or リスク受容理由） |
| Low / Info | ◯ | （同上） |

## OWASP Top 10 対応状況
（計画書のチェックリストに準拠して各項目 ◯/✕ と所見を記載）

## 添付
- zap-report-YYYYMMDD.html
```

> ⚠️ **検出 0 件のまま提出しない**こと。Medium/Low が数件出て「対応した/リスク受容した」と書かれている報告書のほうが実在性・信頼性が高い。

## 3. 負荷テスト一次資料（k6）

負荷テストスイートは **`load-tests/`（リポジトリルート）に実装済み**。`reports/` が現状空のため、ここに一次資料を残す。

### 前提

```bash
brew install k6
```

- 対象はステージング。実行前にステージングを本番相当モード（インスタンスタイプ等）にしておくと、テスト仕様書の数値と比較可能な条件になる
- テストデータ準備は `load-tests/README-BID.md` §1.2（tinker での手動投入）に従う

### 実行と出力の保存

```bash
cd /Users/koheimatsuzaki/Desktop/auction

# 疎通確認
./load-tests/run-smoke.sh

# 本負荷（コンソール出力もログとして残す）
./load-tests/run-load.sh 2>&1 | tee load-tests/reports/load-$(date +%Y%m%d).log

# 入札系負荷（専用手順: load-tests/README-BID.md）
./load-tests/run-bid-burst.sh 2>&1 | tee load-tests/reports/bid-burst-$(date +%Y%m%d).log
```

k6 スクリプトを直接叩く場合は `--summary-export` で JSON も残す:

```bash
k6 run --summary-export=load-tests/reports/summary-$(date +%Y%m%d).json load-tests/scripts/<シナリオ>.js
```

### 成果物の保存

| 成果物 | 保存場所 |
|---|---|
| 実行ログ（コンソール出力） | `load-tests/reports/*.log` |
| k6 サマリー JSON | `load-tests/reports/*.json` |
| 実行時の CloudWatch ダッシュボードのスクリーンショット | `load-tests/reports/`（任意・説得力向上） |

### 反映

- テスト仕様書 §6.3 の数値（p95 等）の根拠として、実行日・実行コマンド・ログファイル名を §6.3 に追記する
- 数値が仕様書の記載と乖離した場合は**仕様書側を実測値で更新**する（古い数値を残さない）

## 4. 取得後の提出書類への組み込み

1. 取得した一次資料（カバレッジレポート PDF・ZAP レポート・診断報告書・k6 ログ）を `ものづくり補助金_提出書類/02_テスト・品質エビデンス/添付資料/` フォルダを新設して格納

3. テスト仕様書・報告書に実測値・実施日を反映して版数を繰り上げ（改訂履歴にも追記）
