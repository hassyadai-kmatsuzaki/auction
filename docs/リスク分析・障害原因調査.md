## 1. オークションが途中で止まる原因

オークションの進行は `ProcessAuctionCountdownJob` という **キュージョブ1本** に依存しています。  
このジョブが何らかの理由で停止すると、カウントダウンが完全に止まります。

### 1-1. 【最重要】キュージョブの自動停止

```php
// ProcessAuctionCountdownJob.php
public int $tries = 1;        // 失敗しても1回しか試みない（リトライなし）
public int $timeout = 3600;   // 1時間でタイムアウト
public int $maxIterations = 3600; // 最大3600ループ
```

**問題:**  
- `tries = 1` のため、例外が発生してもリトライされない
- `maxIterations = 3600` は **1秒間隔**を前提に設計されており、**0.5秒間隔に変更した後は約30分で上限に達する**
- タイムアウト（1時間）前にループが終了するとジョブが停止する

**発生シナリオ:**
```
オークション開始（ジョブ起動）
→ 30分後 maxIterations=3600 に到達
→ ジョブが正常終了扱いで停止
→ カウントダウンが完全に止まる（残り出品物が進行しない）
```

> ✅ **即時対応必須**: `maxIterations` を `7200`（1時間分）以上に増やす

---

### 1-2. キューワーカーのプロセス停止

```
# デフォルトのキュー設定
QUEUE_CONNECTION=database
```

**問題:**  
- `queue:work` は長時間稼働するプロセスだが、**メモリリーク・例外・サーバー再起動**で停止する
- Supervisorなどのプロセス監視ツールが設定されていない場合、停止後に自動復旧しない
- `database` キューは大量アクセス時にDBロック競合が発生しやすい

**チェック事項:**
```bash
# ワーカーが動いているか確認
php artisan queue:monitor countdown

# 失敗ジョブの確認
php artisan queue:failed
```

---

### 1-3. Redisキャッシュの消滅

```php
// CountdownService.php
Cache::put($this->getCacheKey($laneId), $cacheData, 3600); // 1時間でTTL切れ
```

**問題:**  
- カウントダウン状態は `countdown:lane:{id}` というRedisキーに保存されている
- Redisが再起動するとすべてのキーが消える（揮発性）
- TTL = 3600秒（1時間）のため、長時間オークションでキーが期限切れになる可能性

**発生シナリオ:**
```
オークション開始
→ Redis再起動 or キーTTL切れ
→ countdown:lane:{id} が消える
→ tick() が null を返してジョブが停止
→ カウントダウン停止
```

現在の環境では `CACHE_STORE=database` なのでRedisではなくDBが使われているが、  
DB負荷が高まるとキャッシュ読み書きが遅延し、カウントダウンがずれる。

---

### 1-4. データベースキューの `retry_after` 競合

```php
// config/queue.php
'retry_after' => (int) env('DB_QUEUE_RETRY_AFTER', 90), // 90秒
```

**問題:**  
- キュージョブは90秒以上応答がないと「失敗」と判定され、**別のワーカーが同じジョブを再実行**しようとする
- `ProcessAuctionCountdownJob` は **最大1時間動き続ける**ジョブのため、90秒で別プロセスが起動して**二重実行**になる

**発生シナリオ:**
```
ジョブA起動（カウントダウン開始）
→ 90秒後、DBキューが「応答なし」と判定
→ ジョブB起動（同じオークションのカウントダウンが二重に動く）
→ tick()が二重呼び出し → カウントダウンが2倍速で進む
→ 商品が異常な速さで落札・流札される
```

> ✅ **即時対応必須**: `retry_after` を `7200`（2時間）に変更、またはRedisキューに移行

---

### 1-5. 例外発生時のサイレント停止

```php
// ProcessAuctionCountdownJob.php
try {
    $result = $countdownService->tick($lane->id);
} catch (\Exception $e) {
    Log::error("Countdown tick error for lane {$lane->id}: " . $e->getMessage());
    // ← ここで continue しているため、1レーンのエラーが他に伝播しない
    //    しかし同一ループ内でDBエラーが起きた場合はジョブ全体が止まる可能性
}
```

**問題:**
- `$auction = Auction::with('lanes')->find($this->auctionId)` がループ内で毎回DBクエリを実行
- DB接続が一時的に切断された場合、ループが停止する
- エラーログに記録されるが、管理者が気づかなければ手動復旧まで止まったまま

---

### 1-6. フェイルセーフの穴

```php
// LiveController.php resume()
$jobKey = "countdown_job_running:auction:{$auctionId}";
$isJobRunning = Cache::get($jobKey, false);
if (!$isJobRunning) {
    ProcessAuctionCountdownJob::dispatch($auctionId);
}
```

**問題:**
- `countdown_job_running` フラグは「**一時停止→再開**時のみ**チェックされる
- ジョブがサイレントに停止した場合、管理者が「一時停止→再開」を操作しない限り復旧しない
- フラグ自体もRedis/DBキャッシュに保存されているため、キャッシュ消滅時に消える

## 2. 入札オフが反映されないリスク

### 2-1. 【高リスク】API失敗時のUI状態不整合

**コード（AuctionLive.tsx）:**
```typescript
const handleBidToggle = async (itemId, currentStatus) => {
  setBidLoading((prev) => ({ ...prev, [itemId]: true }));
  try {
    const response = await axios.post('/api/participant/bids', { ... });
    if (response.data.success) {
      await fetchLiveState(); // ← 成功時のみUI再同期
    }
  } catch (err) {
    setSnackbar({ message: '入札の切り替えに失敗しました', severity: 'error' });
    // ← 失敗時にfetchLiveState()を呼んでいない
    //   UIとサーバーの状態が乖離する可能性
  }
};
```

**問題:**  
ネットワークエラー・タイムアウト時に、ユーザーには「失敗」と表示されるが、  
サーバー側の処理が完了していた場合、UIとDB状態がズレる。

**最悪のシナリオ:**
```
ユーザーが「入札OFF」を押す
→ APIリクエスト送信
→ サーバー側でOFF処理完了
→ ネットワーク応答が途中で切断
→ UIはエラー表示（「入札OFF」のつもり）
→ サーバーは「入札OFF」になっている（矛盾なし）
↑ この場合はOK

逆ケース:
→ サーバー側で処理失敗（タイムアウト等）
→ UIはスナックバーでエラー表示のみ
→ 次の操作でUIとサーバーが食い違う
```

---

### 2-2. 【高リスク】カウントダウン終了との競合

**コード（BidService.php leave）:**
```php
public function leave(Item $item, int $userId, ...): array
{
    if ($item->status !== 'live') {
        return ['success' => false, 'message' => '...'];
    }
    DB::beginTransaction();
    // ...deactivate()...
    DB::commit();
}
```

**コード（CountdownService.php handleCountdownEnd）:**
```php
protected function handleCountdownEnd(...): array
{
    $this->stopCountdown($lane->id);
    DB::beginTransaction();
    if ($activeBidderCount === 1) {
        $this->bidService->finalizeBid($item); // ← 落札処理
    }
    DB::commit();
}
```

**問題:**  
トランザクションレベルの排他制御がなく、以下の競合が発生しうる。

```
カウントダウン残り 0.5秒

[ユーザー]                    [カウントダウンジョブ]
入札OFF押下 →                  
  DBで is_active=false 書き込み中
                         ↓ tick() 実行
                         activeBidderCount = 1 (まだOFFが反映されてない)
                         カウントダウン = 0 → finalizeBid()
                         → 意図せず落札確定！
```

---

### 2-3. BidderUpdated イベントの toOthers() 設計

```php
// BidService.php join()
broadcast(new BidderUpdated(...))->toOthers();
// ↑ 自分以外にしかブロードキャストしない
```

**問題:**  
自分の入札参加・離脱操作後、**自分自身はWebSocketで入札者数の更新を受け取れない**。  
`fetchLiveState()` で補完しているが、0.5秒以内に次のカウントダウンTickが来た場合は  
自分の入札状態が反映される前に古い入札者数が表示されることがある。

## 3. 画面が固まるリスク

### 3-1. 【高リスク】0.5秒カウントダウンによる過剰レンダリング

```typescript
// AuctionLive.tsx onCountdownTick
setLiveState((prev) => {
  return {
    ...prev,
    lanes: prev.lanes.map((lane) => ...) // 全レーン再計算
  };
});
```

**計算:**

| レーン数 | 更新頻度 | 1秒あたりのsetState回数 |
|---------|---------|----------------------|
| 1レーン  | 0.5秒/回 | 2回 |
| 3レーン  | 0.5秒/回 | **6回** |
| 6レーン  | 0.5秒/回 | **12回** |

各 `setLiveState` はReactの再レンダリングを発生させる。  
レーンカードが多い場合は、毎秒12回の再レンダリングが発生し、低スペック端末では処理が追いつかなくなる。

---

### 3-2. Pusherのメッセージレート制限

| Pusherプラン | メッセージ/秒上限 | 6レーン0.5秒時のイベント数/秒 |
|------------|---------------|---------------------------|
| 無料プラン   | 10            | 12〜18（**超過**）          |
| Startup    | 100           | 12〜18（安全）              |
| Pro        | 1,000         | 安全                       |

Pusherの上限を超えると：
- メッセージが**キューイング・遅延**される
- 場合によっては**ドロップ（消滅）**
- フロントエンドで「残り3秒」が突然「残り0秒」になる現象

---

### 3-3. WebSocket切断後の復旧がない

```typescript
// echo.ts
pusher.connection.bind('disconnected', () => {
  console.warn('[Echo] Pusher disconnected');
  // ← 警告ログのみ。自動再接続・状態再取得のロジックがない
});
```

**問題:**  
- ネットワーク一時切断後、Pusherが自動再接続しても**カウントダウン状態が古いまま**
- 再接続後に `fetchLiveState()` を呼ぶロジックがない
- ユーザーには古い状態が表示され続ける

---

### 3-4. メモリリーク（長時間使用時）

```typescript
// useAuctionSocket.ts
return () => {
  echo.leave(channelName); // ← クリーンアップ処理
};
```

クリーンアップ自体はあるが:
- Strict Mode でのダブルマウント時にリスナーが重複する可能性
- 3〜4時間の長時間オークションで徐々にメモリが増加する
- `countdownIntervalRef` などのrefが正しくクリアされないと `setInterval` が積み重なる

## 4. データ整合性リスク

### 4-1. カウントダウンキャッシュとDBのズレ

```
DB: item.status = 'live'
Redis/Cache: countdown:lane:{id} = 存在しない（キー消滅）
```

この状態になると：
- `tick()` が `null` を返し、カウントダウンが止まる
- 商品は `live` のままどこまでも保持され続ける
- 手動で管理者が「次の商品へ」を押すまで解消されない

---

### 4-2. 落札処理のトランザクション外ブロードキャスト

```php
// BidService.php finalizeAsSold()
DB::commit(); // ← DB確定

broadcast(new ItemSold(...)); // ← ブロードキャストはDB確定後
```

通常はこれで正しいが、`broadcast()` がPusherへの送信に失敗した場合：
- DBには落札レコードが作成されている
- フロントエンドには落札通知が届かない
- 参加者の画面が「まだ入札中」のまま固まる

## 5. 端末・環境依存リスク

### 5-1. モバイル端末の省電力モード

| 状態 | 影響 |
|------|------|
| バックグラウンドタブ | WebSocket受信が遅延・停止 |
| バッテリー節約モード | CPU制限でレンダリング遅延 |
| スリープ復帰後 | WebSocket切断、状態が古いまま |

---

### 5-2. ブラウザ別の挙動差異

| ブラウザ | 懸念事項 |
|---------|---------|
| Safari (iOS) | WebSocketの非アクティブ切断が他より積極的 |
| Chrome Android | バックグラウンドでJSが停止する場合がある |
| Firefox | 問題少ないが古いバージョンはWebSocket対応が不完全 |

---

### 5-3. ネットワーク品質

- **会場Wi-Fi** は多数接続で帯域が共有されるため、0.5秒カウントダウンイベントが混雑する
- **モバイル回線** は基地局切り替え時に一時的に100〜500ms切断が発生する

## 7. 推奨対策ロードマップ

### 🔴 Phase 1: 即時対応（オークション前に必須）

#### 対策1: maxIterations を修正

```php
// ProcessAuctionCountdownJob.php
public function __construct(int $auctionId, int $maxIterations = 14400) // 2時間分（0.5秒×14400=7200秒）
{
    $this->maxIterations = $maxIterations;
    $this->timeout = 7200; // 2時間に延長
}
```

#### 対策2: DBキューの retry_after を延長

```
# .env
DB_QUEUE_RETRY_AFTER=10800  # 3時間
```

または、**Redisキューへの切り替え**（推奨）:
```
QUEUE_CONNECTION=redis
```

#### 対策3: API失敗時に状態再同期

```typescript
// AuctionLive.tsx handleBidToggle
} catch (err: any) {
  setSnackbar({ message: 'エラーが発生しました。状態を再取得しています...', severity: 'error' });
  await fetchLiveState(); // ← 追加：エラー時もUI同期
}
```

```typescript
pusher.connection.bind('disconnected', () => {
```

```typescript
// カウントダウン表示を別コンポーネントに分離してメモ化
const CountdownChip = React.memo(({ seconds, bidderCount }: { seconds: number; bidderCount: number }) => (
  <Chip
    label={`残り ${formatCountdownSeconds(seconds)}`}
    color={bidderCount >= 2 ? 'error' : seconds <= 3 ? 'warning' : 'default'}
  />
));
```

#### 対策6: ジョブ死活監視

```php

$isJobRunning = Cache::get("countdown_job_running:auction:{$auctionId}", false);
if (!$isJobRunning && $auction->status === 'live') {
```

### 🟢 Phase 3: 長期対応（本番化前）

#### 対策7: Pusherプランのアップグレード

0.5秒カウントダウン + 複数レーン運用では **Startupプラン以上が必須**。

#### 対策8: キューバックエンドをRedisに移行

```
QUEUE_CONNECTION=redis
CACHE_STORE=redis
```

Redisはインメモリでの高速処理が可能で、`database`キューよりも信頼性が高い。

#### 対策9: 入札排他ロック

```php
// BidService.php leave()
public function leave(Item $item, int $userId, ...): array
{
    // 落札処理との競合を防ぐ排他ロック
    $lock = Cache::lock("bid:item:{$item->id}", 3);
    return $lock->block(3, function () use ($item, $userId, ...) {
        // 処理
    });
}
```

#### 対策10: Supervisorによるプロセス管理

```ini
# /etc/supervisor/conf.d/auction-countdown.conf
[program:auction-countdown-worker]
command=php /var/www/auction/artisan queue:work --queue=countdown --timeout=7200 --tries=1
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
```

## 補足: 管理者向け緊急対応手順

### オークションが途中で止まった場合

```bash
# 1. 失敗ジョブを確認
php artisan queue:failed

# 2. カウントダウン状態を確認
php artisan tinker
>>> Cache::get('countdown:lane:1')  // レーンIDを指定

# 3. 手動でジョブを再起動
php artisan tinker
>>> \App\Jobs\ProcessAuctionCountdownJob::dispatch(1)  // オークションIDを指定

# 4. ワーカーを再起動
php artisan queue:restart
```

### 入札状態がおかしい場合

```bash
php artisan tinker
# アクティブな入札者を確認
>>> \App\Models\BidParticipant::forItem(1)->active()->get()

# 手動でOFFにする（緊急時）
>>> \App\Models\BidParticipant::forItem(1)->forUser(99)->first()->deactivate()
```
