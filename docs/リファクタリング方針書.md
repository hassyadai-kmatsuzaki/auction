## 2. バックエンド: クリーンアーキテクチャ方針

### 目標アーキテクチャ

```
┌─────────────────────────────────────────────┐
│         HTTP Layer (Controllers)            │  ← リクエスト受付・レスポンス返却のみ
├─────────────────────────────────────────────┤
│         Application Layer (Services)        │  ← ユースケース（ビジネスルール）
├─────────────────────────────────────────────┤
│         Domain Layer (Models + Events)      │  ← ドメインロジック・バリデーション
├─────────────────────────────────────────────┤
│    Infrastructure Layer (Repositories)      │  ← DB・Cache・外部API アクセス
└─────────────────────────────────────────────┘
```

### 2-1. 新規追加するレイヤー

#### Repositories（データアクセス層）

現在はServiceやControllerがEloquentを直接呼び出している。  
Repositoryを挟むことで、将来的なDB変更・テストが容易になる。

```
app/
├── Repositories/
│   ├── Contracts/            ← インターフェース定義
│   │   ├── AuctionRepositoryInterface.php
│   │   ├── ItemRepositoryInterface.php
│   │   ├── BidParticipantRepositoryInterface.php
│   │   └── LaneRepositoryInterface.php
│   └── Eloquent/             ← 実装
│       ├── AuctionRepository.php
│       ├── ItemRepository.php
│       ├── BidParticipantRepository.php
│       └── LaneRepository.php
```

#### Actions（単一責任のユースケース）

現在のServiceは複数の責務を持つ。  
1アクション1クラスにすることで、テスト・変更が容易になる。

### 3-2. 状態の種類と管理場所の分類

オークションの状態は大きく3種類に分類できる。

```
┌───────────────────────────────────────────────────────┐
│  サーバー状態（Server State）                           │
│  → TanStack Query で管理                               │
│  例: ライブ状態, 落札一覧, オークション一覧             │
├───────────────────────────────────────────────────────┤
│  グローバルUIState（Global Client State）               │
│  → Zustand で管理                                      │
│  例: 認証情報, 通知, WebSocket接続状態                 │
├───────────────────────────────────────────────────────┤
│  ローカルUIState（Local Client State）                  │
│  → useState（そのまま）で管理                          │
│  例: ダイアログ開閉, フォーム入力値, ローディング状態   │
└───────────────────────────────────────────────────────┘
```

## 4. 状態管理ライブラリ選定

### 4-1. TanStack Query（旧React Query）— サーバー状態管理

**導入推奨: ◎ 必須**

サーバーデータのキャッシュ・再取得・ポーリングを自動管理。  
現状の「fetchLiveState → setLiveState → ポーリング」という手動管理を自動化できる。

```typescript
// 現状（手動管理・複雑）
const [liveState, setLiveState] = useState<LiveState | null>(null);
const [loading, setLoading] = useState(true);
const fetchLiveState = useCallback(async () => {
  setLoading(true);
  try {
    const res = await axios.get(`/api/...`);
    setLiveState(res.data.data);
  } finally {
    setLoading(false);
  }
}, []);
useEffect(() => {
  fetchLiveState();
  const interval = setInterval(fetchLiveState, 5000); // ポーリング
  return () => clearInterval(interval);
}, []);

// TanStack Query 導入後（シンプル・堅牢）
const { data: liveState, isLoading, refetch } = useQuery({
  queryKey: ['auction-live', auctionId],
  queryFn: () => auctionApi.getLiveState(auctionId),
  refetchInterval: socketConnected ? false : 5000, // WebSocket接続中はポーリング不要
  staleTime: 1000,
  retry: 3,    // 失敗時に自動リトライ
});
```

**TanStack Queryの主なメリット:**

| 機能 | 効果 |
|------|------|
| キャッシュ管理 | 同じデータを複数箇所で使っても1回だけフェッチ |
| 自動リトライ | ネットワークエラー時に自動で再試行 |
| バックグラウンド再取得 | タブを戻った時に自動で最新状態に同期 |
| 楽観的更新 | 入札ボタンを押した瞬間にUIを更新（APIレスポンス待たない） |
| 状態の自動管理 | loading/error/data を手動管理しなくてよい |

### 4-2. Zustand — グローバルUI状態管理

**導入推奨: ◎ 推奨**

Redux より軽量・シンプル。ボイラープレートが少ない。

```typescript
// stores/auctionLiveStore.ts
import { create } from 'zustand';
import { subscribeWithSelector } from 'zustand/middleware';

interface AuctionLiveStore {
  socketConnected: boolean;
  setSocketConnected: (v: boolean) => void;

  // 入札ロック（競合防止）
  bidLockMap: Record<number, boolean>;
  lockBid: (itemId: number) => void;
  unlockBid: (itemId: number) => void;
}

export const useAuctionLiveStore = create<AuctionLiveStore>()(
  subscribeWithSelector((set) => ({
    socketConnected: false,
    setSocketConnected: (v) => set({ socketConnected: v }),
    bidLockMap: {},
    lockBid: (itemId) => set((s) => ({ bidLockMap: { ...s.bidLockMap, [itemId]: true } })),
    unlockBid: (itemId) => set((s) => ({ bidLockMap: { ...s.bidLockMap, [itemId]: false } })),
  }))
);
```

### 4-3. Recoil / Jotai について

**導入推奨: △ 不要**

Recoil・Jotai はアトム単位の細かい状態管理が得意だが、  
このシステムでは「サーバー状態（TanStack Query）+ グローバルUI（Zustand）」の  
2層構成で十分カバーできるため、導入による複雑さの増加がメリットを上回る。

| ライブラリ | 向いているケース | 今回の判断 |
|-----------|---------------|---------|
| TanStack Query | サーバーデータのキャッシュ・同期 | ✅ 導入 |
| Zustand | グローバルUIの状態管理 | ✅ 導入 |
| Jotai | 細粒度なアトム管理（Excelのようなアプリ） | ❌ 不要 |
| Recoil | Meta製、Facebookスケール向け | ❌ 不要 |
| Redux Toolkit | 大規模エンタープライズ | ❌ オーバースペック |

## 6. 具体的なコード設計例

### 6-1. TanStack Query + Zustand 導入後の AuctionLive

```typescript
// features/auction-live/hooks/useAuctionLive.ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { useAuctionLiveStore } from '../stores/auctionLiveStore';
import { auctionApi } from '@/api/participant/auctionApi';
import { bidApi } from '@/api/participant/bidApi';

export function useAuctionLive(auctionId: number) {
  const queryClient = useQueryClient();
  const { socketConnected } = useAuctionLiveStore();

  // サーバー状態はTanStack Queryで管理
  const {
    data: liveState,
    isLoading,
    error,
  } = useQuery({
    queryKey: ['auction-live', auctionId],
    queryFn: () => auctionApi.getLiveState(auctionId),
    refetchInterval: socketConnected ? false : 3000,
    retry: 3,
    staleTime: 500,
  });

  // WebSocketイベントでキャッシュを即時更新（再フェッチ不要）
  const updateCountdown = (event: CountdownTickEvent) => {
    queryClient.setQueryData(['auction-live', auctionId], (prev: LiveState | undefined) => {
      if (!prev) return prev;
      return {
        ...prev,
        lanes: prev.lanes.map((lane) =>
          lane.lane_id === event.lane_id && lane.current_item
            ? { ...lane, current_item: { ...lane.current_item, countdown_seconds: event.remaining_seconds } }
            : lane
        ),
      };
    });
  };

  return { liveState, isLoading, error, updateCountdown };
}
```

```typescript
// features/auction-live/hooks/useBidToggle.ts
export function useBidToggle(auctionId: number) {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: ({ itemId, isActive }: { itemId: number; isActive: boolean }) =>
      bidApi.toggle(itemId, isActive),
    
    // 楽観的更新: APIレスポンス前にUIを即時更新
    onMutate: async ({ itemId, isActive }) => {
      await queryClient.cancelQueries({ queryKey: ['auction-live', auctionId] });
      const prev = queryClient.getQueryData(['auction-live', auctionId]);
      
      queryClient.setQueryData(['auction-live', auctionId], (old: LiveState | undefined) => ({
        ...old!,
        lanes: old!.lanes.map((lane) =>
          lane.current_item?.id === itemId
            ? { ...lane, current_item: { ...lane.current_item, my_bid_status: isActive ? 'active' : 'inactive' } }
            : lane
        ),
      }));
      
      return { prev }; // ロールバック用
    },
    
    // 失敗時: 楽観的更新を元に戻す
    onError: (_err, _vars, context) => {
      queryClient.setQueryData(['auction-live', auctionId], context?.prev);
    },
    
    // 完了時: サーバーから最新状態を再取得（成功・失敗どちらも）
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ['auction-live', auctionId] });
    },
  });

  return mutation;
}
```

```php
// app/Actions/Bid/LeaveBidAction.php
<?php

namespace App\Actions\Bid;

use App\DTOs\BidResultDto;
use App\Events\BidderUpdated;
use App\Models\BidEvent;
use App\Models\BidParticipant;
use App\Models\Item;
use App\Models\Lane;
use Illuminate\Support\Facades\DB;

class LeaveBidAction
{
    public function execute(Item $item, int $userId, ?string $ip, ?string $ua): BidResultDto
    {
        if ($item->status !== 'live') {
            return BidResultDto::failure('この商品は現在入札を受け付けていません。');
        }

        DB::beginTransaction();
        try {
            $participant = BidParticipant::forItem($item->id)->forUser($userId)->first();
            if (!$participant || !$participant->is_active) {
                DB::rollBack();
                return BidResultDto::failure('入札に参加していません。');
            }

            $participant->deactivate();
            BidEvent::recordLeave($item->id, $userId, $item->current_price, $ip, $ua);
            $activeCount = BidParticipant::forItem($item->id)->active()->count();

            DB::commit();

            // 疎結合: イベント経由でカウントダウンに通知
            $lane = Lane::where('current_item_id', $item->id)->first();
            if ($lane) {
                broadcast(new BidderUpdated($item->auction->id, $lane->id, $item->id, $activeCount, 'left'))
                    ->toOthers();
            }

            return BidResultDto::success([
                'item_id'             => $item->id,
                'is_active'           => false,
                'current_price'       => $item->current_price,
                'active_bidder_count' => $activeCount,
            ]);
        } catch (\Exception $e) {
            DB::rollBack();
            throw $e;
        }
    }
}
```

### 6-4. WebSocket切断時の自動復旧

```typescript
// hooks/useSocketReconnect.ts
import { useEffect } from 'react';
import { getEcho } from '@/lib/echo';
import { useQueryClient } from '@tanstack/react-query';
import { useAuctionLiveStore } from '@/features/auction-live/stores/auctionLiveStore';

export function useSocketReconnect(auctionId: number) {
  const queryClient = useQueryClient();
  const setSocketConnected = useAuctionLiveStore((s) => s.setSocketConnected);

  useEffect(() => {
    const echo = getEcho();
    if (!echo) return;

    const pusher = (echo as any).connector?.pusher;
    if (!pusher) return;

    const onConnected = () => {
      setSocketConnected(true);
    };
    const onDisconnected = () => {
      setSocketConnected(false);
      // 切断時: ポーリングに自動切り替え（TanStack QueryがrefetchIntervalを見る）
    };
    const onReconnected = () => {
      setSocketConnected(true);
      // 再接続時: 最新状態を即時再取得
      queryClient.invalidateQueries({ queryKey: ['auction-live', auctionId] });
    };

    pusher.connection.bind('connected', onConnected);
    pusher.connection.bind('disconnected', onDisconnected);
    pusher.connection.bind('connected', onReconnected); // 再接続も同じイベント

    return () => {
      pusher.connection.unbind('connected', onConnected);
      pusher.connection.unbind('disconnected', onDisconnected);
    };
  }, [auctionId, queryClient, setSocketConnected]);
}
```

## まとめ: 堅牢なオークションサービスのための3原則

### 原則1: サーバーが正しい（Single Source of Truth）

フロントエンドの表示は常にサーバーの状態を反映する。  
WebSocketはリアルタイム性のためだけに使い、サーバー状態は常にAPIで同期可能な状態を保つ。

### 原則2: 失敗を前提に設計する

- API失敗時 → 自動リトライ（TanStack Query）
- WebSocket切断 → ポーリングにフォールバック（TanStack Query refetchInterval）
- ジョブ停止 → 死活監視コマンドで自動再起動
- 競合書き込み → Cache::lock で排他制御

### 原則3: 1ファイル1責務

- Controllerはリクエスト受付・レスポンス返却のみ
- Actionは1つのユースケース処理のみ
- コンポーネントは1つの表示責務のみ
- カスタムフックは1つのロジック責務のみ
