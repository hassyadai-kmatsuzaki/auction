# オークション開始不可ケース 調査レポート

**調査日**: 2026-03-09  
**対象**: 生体登録・レーン割り当て済みにも関わらずオークションが開始できないケース

---

## 概要

コードベース全体を調査した結果、生体登録とレーン割り当てを行ったにも関わらずオークションが開始できない原因として、**7つの可能性**を特定しました。影響度の高い順に報告します。

---

## 原因1: オークションのステータスが「scheduled」になっていない【最有力】

### 影響度: ★★★★★（非常に高い）

### 詳細

オークション開始には2つの経路がありますが、**どちらも `scheduled` ステータスを要求**します。

#### 経路A: `LiveController::start()` （管理画面の「開始」ボタン）

```237:241:src/app/Http/Controllers/Admin/LiveController.php
        if (!in_array($auction->status, ['preparing', 'scheduled'])) {
            return response()->json([
                'success' => false,
                'message' => 'このオークションは開始できません。',
            ], 400);
```

一見 `preparing` でも通過できるように見えますが、この経路の内部では `StartAuctionAction` は呼ばれず、直接 `live` に更新されます。

#### 経路B: `StartAuctionAction::execute()` （スケジュール自動開始）

```25:27:src/app/Actions/Auction/StartAuctionAction.php
        if ($auction->status !== 'scheduled') {
            throw new \RuntimeException('このオークションは開始できません。（ステータス: ' . $auction->status . '）');
        }
```

こちらは **`scheduled` 以外すべて拒否**します。

### 発生シナリオ

1. オークションを作成（ステータス: `preparing`）
2. 生体を登録し、レーン割り当てを実施
3. **ステータスを `scheduled` に変更し忘れた**
4. `StartAuctionAction` 経由で開始しようとすると `RuntimeException` で失敗

### 確認方法

- `auctions` テーブルの `status` カラムが `scheduled` であるか確認
- 管理画面でオークション詳細を開き、ステータス表示を確認

---

## 原因2: 生体のステータスが「registered」ではない

### 影響度: ★★★★★（非常に高い）

### 詳細

`Auction::canStart()` は `registered` ステータスの生体が1件以上あることを要求します。

```116:118:src/app/Models/Auction.php
        return $this->status === 'scheduled' 
            && $this->items()->where('status', 'registered')->count() > 0;
```

また、`LiveController::start()` でも商品数チェックがあります。

```245:249:src/app/Http/Controllers/Admin/LiveController.php
        if ($auction->items()->count() === 0) {
            return response()->json([
                'success' => false,
                'message' => '商品が登録されていません。',
            ], 400);
```

さらに、レーン割り当て時の自動割り当てロジックも `registered` のみを対象にしています。

```395:398:src/app/Http/Controllers/Admin/LaneController.php
        $premiumItems = Item::where('auction_id', $auctionId)
            ->where('status', 'registered')
            ->where('is_premium', true)
            ->orderBy('item_number')
```

### 発生シナリオ

1. 生体を登録したが、ステータスが `draft`（下書き）のまま
2. 管理者が承認操作（`draft` → `registered`）を行っていない
3. `canStart()` が `false` を返し、開始不可

### 確認方法

- `items` テーブルで該当オークションの生体のステータスを確認
- `SELECT status, COUNT(*) FROM items WHERE auction_id = ? GROUP BY status`

## 原因3: レーンに生体が割り当てられているが、レーン自体が存在しない

### 影響度: ★★★★☆（高い）

### 詳細

`LiveController::start()` の `createLanesIfNeeded()` は、レーンが0個の場合のみ作成します。

```356:367:src/app/Http/Controllers/Admin/LiveController.php
    private function createLanesIfNeeded(Auction $auction): void
    {
        if ($auction->lanes()->count() === 0) {
            for ($i = 1; $i <= $auction->lane_count; $i++) {
                Lane::create([
                    'auction_id' => $auction->id,
                    'lane_number' => $i,
                    'status' => 'waiting',
                ]);
            }
        }
    }
```

しかし、`auction->lane_count` が `0` や `null` の場合、レーンが1つも作成されません。

### 発生シナリオ

1. オークション作成時に `lane_count` が `1` で初期化される
2. レーン割り当て画面でレーンを削除し、`syncLaneCount()` で `lane_count` が `0` に
3. その後レーンを再作成せずに開始しようとする
4. `assignItemsToLanes()` で `$laneCount === 0` となり、商品がレーンに割り当てられない
5. 各レーンに `startNextItem()` で開始する商品がなく、実質的にオークションが機能しない

### 確認方法

- `auctions.lane_count` の値を確認
- `lanes` テーブルで該当オークションのレーン数を確認

## 原因4: `LiveController::start()` と `StartAuctionAction` の二重パス問題

### 影響度: ★★★★☆（高い）

### 詳細

コードベースにはオークション開始の経路が**2つ**存在し、それぞれ異なるバリデーションを行っています。

| 項目 | `LiveController::start()` | `StartAuctionAction::execute()` |
|------|--------------------------|-------------------------------|
| ステータス要件 | `preparing` or `scheduled` | `scheduled` のみ |
| 商品数チェック | `items()->count() === 0` （全ステータス） | なし（暗黙的） |
| レーン作成 | `createLanesIfNeeded()` | `ensureLanes()` |
| 商品割り当て | `assignItemsToLanes()` (プレミアム優先) | `assignItems()` (item_number順) |
| カウントダウンジョブ | `ProcessAuctionCountdownJob::dispatch()` | `ProcessAuctionCountdownJob::dispatch()` |

`LiveController::start()` は `preparing` ステータスでも通過できますが、`Auction::canStart()` は `scheduled` のみを許可しています。この不整合により、**ステータス変更API（`updateStatus`）経由で `live` にしようとすると `canStart()` で拒否される**ケースがあります。

```81:86:src/app/Actions/Auction/UpdateAuctionStatusAction.php
    private function toLiveState(Auction $auction): string|array
    {
        if (!$auction->start()) {
            return ['error' => 'オークションを開始できません。承認済みの生体を1件以上登録してください。'];
        }
        return 'オークションを開始しました。';
    }
```

### 発生シナリオ

1. 管理者がステータス変更APIで `preparing` → `live` に直接変更しようとする
2. `Auction::canStart()` が `status === 'scheduled'` をチェックし `false` を返す
3. エラー「承認済みの生体を1件以上登録してください」が表示される（実際は生体は登録済み）

## 原因5: キューワーカーが起動していない / `countdown` キューが処理されていない

### 影響度: ★★★★☆（高い）

### 詳細

オークション開始後、`ProcessAuctionCountdownJob` がキューにディスパッチされますが、このジョブは `countdown` 専用キューに投入されます。

```53:53:src/app/Jobs/ProcessAuctionCountdownJob.php
        $this->onQueue('countdown'); // 専用キュー
```

キューワーカーが `countdown` キューを処理していない場合、以下が発生します。

1. オークションのステータスは `live` に変更される（DB更新は成功）
2. プレスタートカウントダウン（10秒）のブロードキャストが行われない
3. 各レーンのカウントダウンが開始されない
4. **UIではオークションが「開始中」のまま固まる**

### 発生シナリオ

- `php artisan queue:work --queue=countdown` が実行されていない
- Redis接続エラーでキューが処理できない
- ワーカーがクラッシュして再起動されていない

### 確認方法

- `php artisan queue:work --queue=countdown` が稼働しているか確認
- Redis の `queues:countdown` キーにジョブが溜まっていないか確認
- `laravel.log` に `Dispatched auction countdown job` のログがあるか確認

## 原因6: 前回のオークションのカウントダウンジョブロックが残っている

### 影響度: ★★★☆☆（中程度）

### 詳細

`ProcessAuctionCountdownJob` は排他制御のためにキャッシュロックを使用しています。

```62:69:src/app/Jobs/ProcessAuctionCountdownJob.php
        $lockKey = "countdown_job_lock:auction:{$this->auctionId}";
        $lockAcquired = Cache::add($lockKey, getmypid(), $this->timeout + 60);

        if (!$lockAcquired) {
            $existingPid = Cache::get($lockKey);
            Log::warning("Auction countdown job SKIPPED for auction {$this->auctionId}: another job is running (pid={$existingPid})");
            return;
        }
```

`StartAuctionAction` ではロックのクリアを試みていますが、**同じオークションIDで再開始する場合**にのみ有効です。

```55:57:src/app/Actions/Auction/StartAuctionAction.php
        Cache::forget("countdown_job_lock:auction:{$auction->id}");
        Cache::forget("countdown_job_running:auction:{$auction->id}");
        Cache::forget("countdown_job_heartbeat:auction:{$auction->id}");
```

一方、`LiveController::start()` にはこのロッククリア処理がありません。

### 発生シナリオ

1. オークションを開始し、途中で異常終了（ワーカークラッシュ等）
2. ロックがキャッシュに残ったまま（TTL: timeout + 60秒 = 約4時間）
3. 同じオークションを再開始しようとする
4. `LiveController::start()` 経由の場合、ロッククリアが行われない
5. ジョブがディスパッチされるが、`lockAcquired` が `false` で即座にスキップ
6. カウントダウンが開始されず、オークションが機能しない

### 確認方法

- Redis で `countdown_job_lock:auction:{id}` キーの存在を確認
- `laravel.log` に `SKIPPED` ログがないか確認

## 原因7: `LiveController::start()` のトランザクション範囲の問題

### 影響度: ★★★☆☆（中程度）

### 詳細

`LiveController::start()` のトランザクション構造に問題があります。

```252:308:src/app/Http/Controllers/Admin/LiveController.php
        DB::beginTransaction();
        try {
            $this->createLanesIfNeeded($auction);
            $this->assignItemsToLanes($auction);
            $auction->update(['status' => 'live']);
            // ...
            DB::commit();

            // ← ここでブロードキャストとジョブディスパッチ
            broadcast(new AuctionStatusChanged(...));
            ProcessAuctionCountdownJob::dispatch($auction->id);

            return response()->json([...]);
        } catch (\Exception $e) {
            DB::rollBack();
            throw $e;
        }
```

`DB::commit()` の後にブロードキャストとジョブディスパッチが行われますが、**ブロードキャストやジョブディスパッチで例外が発生した場合**、`catch` ブロックに入り `DB::rollBack()` が呼ばれます。しかし、既にコミット済みのため、ロールバックは効果がなく、**ステータスは `live` のまま、ジョブは未ディスパッチ**という不整合が発生します。

### 発生シナリオ

1. DB トランザクションは正常にコミット（ステータス `live`、レーン割り当て完了）
2. ブロードキャスト（WebSocket）でネットワークエラー発生
3. 例外が `catch` に到達、`rollBack()` は空振り
4. レスポンスが返らず、フロントエンドではエラー表示
5. 管理者が再度「開始」を押すと、ステータスが既に `live` のため拒否される

## まとめ: 発生可能性ランキング

| 順位 | 原因 | 発生可能性 | 対処の容易さ |
|------|------|-----------|------------|
| 1 | ステータスが `scheduled` でない | 非常に高い | 容易 |
| 2 | 生体ステータスが `registered` でない | 非常に高い | 容易 |
| 3 | キューワーカー未起動 / `countdown` キュー未処理 | 高い | 中程度 |
| 4 | 二重パス問題（`preparing` → `live` 直接遷移） | 高い | 要コード修正 |
| 5 | カウントダウンジョブロック残存 | 中程度 | 中程度 |

## 推奨対応

### 即時対応（運用回避）

1. **オークション開始前チェックリスト**を作成し、以下を確認する運用を徹底
   - オークションステータスが `scheduled` であること
   - 生体のステータスが `registered`（承認済み）であること
   - レーンが1つ以上存在すること
   - `countdown` キューワーカーが稼働していること

### コード修正（中期対応）

1. **`LiveController::start()` にカウントダウンジョブロックのクリア処理を追加**
   - `StartAuctionAction` と同様のロッククリア処理を追加

2. **`LiveController::start()` のステータスチェックを厳格化**
   - `preparing` を許可せず、`scheduled` のみに限定
   - または `preparing` → `scheduled` の自動遷移を追加

3. **トランザクション範囲の修正**
   - ブロードキャストとジョブディスパッチを `try-catch` の外に移動
   - コミット後の処理失敗時のリカバリロジックを追加

4. **開始前バリデーションの統一**
   - `LiveController::start()` と `StartAuctionAction` のバリデーションを統一
   - 共通の `canStartAuction()` メソッドを作成し、詳細なエラーメッセージを返す

5. **フロントエンドの開始ボタン表示条件の改善**
   - 現在は `!isLive && status !== 'finished'` で表示されるが、`scheduled` のみに限定すべき
   - 生体が `registered` 状態で存在するかのチェックも追加
