## 1. 500人対応 ターゲットインフラ構成

### 運用方針: 開催スケジュール連動の2モード運用

オークション開催は**月2回**のため、**常時500人対応は過剰**。
開催2日前〜開催2日後のみスケールアップし、それ以外は最小構成で運用する。

```
月間スケジュール例:
 1日───────10日────────15日────────20日────────30日
  │ 通常モード │▓オークション▓│ 通常モード │▓オークション▓│通常│
  │  (低コスト) │▓ モード(5日)▓│ (低コスト)  │▓ モード(5日)▓│    │
```

### 2モードのスペック比較

| コンポーネント | 通常モード（~20日/月） | オークションモード（~10日/月） |
|--------------|---------------------|---------------------------|
| EC2 | t3.small (2vCPU / 2GB) | **t3.large (2vCPU / 8GB)** |
| PHP-FPM | max_children=30 | max_children=80（推奨）〜100 |
| Queue Worker | countdown×1, default×1 | countdown×5, default×2 |
| RDS | db.t3.micro Single-AZ (1GB) | **db.t3.medium Multi-AZ (4GB)** |
| ElastiCache | cache.t3.micro レプリカなし | **cache.t3.medium + レプリカ** |

### 月額コスト

| 運用パターン | 月額 (USD) | 月額 (JPY) |
|------------|-----------|-----------|
| 常時500人対応（非推奨） | $376 | ¥56,400 |
| **開催連動2モード（推奨）** | **~$190** | **~¥28,500** |

> **約50%のコスト削減**（年間 約¥330,000 節約）

詳細なコスト試算・自動スケーリングの設計は [§14. コスト最適化](#14-コスト最適化オークション開催スケジュール連動--完全自動化) を参照。

**自動化の仕組み**: オークション作成時に `AuctionObserver` が EventBridge Schedule を自動登録。
開催2日前の AM3:00 に Step Functions がスケールアップ、開催2日後の AM3:00 にスケールダウンを自動実行。
スケールダウン忘れのリスクはゼロ。

### 現構成からの変更点

| 項目 | 変更前 | オークションモード | 通常モード |
|------|--------|-----------------|-----------|
| EC2 | t3.medium (4GB) | **t3.large (8GB)** | t3.small (2GB) |
| RDS | db.t3.micro (1GB) | **db.t3.medium Multi-AZ (4GB)** | db.t3.micro (1GB) |
| ElastiCache | cache.t3.small × 1 | **cache.t3.medium + レプリカ** | cache.t3.micro × 1 |

### プロセス構成（EC2 1台あたり）

```
EC2 t3.large (2vCPU / 8GB RAM)
├── Nginx                    … リバースプロキシ + 静的ファイル配信 (~200MB)
├── PHP-FPM (max 100)        … Laravel API (~5GB max)
│   ├── pm.start_servers=20
│   ├── pm.min_spare=10
│   └── pm.max_spare=40
├── Laravel Reverb           … WebSocketサーバー (~500MB)
│   └── 500+ 同時WebSocket接続
├── Queue Worker × 5         … countdown キュー (~500MB)
│   └── 0.5秒tickのカウントダウン処理
├── Queue Worker × 2         … default キュー (~200MB)
│   └── 通知・非同期処理
└── Supervisor               … 上記プロセスの管理・自動再起動

メモリ配分（保守的見積もり — pm.max_children=80 推奨）:
  PHP-FPM: ~4.8GB (80 × 60MB ピーク時)
  Reverb:  ~0.5GB
  Queue:   ~0.7GB (7 workers × 100MB)
  Nginx:   ~0.2GB
  OS:      ~1.0GB
  予備:    ~0.8GB ← OOM Killer 回避のバッファ
  合計:    ~8.0GB

⚠️ 注意: PHP-FPM 1プロセスあたり50MBは平均値。画像アップロードや
大きなレスポンス生成時は80〜120MBに膨らむケースがある。
pm.max_children=100 ではピーク時に OOM Killer が発動するリスクあり。

推奨設定:
  pm.max_children = 80  （安全マージン確保）
  pm.max_children = 100 （負荷テストで OOM が発生しないことを確認した場合のみ）
```


## 4. インフラ構成の現状と課題

### 4-1. 現在の本番構成

| コンポーネント | 現在のスペック | max_connections / 容量 |
|--------------|-------------|----------------------|
| EC2 | t3.medium (2vCPU / 4GB) | PHP-FPM 50ワーカー |
| RDS | db.t3.micro (1vCPU / 1GB) | **max_connections = 20** |
| ElastiCache | cache.t3.small × 1 (1.5GB) | シングルスレッド、3ワークロード共有 |

### 4-2. 500人同時接続時の負荷推定

#### データベース接続数

```
500人 × 平均2接続/人 = 1,000接続必要
db.t3.micro の max_connections = 20
→ 98%の接続が拒否される（致命的）
```

#### Redis ops/sec

| ワークロード | 推定ops/sec（500人時） |
|-------------|---------------------|
| セッション読み書き | 83/sec |
| カウントダウンキャッシュ | 3,000/sec |
| キュージョブ処理 | 40/sec |
| **合計** | **3,123+ ops/sec** |

Redis はシングルスレッドで、シリアライズ込みで1操作5〜10ms。cache.t3.small 1台では遅延が蓄積してカウントダウンが遅れる。

#### WebSocket ブロードキャスト

```
CountdownTick: 0.5秒 × 6レーン = 12イベント/秒
500人 subscribed: 12 × 500 = 6,000メッセージ/秒
+ BidderUpdated/PriceUpdated 等: 追加 1,000〜2,000メッセージ/秒
合計: 最大 8,000メッセージ/秒
```

#### APIポーリング（WebSocket切断時のフォールバック）

```
500人 × 3秒ポーリング = 166リクエスト/秒
166 × 4クエリ/リクエスト（getLiveState） = 664クエリ/秒
→ db.t3.micro の安全処理能力（100-150クエリ/秒）を大幅に超過
```

## 5. バックエンドのボトルネック（実コード調査結果）

### 5-1. CountdownService::tick()

**ファイル**: `app/Services/CountdownService.php`

0.5秒ごと × 6レーン = 12回/秒 の tick 処理。

| 処理 | 内容 | 改善案 |
|------|------|-------|
| `Cache::get()` | countdown状態読み取り | Redis化済み（本番.envで`CACHE_STORE=redis`必須） |
| `BidParticipant::count()` | アクティブ入札者数 | Redisカウンターでキャッシュ推奨 |
| `broadcast(CountdownTick)` | ShouldBroadcastNow（同期） | クライアント側カウントダウン補間で頻度削減 |
| `Cache::put()` | countdown状態書き込み | Redis化済み |
| `$item->update()` | 価格更新（ロックなし） | **lockForUpdate() 必須**（後述 §6-1） |

**500人時の影響**:
- tick 12回/秒 × 500クライアント = 6,000ブロードキャスト/秒
- 各tickでDBクエリ3〜5回 = 36〜60クエリ/秒（tick処理だけで）

### 5-2. BidService::getLiveState()（APIポーリング時）

**ファイル**: `app/Services/BidService.php`

**N+1問題は解消済み**: GROUP BY + whereIn() で一括取得している（良い実装）。

ただし500人同時ポーリング時:
```
500人 × 2回/秒（WebSocket切断時） × 4クエリ = 4,000クエリ/秒
```

**改善案**: `getLiveState()` 結果を2秒TTLでRedisキャッシュ

```php
$cacheKey = "auction:{$auction->id}:live_state:{$userId}";
return Cache::remember($cacheKey, 2, function() use ($auction, $userId) {
    return $this->buildLiveState($auction, $userId);
});
```

### 5-3. Admin/LiveController（N+1問題あり）

**ファイル**: `app/Http/Controllers/Admin/LiveController.php`

```php
// 問題箇所（63-97行付近）: オークションごとに個別クエリ
$auctions = $query->get()->map(function ($auction) {
    $lanes = Lane::where('auction_id', $auction->id)->get();    // N+1
    $items = Item::where('auction_id', $auction->id);            // N+1
    $assignedItems = DB::table('lane_items')->join(...)->count(); // N+1
});
```

**影響**: 5オークション × 5クエリ = 25クエリ/コール。管理者10人が3秒ポーリング → 83クエリ/秒

**修正**: Eager loading に変更
```php
$auctions = $query->with(['lanes', 'items'])->get()->map(...);
```

### 5-4. ProcessAuctionCountdownJob

**ファイル**: `app/Jobs/ProcessAuctionCountdownJob.php`

| 問題 | 内容 | 影響 |
|------|------|------|
| ハートビートTTL | `HEARTBEAT_TTL = 14400`（4時間） | ジョブ死亡後4時間検知不能 |
| ジェネレーション番号 | 非アトミック read-increment-write | 複数管理者のresume操作で重複ジョブ |
| 単一ワーカー | Docker構成で1コンテナのみ | 冗長性なし |

### 5-5. お気に入り通知の同期処理

**ファイル**: `app/Actions/Line/NotifyFavoriteApproachingAction.php`

## 6. 競合状態・レースコンディション（致命的）

### 6-1. Item.current_price のロストアップデート — CRITICAL

**ファイル**: `app/Services/CountdownService.php`（399-407行付近）

```php
$oldPrice  = $item->current_price;           // ロックなしで読み取り
$increment = $auction->calculatePriceIncrement($oldPrice);
$newPrice  = $oldPrice + $increment;
$item->update(['current_price' => $newPrice]); // ロックなしで書き込み
```

**500人時のシナリオ**:
- 複数スレッドが同時に同じ `current_price` を読み取り
- 同じ増分値を計算して書き込み → 1回分の増分が消失
- **推定損失率: 価格増分の20〜30%**

**修正**:
```php
DB::transaction(function () use ($item, $auction) {
    $freshItem = Item::lockForUpdate()->find($item->id);
    $increment = $auction->calculatePriceIncrement($freshItem->current_price);
    $freshItem->update(['current_price' => $freshItem->current_price + $increment]);
});
```

### 6-2. BidParticipant::participate() の非アトミック操作 — CRITICAL

**ファイル**: `app/Models/BidParticipant.php`（100-117行付近）

`updateOrCreate()` は check-then-act パターンで、500人同時実行時に:
- 25〜50件のユニーク制約違反エラー
- `activated_at` タイムスタンプの破損

**修正**: `INSERT ... ON DUPLICATE KEY UPDATE` またはロック付き手動UPSERT

### 6-3. BidLimitPrice のオーファンレコード — CRITICAL

**ファイル**: `app/Models/BidLimitPrice.php`（63-78行付近）、`app/Services/CountdownService.php`（559-620行付近）

`markAsTriggered()` の楽観ロックで、同一 `limit_price` を持つ500人中1人だけ成功。残り499人のレコードが孤児化し、以後リミット設定不能に。

**修正**: `markAsTriggered()` 失敗時に is_triggered の状態を再確認し、既にトリガー済みなら正常処理を継続

### 6-4. MoveToNextItemAction のキャッシュ競合 — CRITICAL

**ファイル**: `app/Actions/Auction/MoveToNextItemAction.php`（69-73行付近）

`DB::commit()` 後、カウントダウンキャッシュ書き込み前に `LaneItemChanged` をブロードキャスト。500クライアントがキャッシュミスの状態でカウントダウン取得を試みる。

**修正**: ブロードキャストをキャッシュ書き込み後に移動

### 6-5. ResumeAuctionAction の非アトミック操作 — CRITICAL

**ファイル**: `app/Actions/Auction/ResumeAuctionAction.php`（48-50行付近）

```php
$newGen = ((int) Cache::get($genKey, 0)) + 1;  // 非アトミック
Cache::put($genKey, $newGen, ...);
```

**修正**: `Cache::increment($genKey)` に変更

### 6-6. JoinBidAction のトランザクション外処理 — HIGH

**ファイル**: `app/Actions/Bid/JoinBidAction.php`（69-107行付近）

`$activeBidderCount` をトランザクション内で取得後、`DB::commit()` の後に `handleImmediatePriceIncrement()` を実行。コミットと価格増分の間に他スレッドが割り込む。

### 6-7. LeaveBidAction の入札者数チェック競合 — HIGH

**ファイル**: `app/Actions/Bid/LeaveBidAction.php`（30-52行付近）

最後の入札者チェック（`activeBidders === 1`）とデアクティベートの間に新しい入札者が参加すると、アイテムが入札者なしの状態になる可能性。

## 13. 障害時のフェイルオーバー・復旧手順

### 自動フェイルオーバー

| 障害 | 自動復旧 | RTO | 備考 |
|------|---------|-----|------|
| RDS Primary 障害 | Multi-AZ 自動フェイルオーバー | 1〜2分 | **オークションモード時のみ**（通常モードはSingle-AZ） |
| ElastiCache Primary 障害 | Multi-AZ 自動フェイルオーバー | 数秒〜1分 | **オークションモード時のみ**（通常モードはレプリカなし） |
| EC2 障害（プロセスレベル） | Supervisor autorestart | 5秒以内 | 両モード共通（Queue Worker, Reverb） |
| **EC2 障害（インスタンスレベル）** | **手動復旧（下記手順）** | **15〜30分** | **単一障害点 — 500人接続中は全断** |

> **通常モード時の注意**: RDS / ElastiCache ともにSingle構成のため、
> ノード障害時はAWS側の自動復旧（数分〜十数分）に依存する。
> 管理業務のみの時間帯であるため、許容範囲と判断。

### EC2 単一障害点（SPOF）のリスクと対策

**現在の構成（EC2 1台）では、インスタンス障害時にサービスが全断する。**
オークション中に発生した場合、500人全員が切断され、カウントダウンが停止する。

#### リスク評価

| シナリオ | 発生確率 | 影響 | 許容判断 |
|---------|---------|------|---------|
| 通常モード時のEC2障害 | 低 | 管理者のみ影響 | **許容** |
| オークション中のEC2障害 | 極低（月1回以下） | **500人全断・カウントダウン停止** | **条件付き許容**（下記対策前提） |

> AWS の EC2 SLA は 99.99%（月間ダウンタイム約4.3分）。
> オークション時間が月合計10時間程度なら、オークション中にEC2障害が発生する確率は年間1回未満。
> **ただし発生時の影響が甚大なため、復旧手順の整備とAMIの事前準備が必須。**

#### EC2 障害時の復旧手順（RTO: 15〜30分）

```
1. 障害検知（ALBヘルスチェック失敗 → SNS通知）        ... 0〜2分
2. 管理者が通知を受信し、AWSコンソールにアクセス       ... 2〜5分
3. 最新AMIから新EC2インスタンスを起動                  ... 3〜5分
   aws ec2 run-instances \
     --image-id ami-xxxxxxxxx \
     --instance-type t3.large \
     --subnet-id subnet-xxxxxxxxx \
     --security-group-ids sg-xxxxxxxxx \
     --iam-instance-profile Name=auction-ec2-role
4. ALBターゲットグループに新EC2を登録                  ... 1分
5. ヘルスチェック通過を待機                            ... 2〜5分
6. オークション再開操作（管理画面から一時停止→再開）     ... 1〜2分
                                               合計: 約15〜30分
```

#### 必須の事前準備

| 準備項目 | 内容 | 頻度 |
|---------|------|------|
| **AMI作成** | デプロイ後に最新AMIを作成（Nginx/PHP/Reverb/Supervisor設定含む） | **毎デプロイ後** |
| **起動テンプレート** | AMI + インスタンスタイプ + SG + IAMロールをテンプレート化 | 初回 + AMI更新時 |
| **復旧手順書** | 上記手順をRunbookとして管理者に共有 | 初回 + 更新時 |
| **復旧訓練** | オークション前にAMIからの起動テストを実施 | **各オークション前** |

#### 将来的な冗長化（1,000人以上対応時）

EC2を2台以上にスケールアウトする場合、ALBが自動的に障害EC2を切り離すため、
EC2のSPOF問題は解消される。§11の段階的スケーリングガイドを参照。

### 運用前提

- オークション開催: **月2回**
- **開催2日前〜開催2日後**（約5日間）: 500人対応の増強構成
- **それ以外**（約20日間）: 最小構成で低コスト運用（管理画面・商品登録等のみ）
- **スケーリングは完全自動化** — オークション作成時にスケジュールが自動登録される

### スケーリング時のダウンタイム

| コンポーネント | 操作 | ダウンタイム | 実行タイミング |
|--------------|------|------------|-------------|
| EC2 | 停止 → リサイズ → 起動 | **2〜5分**（サービス全断） | AM 3:00（深夜） |
| RDS | インスタンスクラス変更 + Multi-AZ切替 | **5〜15分**（DB接続断） | AM 3:00（深夜） |
| ElastiCache | ノードタイプ変更 | **数秒〜数分**（短時間の接続断） | AM 3:00（深夜） |

> **合計ダウンタイム**: 約10〜25分（AM 3:00 に自動実行のため影響は極小）。
> RDS の Multi-AZ 有効化は内部的にフェイルオーバーが発生し、数秒の接続断を伴う。
> **オークション中にスケーリングが実行されることはない**（開催2日前/2日後のAM3:00固定）。

### なぜこの構成がベストプラクティスか

| 要件 | ❌ 旧設計の問題 | ✅ 新設計の解決策 |
|------|---------------|----------------|
| EC2上の設定切り替え | Lambda→SSH（鍵管理、セキュリティリスク） | **SSM Run Command**（IAMロール認証、監査ログ付き） |
| 途中失敗時の復旧 | ロールバックなし（半端な状態で放置） | **Step Functions の Catch/Retry**（自動リトライ+ロールバック分岐） |
| RDS変更待ち | `aws rds wait` がLambda 15分タイムアウトに収まらない可能性 | **Step Functions の Wait + Polling**（タイムアウトなし） |
| 完了確認 | なし | **SNS通知**（成功/失敗をメール or Slackで受信） |
| スケジュール忘れ | カレンダーリマインダー頼み | **AuctionObserver が自動登録**（オークション作成時に確定） |
| スケールダウン忘れ | 人的ミスリスク | **EventBridge Scheduler が自動実行**（忘れようがない） |
| ヘルスチェック | 手動 curl | **Step Functions 内で自動チェック**（失敗なら通知） |

#### 主要コンポーネントの概要（実装ガイドからの抜粋）

**AuctionObserver**: オークション作成/更新/削除時にEventBridge Scheduleを自動登録・削除。

**ScheduleInfraScalingAction**: EventBridge Scheduler API を呼び出し、開催2日前(scale-up)/2日後(scale-down)のワンショットスケジュールを作成。実行後に自動削除。

**Step Functions**: RDS → ElastiCache → EC2 → SSM設定切り替え → ヘルスチェックの順で実行。各ステップにRetry/Catch/Rollback分岐を実装。

**Lambda関数 9本**:

| 関数名 | タイムアウト | 役割 |
|--------|------------|------|
| auction-scale-ec2 | 300秒 | EC2 停止→リサイズ→起動 |
| auction-check-ec2-status | 30秒 | EC2 running + ステータスチェック確認 |
| auction-scale-rds | 30秒 | RDS クラス変更 + パラメータグループ切替 |
| auction-check-rds-status | 30秒 | RDS available 確認 |
| auction-scale-elasticache | 60秒 | ElastiCache ノードタイプ変更 + レプリカ調整 |
| auction-check-elasticache-status | 30秒 | ElastiCache available 確認 |
| auction-switch-config | 180秒 | SSM Run Command で PHP-FPM/Supervisor 設定切替 |
| auction-health-check | 30秒 | ALB経由 /api/health チェック |
| auction-pre-scaledown-check | 60秒 | 未精算/残ジョブチェック |

> **重要**: `auction-scale-ec2` のタイムアウトはデフォルト3秒では不足。**300秒**に設定すること。

```

□ 8. config/services.php に ARN 設定追加
```

```bash
# Step Functions を直接起動

  --state-machine-arn arn:aws:states:ap-northeast-1:ACCOUNT:stateMachine:AuctionInfraScaling \
  --input '{"action":"scale-up","auction_id":0}'
```
