## 6. CPU 負荷の原因分析

### 6-1. 観察された現象との整合

**現象**: 「全ユーザー同時にネットワークエラートースト、カウントダウンは正常動作継続」

これは以下の経路で説明できる:

```
[商品切替の瞬間 = T+4, T+8, T+14, T+18, T+26 など]
   ↓
4 vCPU 上で複数の処理が同時集中
   ↓
load avg スパイク (idle 0%、CPU取り合い発生)
   ↓
Reverb (PHP CLI 単一プロセス) も CPU 取り合いに巻き込まれる
   ↓
Reverb の broadcast 配信が瞬間遅延 (数百ms 〜 数秒)
   ↓
全クライアントの laravel-echo が「接続失われた」と検知
   ↓
全ユーザーに「ネットワークエラー」トースト表示
   ↓ (Reverb プロセス自体は生きてるので)
WebSocket は自動再接続、カウントダウンは正常継続
```

### 6-2. CPU を食っていた処理 (実コードから推定)

#### A. 商品切替時の集中処理 (主犯候補1)

[ProcessAuctionCountdownJob.php:179](../../app/Jobs/ProcessAuctionCountdownJob.php) の startCountdown + [SetBidLimitAction::activatePendingBidLimits](../../app/Actions/Bid/SetBidLimitAction.php):

商品切替の瞬間に走る処理:

```
LaneItemChanged broadcast (全クライアントへ配信)
   ↓
activatePendingBidLimits 実行
  - items 行ロック取得
  - 該当 item の事前指値を一括 SELECT (今回最大9件/商品)
  - BidParticipant::participate 一括実行
  - BidderUpdated broadcast 1回
   ↓
指値2件以上なら adjustPriceByBidLimits 発火
  - 価格自動調整 (proxy-bid 仕様)
  - PriceUpdated broadcast
  - BidLimitsBatchTriggered broadcast
   ↓
お気に入り通知 dispatch (3商品先のお気に入りユーザー)
  - 619件の中から該当ユーザー特定
  - Mail + LINE Job を notify queue へ
```

これが **2レーンで独立に発火** するので、タイミングが重なると 2倍負荷。

#### B. 入札集中時の bid 処理並列実行 (主犯候補2)

[JoinBidAction.php](../../app/Actions/Bid/JoinBidAction.php) の入札処理:

```
1回の bid ホットパス:
  - Redis Cache::lock 取得 (~1-5ms)
  - items.lockForUpdate (~10ms)
  - DB select + count + insert (~20-30ms)
  - broadcast(BidderUpdated) (~5ms)
  - 合計 ~50-80ms / リクエスト
```

200人想定 × throttle (1秒4回) × 商品切替直後の集中:
- 瞬間最大 200リクエスト同時着信の可能性
- php-fpm 100 worker が一気に active
- **1コアあたり 25 worker** が CPU を奪い合う
- 各 worker の処理時間が 50ms → 200ms 以上に伸びる
- これが他の処理 (Reverb broadcast) も巻き込んで遅延

#### C. Reverb broadcast の発火集中 (主犯候補3)

[CountdownService.php](../../app/Services/CountdownService.php) の tick:

```
0.5秒粒度の tick で:
  - 2レーン × CountdownTick (1秒粒度に間引き済み)
  - 価格上昇時 PriceUpdated
  - 入札参加/離脱 BidderUpdated
  - 指値発動 BidLimitsBatchTriggered
  - 商品切替 LaneItemChanged
```

最大 fan-out 計算:
- 60接続 × 5種類のイベント × 1秒 = 300 broadcast/秒
- 商品切替の瞬間は更に 2-3倍

Reverb は単一 PHP プロセスなので、php-fpm が CPU 取り合いになると **Reverb 自身が遅延**。

### 6-3. なぜ「商品切替の瞬間」に集中するか

bidding tick (0.5秒) → freeze (5-10秒) → 落札確定 → 次商品 bidding 開始 のサイクルで:

```
[次商品 bidding 開始 = T 秒]
   ↓
T+0.0: LaneItemChanged 配信 → 全クライアント受信
T+0.0-0.5: フロントが UI 更新
T+0.5-1.0: 全員が入札ボタンを見つけてタップ集中
T+0.5-1.5: 200リクエストが server に着信
   ↓ ここで CPU バースト発生
T+1.5-2.5: 処理完了、Reverb broadcast 完了
T+2.5以降: 通常 bidding tick (静か)
```

→ **「商品切替直後の 1-2秒間」に処理が集中**して CPU が振り切れる

### 6-4. インフラエンジニアの指摘 (max_children=100 が多すぎ) との整合性

```
4 vCPU + 100 max_children の問題:
  100 worker が同時 active になると 1コアあたり 25 worker
  → CPU タイムスライス取り合い (context switch 多発)
  → 1リクエストの処理時間が 2-3倍に
  → さらに次のリクエストが詰まる悪循環
  → load avg がスパイク (= 実行待ち worker 数)
```

これは **「CPUバウンドな処理を多数並列化すると性能が下がる」典型例**。
解消策は「CPU性能を上げる」or「並列度を下げる」の2方向。

### 6-5. notify queue は CPU 食ってない (除外できる候補)

| 観点 | 結果 |
| --- | --- |
| notify queue 深さ | 開催中 常時 0 |
| お気に入り通知 619件分のジョブ | 即時消化されていた |
| → notify worker (numprocs=2) は CPU を食っていない |

**お気に入り通知 fan-out は CPU バーストの直接原因ではない**。

### 6-6. 動画変換 (media queue) は影響なし

| 観点 | 結果 |
| --- | --- |
| media queue 深さ | 開催中 常時 0 |
| 開催中の動画変換 | 走っていない |
| → media worker は CPU を食っていない |

## 7. 結論: CPU 負荷の主犯ランキング

| 順 | 原因 | 寄与度 | 根拠 |
| --- | --- | --- | --- |
| 🥇 | **入札タップ集中時の php-fpm worker 大量並列化** | **大** | 商品切替直後にバースト集中、4コアでの取り合い |
| 🥈 | **商品切替時の broadcast + activatePendingBidLimits** | 中 | LaneItemChanged の瞬間に処理重複 |
| 🥉 | **2レーン独立切替の重なり** | 中 | タイミングによっては2レーン同時発火 |
| 4 | bidding tick の Reverb 配信集中 | 小 | 既に 1秒粒度に間引き済 |
| 除外 | notify queue / media queue | なし | キュー深さ 0 で確認 |

## 8. 今後の対策

### 8-1. インフラエンジニア提案 (実施予定)

1. ✅ **EC2: t3.xlarge → c6i.2xlarge (8 vCPU)** ← 根本解決
2. ✅ **max_children: 100 → 64** (8コアに見合う適正値)
3. ✅ **AMI バックアップ取得** (ロールバック可能)

### 8-2. フロント側 (並行実施推奨)

4. ⏳ **laravel-echo のエラー検知時に「3秒以内の瞬間切断ではトーストを出さない」**
   - これだけで「ユーザー目線でのエラー表示ゼロ」を達成可能
   - 根本対策と組み合わせれば実質エラー撲滅

### 8-3. 監視強化 (運用)

5. **active worker 数の常時監視**
   ```bash
   watch -n 5 'ps aux | grep "php-fpm: pool" | grep -v grep | wc -l'
   ```
6. **load avg 1分が 5.0 超えたら CloudWatch Alarm**

### 8-4. 将来 (300人以上を目指す場合)

7. Reverb の専用コア固定 (cpuset) or scaling 有効化
8. お気に入り通知の bulk 化 (現状は1ユーザーごと dispatch)
9. 商品切替時の broadcast 集約 (B2の更なる拡張)
