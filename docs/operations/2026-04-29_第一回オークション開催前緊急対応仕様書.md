## 1. 前日通知ジョブ（SendAuctionPreviewJob）の確認

### 1.1 背景

`SendAuctionPreviewJob` は `bootstrap/app.php` で **毎日 18:00** に dispatch される。`event_date = 翌日` の `status=scheduled` のオークションを対象に、全参加者・全出品者へメール送信を行う。同 Job は `default` キュー（timeout=300 秒）で動作するため、152 名 + 出品者 への SMTP 送信が 300 秒に収まらないと timeout で失敗する可能性がある。本日 18:00 の実行が成功しているか即時確認する必要がある。

### 1.2 完了条件

1. `failed_jobs` テーブルに `SendAuctionPreviewJob` のエントリがない。
2. `storage/logs/laravel-2026-04-28.log` に `Auction preview notifications sent` が 1 行以上、`auction_id` と件数が記録されている。
3. 件数が「対象オークションの参加者数 + 出品者数」とほぼ一致する（差分はメール OFF 設定のユーザー）。
4. LINE 通知の `SendLineNotificationJob` も failed_jobs にない。

### 1.3 作業手順

```bash
ssh ec2-user@<本番ホスト>
cd /var/www/auction

# (a) failed_jobs を確認
php artisan queue:failed | head -50
# 期待: No failed jobs found.（または無関係なジョブのみ）

# (b) 18:00 実行の証跡を確認
grep "Auction preview notifications sent" storage/logs/laravel-2026-04-28.log | tail -5
# 例: [2026-04-28 18:00:42] production.INFO: Auction preview notifications sent {"auction_id":1,"email_count":151,"participant_count":152,"seller_count":N}

# (c) 件数が想定と一致するか
php artisan tinker --execute="
\$a = \App\Models\Auction::where('status','scheduled')->whereDate('event_date', '2026-04-29')->first();
echo 'auction_id='.\$a->id.PHP_EOL;
echo 'participants='.\App\Models\User::whereHas('roles', fn(\$q)=>\$q->where('name','participant'))->where('is_active', true)->count().PHP_EOL;
echo 'sellers='.\App\Models\User::whereHas('roles', fn(\$q)=>\$q->where('name','seller'))->where('is_active', true)->count().PHP_EOL;
"
```

### 1.4 想定外パターンの対応

#### (i) failed_jobs にエントリがある

```bash
# 失敗したジョブを再実行（ID は queue:failed 出力の左端 UUID）
php artisan queue:retry <UUID>
# あるいは全失敗ジョブを再投入
php artisan queue:retry all
```

#### (ii) 18:00 のログが出力されていない（=スケジューラーが走っていない）

```bash
# crontab の確認
sudo crontab -l -u ec2-user
# 期待行: * * * * * cd /var/www/auction && php artisan schedule:run >> /dev/null 2>&1

# 直近の schedule:run 動作確認
sudo journalctl -u crond --since "30 minutes ago" | grep schedule:run

# 手動で投入し直す
php artisan tinker --execute="dispatch(new \App\Jobs\SendAuctionPreviewJob);"
sleep 10
grep "Auction preview notifications sent" storage/logs/laravel-2026-04-28.log | tail -1
```

#### (iii) 送信件数が想定より少ない

ユーザーの `notification_settings.email_auction_start` が `false` のケースを除いた数になる。`participant_count - email_count = OFF にしている人数` なので、極端に乖離していなければ正常。極端に少なければ SES のクレジット枯渇・サンドボックス未解除を疑う。

```bash
# SES 送信統計
aws ses get-send-statistics --region ap-northeast-1 \
  --query "SendDataPoints[-3:]"
# Bounces / Complaints が突発的に増えていないか確認
```

### 1.5 ロールバック

不要（送信済みメールは取り消せない）。再送が必要な場合は管理画面の「お知らせ送信」機能から個別配信。

## 2. カウントダウン監視の高頻度化

### 2.1 背景

`MonitorAuctionJobs` は `auctions:monitor-jobs` を **scheduler の everyMinute()** で起動するため、最大 1 分間「heartbeat 検知 → 復旧」が遅延する。さらに `HEARTBEAT_STALE_SECONDS = 30` のため、ジョブ死亡から最悪 **約 90 秒**カウントダウンが止まる。152 名がリアルタイムに体験するオークションでは到底許容できないため、以下を実施する。

### 2.2 完了条件

1. `MonitorAuctionJobs::HEARTBEAT_STALE_SECONDS` を `30` → `15` に変更しデプロイ済み。
2. `auctions:monitor-jobs` が **15 秒間隔**で実行される。
3. 死亡シミュレーション（ProcessAuctionCountdownJob を強制 kill）から **30 秒以内**に再ディスパッチされる。

### 2.3 作業手順

#### 2.3.1 コード変更

`src/app/Console/Commands/MonitorAuctionJobs.php`：

```php
private const HEARTBEAT_STALE_SECONDS = 15;   // 30 → 15
```

> Heartbeat は `ProcessAuctionCountdownJob` 内で 10 ティック（= 5 秒）ごとに更新するため、15 秒は false-positive 余裕がある。

#### 2.3.2 15 秒間隔の常駐ループを supervisor に追加

`/etc/supervisord.d/auction.ini` に以下を追記：

```ini
[program:auction-monitor-jobs]
command=/bin/bash -c 'while true; do php /var/www/auction/artisan auctions:monitor-jobs >> /var/www/auction/storage/logs/monitor-jobs.log 2>&1; sleep 15; done'
user=ec2-user
umask=0002
autostart=true
autorestart=true
startretries=3
stopwaitsecs=30
stdout_logfile=/var/log/supervisor/auction-monitor-jobs.log
stderr_logfile=/var/log/supervisor/auction-monitor-jobs.err.log
```

> Laravel scheduler の `everyFifteenSeconds()` を使う案もあるが、`schedule:run` プロセスが 1 分間ホールドされる挙動になり、スケジューラ全体の挙動が変わるため、本仕様書では既存スケジューラに触らず supervisor 側に常駐ループを置く方式を採用する。

合わせて、`bootstrap/app.php` に書かれている既存の `everyMinute()` の登録は**残す**（多重発動しても再ディスパッチは世代番号で冪等に動くため害はなく、保険になる）。

#### 2.3.3 反映

```bash
ssh ec2-user@<本番ホスト>
cd /var/www/auction
git pull origin main          # HEARTBEAT_STALE_SECONDS の変更を取得
php artisan config:cache

sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status auction-monitor-jobs   # RUNNING を確認
```

#### 2.3.4 動作確認（リハーサル / オークション開始前）

> ⚠️ 本テストは ライブオークション中ではなく、**テスト用オークションを 1 件 live にして**実施すること。本番の参加者向けデータには触れない。

```bash
# (a) 動作中の countdown ワーカープロセスを 1 つ kill
sudo supervisorctl status | grep countdown
ps -ef | grep ProcessAuctionCountdownJob | grep -v grep
sudo kill -9 <PID>

# (b) 30 秒以内に再ディスパッチログが出ることを確認
tail -f /var/www/auction/storage/logs/monitor-jobs.log
# 期待: "MonitorAuctionJobs: Re-dispatched countdown job for auction X"
```

### 2.4 ロールバック

```bash
sudo supervisorctl stop auction-monitor-jobs
# auction.ini から該当ブロックを削除
sudo supervisorctl reread
sudo supervisorctl update

# HEARTBEAT_STALE_SECONDS は git revert
```

### 3.2 監視窓レイアウト

主担当は tmux などで以下 6 ペインを開いておく。

| Pane | コマンド | 目的 |
| --- | --- | --- |
| 1 | `sudo watch -n 2 'supervisorctl status'` | 全 worker の生存確認 |
| 2 | `tail -F /var/www/auction/storage/logs/laravel-2026-04-29.log` | アプリログのリアルタイム監視 |
| 3 | `tail -F /var/www/auction/storage/logs/monitor-jobs.log` | 監視ジョブの再ディスパッチ検知 |
| 4 | `tail -F /var/log/supervisor/auction-queue-countdown*.log` | カウントダウン worker の生ログ |
| 5 | `tail -F /var/log/nginx/error.log` | 502 / 504 / FastCGI バッファ系の検知 |
| 6 | `top -p $(pgrep -d, -f 'reverb|countdown')` | Reverb / countdown の CPU・メモリ |

### 3.3 自動アラート（既存）の疎通確認

開催 1 時間前までに、CloudWatch アラーム → Slack/SMS が**実際に飛ぶことを必ず1回テスト**する。

```bash
# テスト用に閾値を一時的に下げて発火させ、Slack/SMS 受信を確認 → 元に戻す
# （CloudWatch コンソールで「テスト通知」機能を使うのが最速）
```

CloudWatch メトリクスの観点：

| メトリクス | 警告閾値 | アクション |
| --- | --- | --- |
| RDS `DatabaseConnections` | > 100（max 150 の 2/3） | 即時調査 / queue worker 数削減検討 |
| RDS `CPUUtilization` | > 80% | スロークエリ確認 |
| ElastiCache `EngineCPUUtilization` | > 80% | フェイルオーバー準備 |
| EC2 `CPUUtilization` | > 85% | PHP-FPM プロセス数確認 |
| ALB `HTTPCode_Target_5XX_Count` | 1 分で > 10 | アプリエラー調査 |
| カスタム: `failed_jobs` 件数 | > 0 | 該当 Job 種別調査 |

### 3.4 緊急対応プレイブック

#### 症状 A: 「カウントダウンが3秒のまま固まった」報告が来た

```bash
# 1) 該当オークション ID を把握
php artisan tinker --execute="echo \App\Models\Auction::where('status','live')->pluck('id');"

# 2) 各レーンの状態キャッシュを確認（null なら異常）
php artisan tinker --execute="
foreach (\App\Models\Lane::whereHas('auction', fn(\$q)=>\$q->where('status','live'))->get() as \$l) {
    echo \"lane={\$l->id} status={\$l->status} cache=\" . (Cache::get('countdown:lane:'.\$l->id) ? 'OK' : 'NULL') . PHP_EOL;
}
"

# 3) failed_jobs に countdown が落ちていないか
php artisan queue:failed | grep -i countdown

# 4) 強制再ディスパッチ（auction_id を指定）
php artisan tinker --execute="
\$id = <auction_id>;
Cache::forget(\"countdown_job_running:auction:{\$id}\");
Cache::forget(\"countdown_job_heartbeat:auction:{\$id}\");
Cache::forget(\"countdown_job_lock:auction:{\$id}\");
Cache::increment(\App\Jobs\ProcessAuctionCountdownJob::generationKey(\$id));
\App\Jobs\ProcessAuctionCountdownJob::dispatch(\$id);
echo 'redispatched';
"

# 5) ログ書き込みエラーが原因なら storage/logs の所有を再確認
sudo ls -l /var/www/auction/storage/logs/laravel-2026-04-29.log
# 違っていれば
sudo chown ec2-user:ec2-user /var/www/auction/storage/logs/laravel-2026-04-29.log
sudo chmod 0664 /var/www/auction/storage/logs/laravel-2026-04-29.log
```

#### 症状 B: WebSocket が切れる / 入札ボタンが反応しない

```bash
sudo supervisorctl status auction-reverb
sudo supervisorctl restart auction-reverb
# クライアントは Echo の自動再接続で復旧
```

#### 症状 C: 5xx 多発 / RDS 接続枯渇

```bash
# 接続数をリアルタイム確認
mysql -h <RDS endpoint> -u admin -p -e "SHOW STATUS LIKE 'Threads_connected';"

# 一時的に PHP-FPM の max_children を下げる（接続数を抑える）
sudo sed -i 's/pm.max_children = 80/pm.max_children = 60/' /etc/php-fpm.d/www.conf
sudo systemctl reload php-fpm
```

#### 症状 D: queue worker が落ちている

```bash
sudo supervisorctl status
# FATAL や STOPPED があれば
sudo supervisorctl restart auction-queue-countdown:*
sudo supervisorctl restart auction-queue-default:*
```
