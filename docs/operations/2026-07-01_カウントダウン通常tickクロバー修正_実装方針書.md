## 0. 一行サマリ

DEV-2026-007（Option A）は tick の **確定判定** だけを `bid_inflight` ロック下に置いたが、**通常 bidding tick の「カウント減算 → `Cache::put`」という read-modify-write は無保護**のまま残った。ラウンド終了間際に滑り込み入札が `bid_inflight` 下で書いた freeze を、この無保護な書き戻しが**古い bidding state で上書き（クロバー）**し、次 tick が phase=bidding・残り0 を見て**新ラウンド（10秒）を飛ばして即落札**する。tick の bidding ブランチの read-modify-write も同じ `bid_inflight` 下に入れて直列化する。

---

## 1. 事象（2026-06-19 本番・実データ）

同一オークションで **3件** 発生。いずれも「価格が上がった直後、freeze の2秒だけで、新しい入札ラウンド（10秒）を経ずに落札」。

| item | lane | 発火（ラウンド残り時間での入札） | 経路 | 最後の値上げ→落札 | 落札 |
| --- | --- | --- | --- | --- | --- |
| 1875 | 77 | 約1秒（11:21:00） | 手動 `protectedUsers=[]` | 2秒・新ラウンド欠落 | 864 / 180円 |
| 1843 | 80 | 約2秒（11:27:44） | 手動 `protectedUsers=[]` | 3秒・新ラウンド欠落 | 819 / 110円 |
| 1936 | 77 | 約1秒（12:13:15） | 手動（指値1098併存） | 1秒・新ラウンド欠落 | 1098 / 250円（**undersell**） |

### 1.1 決定的ログ（item 1843／最も素直な例）

```
11:27:36  Pre-bid ended, bidding started: lane 80, item 1843, countdown=10s   ← 10秒ラウンド（自然終了 11:27:46）
11:27:44  handlePriceIncrement: item=1843, 100→110, activeCount=2, protectedUsers=[], effectiveHolder=819  ← 残り約2秒で滑り込み入札
11:27:44  Auto-left users on price increment: item=1843, left=821, holder=819
11:27:45  Freeze countdown started: lane 80, 2s
11:27:47  Item 1843 sold        ← "Freeze ended, bid countdown started ... item 1843" が無いまま即落札
```

直前の全ラウンドには必ずあった `Freeze ended, bid countdown started ... item 1843` が、**最後だけ欠落**している点が動かぬ証拠。freeze は書かれたのに、freeze→bidding の遷移（新ラウンド生成）が起きていない＝**freeze が消されている**。

### 1.2 3件に共通する発火条件

- **bidding ラウンドの残りわずか（≈1〜2秒）で滑り込み入札**が着弾し、`handleImmediatePriceIncrement` が価格上昇＋ freeze を書く。
- その入札の直後（ほぼ同時刻）に、**当該ラウンドの終了間際の通常 tick**が動いている。
- 指値の有無は無関係（1936 は指値併存だが致命傷の最後の増額は手動入札由来）。デプロイ状態も無関係（Option A は配備済みを L322/L325 で確認済み）。

### 1.3 なぜ「ギリギリ入札」全部ではなく稀にしか起きないのか

同じ「残りわずかで入札」でも、**次の3条件が同時に揃った時だけ**即落札に至る。6/19 に多数あったギリギリ入札のうち3件だけが全条件を踏んだ。

1. **入札がラウンドの最後の約1秒（＝最後の1 tick間隔）に着弾**。もっと手前で潰されても `phase=bidding, 残りN秒` として**カウントが続くだけ**で即落札にならない（誰かが追随すれば競り継続）。即落札は「クロバー後に残り≒0」の時のみ。
2. **その入札で相手が auto-left され active=1 に落ちる**。二人が最後まで押し合っていれば active=2 のまま増額継続で新ラウンドが立ち、表面化しない。
3. **tick の「読み(L251)」と「書き(L376)」が入札側の freeze 書き込みを跨ぐ**（読みは freeze 前・書きは freeze 後）。tick は0.5秒に一度・数ミリ秒しか動かず、freeze 書き込みがその**数ミリ秒の隙間に嵌る**必要がある。tick が freeze の後に読めば安全、tick の書きが freeze の前なら freeze 後勝ちで安全。**跨いだ時だけ**潰れる。

> つまり他の品種は①〜③のどれかを外して「運良く safe な順序」だっただけで、**構造的に安全だったわけではない**。修正が要る理由はここにある。

## 2. 根本原因

`CountdownService::tick()` の構造上の lost-update。

```
L251  $state = Cache::get(key)                         ← ★ロックなしで read（tick 冒頭）
L273  if ($phase === 'freeze') return tickFreeze(...)   ← 分岐は L251 の古い読み値で決まる
L277  ========= bidding ブランチ =========
L291  $state['remaining_seconds'] -= 0.5                ← 減算（メモリ上の古い $state）
L321  if (remaining <= 0) { bid_inflight ロックで確定 } ← Option A はここ「だけ」保護
L376  Cache::put(key, $state)                           ← ★remaining>0 の通常 tick の書き戻し（無保護）
```

参照: [tick 冒頭 read L251](../../app/Services/CountdownService.php#L251) / [freeze 分岐 L273](../../app/Services/CountdownService.php#L273) / [確定ブロック L321](../../app/Services/CountdownService.php#L321) / [通常書き戻し L376](../../app/Services/CountdownService.php#L376)

### 2.1 クロバーが起きる interleave（item 1843 で説明）

```
ラウンド開始 11:27:36（remaining=10, 自然終了 11:27:46）

t0  tick   : L251 で {phase:bidding, remaining≈1.x} を読む（★freeze書き込みより前）
t1  821入札: JoinBidAction が bid_inflight を取得
              → handleImmediatePriceIncrement → 100→110 / 821離脱 / holder=819
              → startFreezeCountdown が {phase:freeze, remaining:2} を Cache::put
              → commit → bid_inflight release
t2  tick   : L291 で t0 の古い $state を減算（remaining≈0.5, まだ>0）
              → L321 の確定ブロックはスキップ
              → L376 で {phase:bidding, remaining:0.5} を Cache::put
              ★★ ここで t1 の freeze を丸ごと上書き＝クロバー ★★
t3  次tick : L251 で {phase:bidding, remaining:0.5} を読む → 減算で 0 → L321 確定ブロックへ
              → bid_inflight 取得（誰も保持していない）
              → 再read しても phase=bidding のまま（freeze は t2 で消えている）→ ガード通過
              → active=1（819のみ, 821は離脱済み）→ handleCountdownEnd → 819 へ即落札
```

### 2.2 なぜ Option A（DEV-2026-007）ですり抜けたか

Option A は「`remaining<=0` の**確定判定**」を `bid_inflight` 下に移し、`(a)` ロック取得後の state 再read、`(b)` 中止時に `Cache::put` しない、を実装した。しかしそれは **finalize の1点だけ**。

- `remaining>0` の**通常 tick の減算＋書き戻し（L376）は依然ロック外**で、`bid_inflight` 下で書かれた freeze を平気で上書きする。
- しかも上書きは「phase=bidding」で行われるため、次 tick の確定ブロックの再read（`phase==='bidding'` チェック）も**すり抜ける**（freeze はもう消えているので検知不能）。

つまり DEV-2026-007 は「freeze を**見て確定を止める**」側は直したが、「freeze を**消す**側の経路」が残っていた。

## 3. 修正方針

### 3.0 採用方式（2段構え：B先行投入 → A後日）

明後日（2026-07-03）第4回本番を控え「ミス不可・検証時間なし」のため、**低リスクの最小ガード（B）を先行投入**し、完全直列化（A）は本番後にステージング負荷検証を通してから差し替える。

| 案 | 内容 | 封殺度 | リスク | 判断 |
| --- | --- | --- | --- | --- |
| **B（最小ガード）** | L376 の書き戻し直前に state を読み直し、bidding でなければ上書き見送り。ロック構造・確定ロジック無改造 | 危険窓を数ms→数μsに約100〜1000倍圧縮（TOCTOU は残る） | **開催停止リスクゼロ**（ロック不変） | **✅ 第4回本番へ投入（実装済み 2026-07-01）** |
| A（完全直列化） | bidding ブランチ全体を bid_inflight 下に（§3.1〜3.3） | 完全（TOCTOU なし） | 二重ロック撤去ミスが開催停止に直結、要負荷検証 | ⏳ 本番後に検証して差し替え |

**B の実装（適用済み）**: [CountdownService.php L376 手前ガード + `shouldSkipBiddingWriteback()`](../../app/Services/CountdownService.php#L376)。回帰テスト `CountdownServiceTest::test_shouldSkipBiddingWriteback_は_freeze等の割り込みを検知して上書きを見送る` を追加（全32件パス）。

以下 §3.1〜3.3 は**後日投入する A 案**の設計。

### 3.1 基本アイデア

**tick の bidding ブランチの read-modify-write（減算〜書き戻し〜確定）を、丸ごと `bid_inflight:item:{id}` 非ブロッキングロック下に入れる。** Join/Leave/即時増額（すべて同ロックを取る）と直列化し、「読み → 書き」の間に freeze が割り込む窓を消す。DEV-2026-007 の非ブロッキング思想（全レーン逐次処理を止めない）をそのまま踏襲する。

処理フロー（bidding ブランチ）:

1. `bid_inflight:item:{id}` を**非ブロッキング** `get()`。
2. **取れない**（HTTP 側が入札処理中＝freeze を書いている最中かもしれない）
   → 今回の減算・書き戻しを**丸ごと見送る**（`Cache::put` しない）。次 tick で再処理。
   → カウントは 0.5 秒据え置かれるが、混雑中に閉じない挙動はむしろ正しい。
3. **取れたら state を再read**。
   - phase が `bidding` でない、item 不一致、`is_running` でない → **bail**（減算せず return。freeze/世代交代に譲る）。
   - phase が `bidding` のまま → **再readした state を基準に**減算する（L251 の古い値は破棄）。
4. `remaining<=0` なら既存の確定ロジック（active 再カウント → 増額 or 落札/流札）を**同じロック保持のまま**実行（現行 L321 が別途取り直していた `bid_inflight` を統合）、`else` は再readベースの state を書き戻す。
5. `finally` で必ず `release()`。

### 3.2 既存資産の活かし方（最小差分・二重ロック解消）

- L321 の確定ブロックは「bidding ブランチ先頭で取ったロックの中」に入るので、**確定ブロック内の `Cache::lock` 再取得は撤去**（同一プロセス内の同キー二重取得を避ける）。ロジック本体（active 再カウント / `handlePriceIncrement` / `handleCountdownEnd`）は**無改造**。
- `handlePriceIncrement` / `handleCountdownEnd` は内部で独自に `DB::beginTransaction` + items 行ロックし、`handleCountdownEnd` は `moveToNextItem` を tx 外で実行する既存構造を維持（DEV-2026-007 と同じ制約）。**tick に DB 行ロックは足さない。**
- `tickPreBid` / `tickFreeze` は対象外。**pre_bid / freeze 中は入札ボタンが無効で即時増額が来ない**ため、クロバー源が存在しない。ロックは bidding ブランチにのみ足す。

### 3.3 擬似コード

```php
// ========= 入札カウントダウンフェーズ（bidding）=========
$biddingLock = Cache::lock("bid_inflight:item:{$item->id}", 5);
if (!$biddingLock->get()) {
    // 入札処理中。今回の減算・書き戻しを見送る（freeze を潰さない）。$state は書かない。
    return ['action' => 'bidding_tick_deferred', 'lane_id' => $laneId];
}
try {
    // ロック下で読み直す（L251 の古い $state は破棄）
    $state = Cache::get($this->getCacheKey($laneId));
    if (!$state
        || ($state['phase'] ?? 'bidding') !== 'bidding'
        || ($state['item_id'] ?? null) !== $item->id
        || empty($state['is_running'])) {
        // 他 writer が freeze/世代交代を書いた → 何もしない（次 tick が拾う）
        return ['action' => 'bidding_tick_yielded', 'lane_id' => $laneId];
    }

    // …（現行 L278〜L309 の active カウント・設定同期・減算・broadcast を再readベースで実施）…
    $state['remaining_seconds'] = max(0, $state['remaining_seconds'] - self::TICK_INTERVAL);

    if ($state['remaining_seconds'] <= 0) {
        // 現行 L328〜L370 の確定ロジックをそのまま（ただし内側の Cache::lock 再取得は撤去）
        $freshItem = $item->fresh();
        if (!$freshItem || $freshItem->status !== 'live') {
            $this->stopCountdown($laneId);
            return ['action' => 'finalize_skip_not_live', 'lane_id' => $laneId];
        }
        $freshCount = BidParticipant::forItem($freshItem->id)->active()->count();
        if ($freshCount >= 2) {
            $this->handlePriceIncrement($lane, $freshItem, $auction, $freshCount, $state['last_bidder_user_id'] ?? null);
            return ['action' => 'price_increment', 'lane_id' => $laneId];
        }
        return $this->handleCountdownEnd($lane, $freshItem, $auction, $freshCount);
    }

    Cache::put($this->getCacheKey($laneId), $state, self::CACHE_TTL);
    return ['action' => 'tick', 'remaining_seconds' => $state['remaining_seconds']];
} finally {
    $biddingLock->release();
}
```

> 注: ロックが取れなかった tick は「見送り」。remaining は据え置きだが、DEV-2026-007 の `finalize_deferred` と同様に次 tick で自然回復する。broadcast も見送るが、フロントは 1 秒粒度表示なので UX 影響はない。

## 4. 実装ルール（違反すると逆に壊す）

| # | ルール | 破った場合 |
| --- | --- | --- |
| R1 | bidding ブランチのロックは **非ブロッキング `get()`**。`block()` 禁止 | 単一ジョブが全レーン逐次処理のため、複数レーン同時で **全レーン tick 停止** |
| R2 | ロック取得後に **state を必ず再read**し、それを基準に減算・書き戻す | L251 の古い値で書くと、結局 freeze を上書きして**本バグ再発** |
| R3 | 見送り／bail 時は **`Cache::put` しない** | 直前 freeze を古い bidding-0 で上書き＝即落札再発 |
| R4 | 確定ブロック内の `Cache::lock("bid_inflight:item:…")` 再取得は **撤去**（外側で保持済み） | 同一プロセスの同キー二重取得。実装により再取得失敗で確定不能 |
| R5 | ロックキーは `bid_inflight:item:{$item->id}`。Join/Leave/即時増額と**完全一致** | 直列化されず無意味化 |
| R6 | `release()` は必ず `finally`。TTL 5s | 例外時ロック残留 → その item への入札が最大5秒「処理中」 |
| R7 | 対象は **bidding ブランチのみ**。pre_bid/freeze には足さない | 不要なロックでホットパス増。freeze 中は入札来ないので効果もない |

## 5. 影響範囲・副作用

| 経路 | 挙動 | 評価 |
| --- | --- | --- |
| 滑り込み入札（本件3件） | 入札が freeze を書く間、tick はロックを取れず見送り／取れても再readで freeze を尊重 → 新ラウンド保存 | ✅ 修正の主目的 |
| 通常進行（競合なし） | ロック即取得 → Redis GET 追加1回のみ。減算・書き戻しは従来通り | ✅ ほぼ無影響 |
| 確定（落札/流札/増額） | 外側ロック内で実行。内側の重複ロック取得を撤去して整理 | ✅ 挙動同一・軽量化 |
| numprocs=5 複数ワーカー | `countdown_job_lock`+世代でオークションあたり実行1本（[ProcessAuctionCountdownJob L100](../../app/Jobs/ProcessAuctionCountdownJob.php#L100)）。tick 同士の競合は元々なし | ✅ |
| デッドロック | 全経路「bid_inflight → items」順で統一。サイクルなし | ✅ |
| ロック残留（プロセス死） | TTL 5秒で自動解放。その間 tick 見送り→5秒後回復 | ⚠️ 軽微・許容 |

### 5.1 負荷影響（≈150名規模）

- 追加は **bidding tick ごとに Redis 非ブロッキング `get()`＋`release()` 各1回**（sub-ms）。pre_bid/freeze は対象外。2〜3レーンでも毎秒数回程度で、DEV-2026-007 §5.5 の許容範囲内。
- **新たな DB ロックは tick に足さない**（Option A の構造を維持）。「単一 tick が行ロック待ちで全レーン停止」リスクは引き続き無い。
- 混雑時は tick 見送りでカウントが 0.5 秒据え置かれることがあるが、「入札が飛んでいる間は閉じない」望ましい挙動。

## 6. テスト方針

### 6.1 競合再現（最重要・本バグの回帰テスト）
- bidding remaining≈残り0.5 の tick 処理の直前に `handleImmediatePriceIncrement`（freeze 書き込み）を差し込み、**tick 実行後に phase が freeze のまま保持される**ことを検証（＝クロバーしない）。
- 逆順（tick がロック先取り）で、入札側が待たされた後 `status`/`phase` を正しく観測することを確認。
- ロック取得不可 → `bidding_tick_deferred` を返し **`Cache::put` しない**ことを検証。
- ロック取得後の再readで phase=freeze → `bidding_tick_yielded`、**書き戻さない**ことを検証。

### 6.2 リグレッション
- DEV-2026-007 の既存 `CountdownServiceTest` 全件 green（特に `finalize_deferred` 系）。
- カウントダウン進行・商品切替・指値・一時停止/再開の既存テストが green。
- `load-tests/` で 120〜150名規模の tick 安定（メモリ不変・failed_jobs 0・`finalize_deferred`/`bidding_tick_deferred` が終盤散発で starvation しない）を確認。
