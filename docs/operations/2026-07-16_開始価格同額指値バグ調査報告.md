## 1. TL;DR

開始価格と同額の指値を**2名以上**が設定すると、`adjustPriceByBidLimits` の早期 return により**「同額後発者を脱落させる」処理が丸ごとスキップ**される。結果、両者が `is_active=true` のまま残り、**単方向入札仕様によって両者の入札ボタンが disabled になる**（＝報告の「入札できない」）。

この「入札できない」までは**コードで確実に説明がつく**。ただし最終結果について、静的トレース上は **流札（unsold）** になり、報告の「最低価格で落札された」を再現できていない（§6）。

**修正は1箇所では済まない**（§8）。開催18時間前の変更は非推奨で、まず §7 で事実を確定させることを推奨する。

## 2. 前提: 指値（bid_limit）の設計意図

`bid_limit_prices` は proxy-bid として設計されている（2026-05-15 改修）。

- 同額の指値が並んだ場合、**`created_at` が最も早い1名だけを落札権利者として残し、後発者は強制脱落させる**
- 脱落した指値レコードは `is_triggered=true` を立てた**直後に同一トランザクション内で物理削除**される
  → これは意図的（[CountdownService.php:1382](../../app/Services/CountdownService.php#L1382) `// 非アクティブ入札者 → 削除のみ（再入札をブロックしないため）`）
- 「上限価格」は**包含的**。`limit_price == current_price` は「ちょうど耐える」扱いで、まだ有効

この設計意図はコード内コメントに明記されている（[:1393-1394](../../app/Services/CountdownService.php#L1393-L1394)）。

```php
// 発動条件:
//   (a) limit_price < current_price       → 払えない指値（無条件で発動）
//   (b) limit_price == current_price で
//       protectedUserIds に入っていない    → 同額後発の指値（強制脱落）
```

**本バグは、この (b) が特定条件下で一度も実行されないというもの。**

### なぜこうなるか

同額タイ分岐（L1329-1333）は「価格は最高指値のまま据え置く」ため `targetPrice = $highestLimit` を代入する。ところが**開始価格 == 最高指値**のとき `targetPrice == $currentPrice` となり、直後の L1362「価格が上がらないなら何もしない」ガードに吸い込まれる。

**L1362 は「価格更新の要否」だけを判断すべき箇所だが、実際には「指値トリガー処理の要否」まで巻き添えで殺している。**

### 同額タイ分岐が無くても同じ

L1329 の分岐を通らず else 側（通常の刻み上げ）へ行った場合も同じ結果になる。

```php
while ($targetPrice <= $secondHighestLimit) {   // 100 <= 100 → true
    $increment = $auction->calculatePriceIncrement($targetPrice);  // 例: 10
    $targetPrice += $increment;                 // 110
}                                               // 110 <= 100 → false → 脱出
if ($targetPrice > $highestLimit) {             // 110 > 100 → true
    $targetPrice = $highestLimit;               // 100 に引き戻される
}
// → L1362 で 100 <= 100 → rollback
```

つまり**同額タイ分岐の追加前後どちらのバージョンでも L1362 に到達する**。第4回時点のコードでも同様だった可能性が高い。

### テストカバレッジ

[`tests/Unit/Services/CountdownServiceTest.php:499`](../../tests/Unit/Services/CountdownServiceTest.php#L499) `test_adjustPriceByBidLimits_は_同額指値で先設定者を保護してアクティブのまま残す` は、**開始価格 10000 に対して指値 20000** でタイを作っている。`targetPrice(20000) > currentPrice(10000)` なので L1362 を通過してしまう。

**「同額指値 == 開始価格」のケースは既存テストで一行もカバーされていない。**

## 8. 修正案とリスク

### 最小修正（案）

**① `CountdownService.php:1362` — 同額タイのときは価格更新をスキップしつつトリガー処理へ進ませる**

```php
$samePriceTie = ($highestLimit == $secondHighestLimit);
if ($targetPrice < $currentPrice || ($targetPrice == $currentPrice && !$samePriceTie)) {
    DB::rollBack();
    return;
}
if ($targetPrice > $currentPrice) {   // 同額タイでは価格を動かさない
    $item->update(['current_price' => $targetPrice]);
    PriceEvent::recordAutoIncrement($item->id, $currentPrice, $targetPrice, $limits->count());
}
```

**② `CountdownService.php:702` — `checkBidLimits` に `protectedUserIds` を渡す**

①だけでは不十分。§6 Step 6 の通り、`handlePriceIncrement` が `checkBidLimits` を保護リストなしで呼んでいるため、**保護したはずの先設定者が直後に蹴られる**。

## 9. 付随して判明した問題

### 9-1. 同額タイの `created_at` が秒精度

`bid_limit_prices` の [migration](../../database/migrations/2026_02_19_135909_create_bid_limit_prices_table.php#L18) は `$table->timestamps()` で精度指定なし ＝ MySQL 精度0（秒）。

タイブレークは `orderBy('limit_price','desc')->orderBy('created_at','asc')` の2キーのみで **`id` による第3キーがない**。

→ **同一秒内に同額の指値が2件入ると、どちらが残るかが MySQL の返却順依存で非決定**になる。

実運用上の実害は「同額同秒の2人のうちどちらが先に権利を持つか」だけで、金額は変わらず敗者も再入札できるため軽微。ただし**テストの再現性は壊れる**ので、E2E では指値設定を1秒以上あけること。

### 9-2. `updateOrCreate` で `created_at` が据え置かれる

[SetBidLimitAction.php:65-68](../../app/Actions/Bid/SetBidLimitAction.php#L65-L68) は `updateOrCreate` のため、既存行の `limit_price` を書き換えても `created_at` は最初の設定時刻のまま。

→ 「先に安い指値を置いて後で吊り上げた人」が、「後から同額を直接置いた人」にタイブレークで勝つ。仕様として意図的かどうか要確認。

### 9-3. `L1433-1444` の防御コードは到達不能

`adjustPriceByBidLimits` の `if ($isProtected)` 分岐は、`$allTriggeredLimits` のクエリが protected を除外済みかつ protected の `limit_price >= current_price` が常に成立するため、実際には到達しない。動作影響はないが、読み手を混乱させる。
