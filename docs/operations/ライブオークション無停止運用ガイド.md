# ライブオークション無停止運用ガイド

| 項目 | 内容 |
| --- | --- |
| 文書番号 | OPS-2026-002 |
| 版数 | 1.0 |
| 作成日 | 2026-05-01 |
| 対象環境 | 本番（EC2 AL2023 / Nginx + PHP-FPM / supervisor / ElastiCache(Valkey) / RDS MySQL / Reverb） |
| 想定負荷 | 同時参加 〜200名、指値 〜100件/商品、お気に入り 〜1,000件/オークション |
| 想定読者 | 運用担当・開発担当・当日モニタリング担当 |

> 本ガイドは本番運用前提。Docker / docker-compose は対象外。
> 作業はすべて `ec2-user` で SSH ログインし `/var/www/auction` を作業ディレクトリとする。
> `php artisan` 系コマンドは必ず `sudo -u ec2-user php artisan ...` で実行すること（root 実行は `storage/logs` を root 所有で生成し worker を全滅させる）。

---

## 0. このガイドの目的

ライブオークションは「価格カウントダウンが進み続けている」ことが商品価値そのものになる。
**tick が1秒でも止まれば全レーン全商品が unsold 化する** リスクがあり、復旧してもユーザー信頼は戻らない。

このガイドは、想定される負荷と既知の故障モードを台帳化し、「止めない」ための事前・最中・事後の打ち手を1か所にまとめたもの。緊急対応プレイブックではなく、**当日までに整えておく恒常的な運用基盤** を扱う。

---

## 1. 「止まる時はどう止まるか」既知の故障モード台帳

ライブオークションが過去・現在に止まり得る経路を、再発しやすさ順に列挙する。

### 1-1. Critical：tick チェーン全停止（最も致命的）

**症状**：全レーンのカウントダウンが「3秒のまま」固定。WebSocket は生きているのに価格が動かず、商品が次に進まない。

**原因系統**：
- `ProcessAuctionCountdownJob` 冒頭の `Log::info()` が `storage/logs` 書き込み権限不足で例外を投げる
- 例外で次 tick の dispatch が走らず、tick の自己連鎖が切れて全停止
- `php artisan` を root で叩いた直後に発生しやすい（root 所有のログファイルが生成され、その後 ec2-user の worker が書き込めなくなる）

**事前対策**：
- `storage/logs` を `ec2-user:ec2-user` 所有 / `0775` で固定
- すべての artisan 実行は `sudo -u ec2-user php artisan ...`（恒久ルール）
- supervisor の worker ユーザーが `ec2-user` であることを `cat /etc/supervisord.d/*.ini` で毎回確認

**監視**：
- `ProcessAuctionCountdownJob` の実行間隔を CloudWatch メトリクスで watch（後述§4）
- `failed_jobs` テーブルの行数増加アラート

参考：[CountdownService.php](../../app/Services/CountdownService.php) / [ProcessAuctionCountdownJob.php](../../app/Jobs/ProcessAuctionCountdownJob.php)

### 1-2. Critical：Reverb ポート誤設定で全件 unsold 化

**症状**：開始直後にすべての商品が unsold。フロントの WebSocket 接続が `Connection reset by peer`。

**原因**：
- `.env` の `REVERB_PORT` を `8080`（nginx の WebSocket proxy 用）に向けてしまうと、broadcast が proxy 層で reset され全商品の状態通知が落ちる

**正しい設定**：
- Reverb 本体は **6001** で listen
- nginx 8080 はその前段の WebSocket proxy 専用
- broadcast 元のアプリは **必ず 6001 を直接指す**

**確認コマンド**：
```bash
grep -E "^REVERB_(HOST|PORT|SCHEME)" /var/www/auction/.env
ss -tlnp | grep -E ':6001|:8080'
```

### 1-3. High：items ロック順違反によるデッドロック

**症状**：入札が散発的に失敗、`Deadlock found when trying to get lock` がログに出る。深刻化すると同一商品で連鎖。

**原則**（既存メモから）：
- `bid_participants` / `bid_events` を触るトランザクションは **必ず `items.lockForUpdate()` → 子テーブル** の順
- 子から先にロックを取ると外部キーロックで逆順デッドロックを引き起こす
- price freeze cache などの cache 書き込みは **commit 前** に書く（commit 後だと参加者から見て不整合な瞬間が生まれる）

**既に適用済みの対策**：
- [SetBidLimitAction::activatePendingBidLimits](../../app/Actions/Bid/SetBidLimitAction.php) は items 行ロックを **1回だけ**取得し foreach 内では取り直さない
- `BidderUpdated` broadcast は `DB::afterCommit` で **1回のみ**

**新規実装時のレビュー観点**：
- 入札系の新しいトランザクションを足すときは、必ずこのロック順をコードレビューで確認

### 1-4. High：notify キュー詰まりが countdown を巻き込まない設計

**現状の良い点**：キューは既に分離されている。

| キュー | 主なジョブ | 性質 |
| --- | --- | --- |
| `countdown` | `ProcessAuctionCountdownJob`, `ProcessCountdownJob` | 同期律速（1秒の遅延も致命） |
| `notify` | `SendLineNotificationJob`, `NotifyFavoriteApproachingJob`, `SendCampaignEmailJob`, `SendPaymentReminderJob`, `SendAuctionPreviewJob` | 外部API依存・遅延許容 |
| `media` | `ProcessItemVideoJob` | 重処理・後追い |

**運用ルール**：
- supervisor では **キューごとに別 worker プロセス** を起動する。`--queue=countdown,notify` のように混ぜない
- `notify` worker が LINE API のレート制限で詰まっても、`countdown` worker は影響を受けないこと
- 新規ジョブを追加する際は `onQueue()` を必ず指定。未指定（default）は禁止

**確認コマンド**：
```bash
# supervisor で countdown と notify の worker が別プロセスになっているか
ps -ef | grep "queue:work" | grep -v grep
# Redis の各キュー深さ
redis-cli -h <ElastiCache endpoint> LLEN queues:countdown
redis-cli -h <ElastiCache endpoint> LLEN queues:notify
```

### 1-5. Medium：価格自動調整ループの tick 内実行時間

**箇所**：[CountdownService::adjustPriceByBidLimits](../../app/Services/CountdownService.php)（行1043-1311）

- 安全カウンタ最大 10,000 回の while ループ
- 通常は「指値価格の段階数」しか回らないため100人指値でも数十回程度
- ただし価格刻みが小さく + 指値ばらつきが大きいと tick 1 回の処理時間が伸びる
- tick 内同期実行 → countdown キューを長時間専有するリスク

**監視**：
- `adjustPriceByBidLimits` の実行時間を計測する Log を入れる（p95 で 200ms を超えたら警戒）
- 100人指値に到達するレーンが事前に分かっているなら、開始前に `SHOW PROCESSLIST` を流して長時間ロックがないか確認

### 1-6. Medium：お気に入り通知の fan-out

**箇所**：[NotifyFavoriteApproachingAction](../../app/Actions/Line/NotifyFavoriteApproachingAction.php)

- 商品が3つ先に進むたびに該当商品をお気に入りしているユーザー全員へ LINE + Mail の2ジョブを dispatch
- 例：1商品100人お気に入り → 商品切替1回で **200ジョブ**
- 1オークション100商品 → **最大 20,000 ジョブ/オークション**

**律速要因**：
- LINE Messaging API のプッシュ送信レート制限
- `notify` queue worker の同時実行数

**運用閾値**：
- `notify` キュー深さが **5,000 件を超えたらアラート**
- LINE API の 4xx / 5xx レスポンス率が **5% を超えたらアラート**
- 必要に応じて `notify` worker を一時的にスケールアウト

### 1-7. Low：Reverb 単一プロセスのメモリ

- `REVERB_SCALING_ENABLED=false` のままなら Reverb は **単一プロセスのメモリ常駐**
- 200名想定なら問題ないが、複数 EC2 に展開した瞬間に状態同期が崩れる
- 将来スケールする場合は `REVERB_SCALING_ENABLED=true` + Redis pub/sub 設定を有効化（[config/reverb.php](../../config/reverb.php)）

## 2. 想定負荷の数値見積り

### 2-1. 指値 100人 / 商品

| 動作 | DB クエリ | broadcast | 想定実行時間 |
| --- | --- | --- | --- |
| `activatePendingBidLimits`（オークション開始時） | items 行ロック1回 + whereIn 1回 + INSERT 200件（participate + recordJoin） | `BidderUpdated` × 1 | 1〜2秒 |
| `adjustPriceByBidLimits`（tick 内） | 段階ごとに SELECT/UPDATE | `PriceUpdated` + 必要なら `BidderUpdated` | 通常 50ms 以下 / ワーストで数百ms |

→ **設計上、100人指値は捌ける**。問題は同時 commit 時のロック競合のみ。

### 2-2. お気に入り 1,000件 / オークション

| 動作 | DB クエリ | dispatch ジョブ数 |
| --- | --- | --- |
| 商品切替時の事前通知 | `Favorite::whereIn(...)` 1クエリ | 該当商品をお気に入りしているユーザー数 × 2（LINE + Mail） |

→ **DB 負荷は無視できる**。律速は LINE API と notify worker のスループット。

### 2-3. WebSocket broadcast / tick

1 tick あたり最大 5 種類のイベント（`CountdownTick`, `PriceUpdated`, `BidderUpdated`, `BidLimitReached`, `LaneItemChanged`）が public channel `auction.{auctionId}.live` に流れる。

- 200名接続 × 5イベント × tick間隔1秒 = **最大 1,000 メッセージ/秒**
- Reverb 単体で十分捌ける範囲

## 3. 多層防御：事前・最中・事後の打ち手

### 3-1. 事前（オークション前日まで）

| 項目 | 確認方法 |
| --- | --- |
| `storage/logs` の所有者と権限 | `ls -la /var/www/auction/storage/logs` で `ec2-user:ec2-user 0775` |
| supervisor の worker ユーザー | `grep user /etc/supervisord.d/*.ini` がすべて `ec2-user` |
| `failed_jobs` 空 | `sudo -u ec2-user php artisan queue:failed` で空 |
| Reverb ポート | `.env` `REVERB_PORT=6001`、`ss -tlnp` で 6001 listen |
| キュー分離 | `ps -ef \| grep queue:work` で countdown/notify/media が独立プロセス |
| ステージングでの 100人指値リハーサル | medaka-auction.com（ステージング）で k6 などを使い実施 |
| LINE API 残レート枠 | LINE Developers コンソールで月次配信枠を確認 |

### 3-2. 最中（オークション開催中）

最低3つのターミナル窓を開き常時監視：

```bash
# 窓1: countdown ジョブの実行ログ（tick の心拍）
sudo tail -f /var/www/auction/storage/logs/laravel.log | grep -E "ProcessAuctionCountdown|tick"

# 窓2: notify キュー深さの推移
watch -n 5 'redis-cli -h <endpoint> LLEN queues:notify'

# 窓3: failed_jobs 監視
watch -n 10 'sudo -u ec2-user php /var/www/auction/artisan queue:failed | head -20'
```

**警戒シグナルと初動**：

| シグナル | 初動 |
| --- | --- |
| tick ログが10秒途切れた | §5-A プレイブック |
| `notify` キュー深さが 5,000 超 | §5-B プレイブック |
| `failed_jobs` に countdown 系が積まれた | §5-A プレイブック |
| WebSocket 切断率が急上昇 | Reverb プロセス・ポート確認（§1-2） |

### 3-3. 事後

- オークション終了後 30 分以内に `failed_jobs` を全件確認、未送信通知があれば再投入
- LINE / Mail の送信成功率レポートを記録
- `adjustPriceByBidLimits` の最大実行時間を CloudWatch から抽出して台帳に追記
- 異常があった時系列を Slack に時刻入りで残す（次回の閾値調整に使う）

## 5. 緊急時プレイブック

> **大原則**：止まったライブオークションは「再起動」より「気づくこと」が9割。
> 検知が早ければほとんどの故障は1〜3分で復旧できる。

### 5-A. tick が止まった時

```bash
# 1. tick ジョブが生きているか
sudo -u ec2-user php /var/www/auction/artisan queue:failed | grep -i countdown

# 2. supervisor で countdown worker の状態確認
sudo supervisorctl status | grep countdown

# 3. 詰まっていれば再起動（worker のみ。Reverb は触らない）
sudo supervisorctl restart auction-countdown:*

# 4. ログ権限の確認（典型原因）
ls -la /var/www/auction/storage/logs/
# root所有のファイルがあれば即修正
sudo chown ec2-user:ec2-user /var/www/auction/storage/logs/*.log

# 5. 失敗ジョブを retry
sudo -u ec2-user php /var/www/auction/artisan queue:retry all
```

### 5-B. notify キュー詰まり

```bash
# 1. 深さ確認
redis-cli -h <endpoint> LLEN queues:notify

# 2. LINE API 側のエラーか確認
sudo tail -100 /var/www/auction/storage/logs/laravel.log | grep -iE "line|notify"

# 3. countdown には影響しないので、LINE が回復するまで待つのが基本
# 4. どうしても捌けないなら notify worker を一時的に増やす
sudo supervisorctl start auction-notify-extra:*
```

### 5-C. WebSocket 全断

```bash
# 1. Reverb プロセス
sudo supervisorctl status reverb

# 2. ポート確認（6001 が listen していない＝Reverb 落ち）
ss -tlnp | grep 6001

# 3. .env のポート確認（8080 を指していたら最も多い致命的誤り）
grep REVERB_PORT /var/www/auction/.env

# 4. Reverb 再起動
sudo supervisorctl restart reverb
```

**ライブ中に Reverb を再起動するとその瞬間の broadcast は失われる**。再起動後は CountdownService が次 tick で状態を再送するので価格表示は復旧するが、それまでの数秒間は「止まったように見える」点をモニタリング担当に共有しておく。

### 5-D. デッドロック多発

```bash
# 1. ロック中トランザクションの確認
sudo -u ec2-user php /var/www/auction/artisan tinker
>>> DB::select('SHOW ENGINE INNODB STATUS');

# 2. 単発なら Laravel のリトライ（3回設定済み）で吸収される
# 3. 連鎖的に発生 → 直近に追加した入札系コードがロック順違反していないかコードレビュー
```

## 6. リハーサル必須項目（オークション開催前）

ステージング（medaka-auction.com）で以下を**必ず1回は通す**。1つでも通らなければ本番開催は延期。

- [ ] 100人同時 join → 全員が participant に入る
- [ ] 100人指値設定 → `activatePendingBidLimits` が1秒以内に完了
- [ ] 100商品連続切替 → notify キューが詰まらない
- [ ] tick が連続300秒以上途切れない（ログ権限事故の検知テスト）
- [ ] わざと `storage/logs` を root 所有に変えてみて tick が止まることを再現 → 監視で検知できることを確認 → 戻す
- [ ] Reverb を `kill` → 再起動 → カウントダウンが復旧することを確認
- [ ] `notify` worker を停止 → countdown は影響を受けず動き続けることを確認
