## 0. 大前提: 自動回復の仕組み

**触る前に思い出すこと**: システムは**二段の自動回復機構**を持っています。

```
                                                ┌─ Job 内 maxIterations 自然終了 (4時間)
                                                │   ↓
ProcessAuctionCountdownJob ─── heartbeat 更新 ───┤   finished cache 120秒
   (5時間 timeout)              (毎iteration)    │   ↓
                                                │   MonitorAuctionJobs (1分ごと scheduler)
                                                │   ↓
                                                │   heartbeat 古い検知 → 新ジョブ dispatch
                                                │
                                                └─ Job 中で例外/エラー → supervisor autorestart
```

→ **多くの「止まった」は 1〜2分で自動回復します**。慌てて手を出すと逆効果になることも。
→ ただし「**ログ書き込み権限破壊**」だけは自動回復しないので最優先で確認。

## 1. 検知: tick が止まった時のシグナル

| シグナル | 検知方法 | 緊急度 |
| --- | --- | --- |
| 監視窓1 (tick 心拍) が **10秒以上** 途切れる | `tail -f laravel.log \| grep ProcessAuctionCountdown` | 🟡 様子見1分 |
| 監視窓1 が **30秒以上** 途切れる | 同上 | 🔴 即対応 §3-A |
| 監視窓3 で failed_jobs に `ProcessAuctionCountdownJob` が積まれる | `queue:failed` | 🔴 即対応 §3-A |
| ユーザーから「カウントダウンが動かない」報告 | Slack / フォーム | 🟡 監視窓1再確認 |
| 全レーンで同じ商品が表示され続ける | 管理画面 | 🔴 即対応 |
| カウントダウンが「3秒のまま」固定 | 管理画面 | 🔴 ログ権限破壊の典型 |

---

## 2. 5秒判断: まず何を見るか

検知したら **30秒以内** にこの3つを順に叩く:

### 2-1. tick ログの最新行 (生きてるか死んでるか)

```bash
sudo tail -50 /var/www/auction/storage/logs/laravel.log | grep -iE "countdown\.job|ProcessAuctionCountdown|tick" | tail -5
```

| 結果 | 判定 |
| --- | --- |
| 直近10秒以内に新ログ | 🟢 動いてる、誤検知 |
| 直近30秒以内に「countdown.job.completed」 | 🟡 ジョブが自然終了済み、MonitorAuctionJobs の dispatch 待ち (1分以内に復旧) |
| 直近30秒以内に「countdown.job.re_dispatched」 | 🟡 既に再ディスパッチ済み、新ジョブ起動待ち |
| **30秒以上ログなし** | 🔴 §3-A 発動 |

### 2-2. ログ書き込み権限確認 (最頻原因)

```bash
ls -la /var/www/auction/storage/logs/ | head -10
```

| 結果 | 判定 |
| --- | --- |
| 全部 `ec2-user:ec2-user` | 🟢 |
| **root所有のファイルが1つでもある** | 🔴 §3-B 発動 (権限修復) |

### 2-3. supervisor 状態確認

```bash
sudo supervisorctl status | grep countdown
```

| 結果 | 判定 |
| --- | --- |
| 全 RUNNING / uptime 数分以上 | 🟢 worker は生きてる、ジョブ側問題 |
| 一部 EXITED / FATAL | 🔴 §3-D 発動 (worker 死亡) |
| uptime が極端に短い (数秒) | 🟡 再起動を繰り返してる、ログ確認 |

## 3. 復旧手順 (パターン別)

### 3-A. tick が止まったが worker は RUNNING (最頻ケース)

**典型原因**:
1. `ProcessAuctionCountdownJob` 冒頭の `Log::info()` がログ権限失敗で例外
2. heartbeat 更新が止まり、MonitorAuctionJobs が再 dispatch 待ち中
3. Redis lock 競合で stuck

**手順**:
```bash
# ① まずログ権限を直す (最頻原因、これだけで直ることが多い)
sudo chown -R ec2-user:ec2-user /var/www/auction/storage/logs/
sudo chmod -R 0775 /var/www/auction/storage/logs/

# ② failed_jobs に countdown 系が積まれてないか確認
sudo -u ec2-user php /var/www/auction/artisan queue:failed | grep -i countdown

# ③ Cache の状態確認
sudo -u ec2-user php /var/www/auction/artisan tinker <<'PHPEOF'
$auctionId = App\Models\Auction::where('status','live')->value('id');
echo "live auction: {$auctionId}".PHP_EOL;
echo "heartbeat: ".(Cache::get("countdown_job_heartbeat:auction:{$auctionId}") ?? 'null').PHP_EOL;
echo "running: ".(Cache::get("countdown_job_running:auction:{$auctionId}") ? 'true' : 'false').PHP_EOL;
echo "finished: ".(Cache::get("countdown_job_finished:auction:{$auctionId}") ? 'true' : 'false').PHP_EOL;
echo "generation: ".(Cache::get("countdown_job_generation:auction:{$auctionId}") ?? 0).PHP_EOL;
echo "now: ".now()->timestamp.PHP_EOL;
PHPEOF

# ④ ①〜③で復旧しなければ worker 再起動 (この時点でも MonitorAuctionJobs が 1分以内に dispatch する)
sudo supervisorctl restart auction-queue-countdown:*

# ⑤ failed_jobs を retry
sudo -u ec2-user php /var/www/auction/artisan queue:retry all

# ⑥ 30秒以内に tick ログ復活を確認
sudo tail -f /var/www/auction/storage/logs/laravel.log | grep -E "countdown\.job|tick"
```

### 3-B. ログ書き込み権限破壊

```bash
# 1. 即修復
sudo chown -R ec2-user:ec2-user /var/www/auction/storage/logs/
sudo chmod -R 0775 /var/www/auction/storage/logs/

# 2. 確認
ls -la /var/www/auction/storage/logs/ | head -5

# 3. 30秒待って復旧確認 (MonitorAuctionJobs が次の minute に再 dispatch)
sleep 30
sudo tail -20 /var/www/auction/storage/logs/laravel.log | grep -E "countdown\.job|tick"
```

**予防**: artisan を root で叩かない (memory: [artisan を root で叩かない](memory/feedback_no_sudo_artisan.md))。**必ず** `sudo -u ec2-user php artisan ...`

### 3-C. heartbeat が更新されているのに tick ログがない (謎の沈黙)

worker は生きてるが、表面に出るログが出ない状態:

```bash
# 1. Cache の generation を確認
sudo -u ec2-user php /var/www/auction/artisan tinker <<'PHPEOF'
$auctionId = App\Models\Auction::where('status','live')->value('id');
$gen = Cache::get("countdown_job_generation:auction:{$auctionId}", 0);
echo "current generation: {$gen}".PHP_EOL;
echo "heartbeat: ".(Cache::get("countdown_job_heartbeat:auction:{$auctionId}") ?? 'null').PHP_EOL;
PHPEOF

# 2. 強制的に世代を進めて新ジョブを起動 (最終手段)
sudo -u ec2-user php /var/www/auction/artisan tinker <<'PHPEOF'
$auctionId = App\Models\Auction::where('status','live')->value('id');
// 古いジョブを「古い世代」にして次の iteration で自発終了させる
$genKey = App\Jobs\ProcessAuctionCountdownJob::generationKey($auctionId);
$newGen = ((int) Cache::get($genKey, 0)) + 1;
Cache::put($genKey, $newGen, App\Jobs\ProcessAuctionCountdownJob::HEARTBEAT_TTL);
// 関連キャッシュをクリア
Cache::forget("countdown_job_running:auction:{$auctionId}");
Cache::forget("countdown_job_heartbeat:auction:{$auctionId}");
Cache::forget("countdown_job_lock:auction:{$auctionId}");
// 新ジョブを dispatch
App\Jobs\ProcessAuctionCountdownJob::dispatch($auctionId);
echo "Re-dispatched with generation {$newGen}".PHP_EOL;
PHPEOF
```

### 3-D. supervisor で countdown worker が EXITED / FATAL

```bash
# 1. ログ確認
sudo tail -50 /var/log/supervisor/queue-countdown.log

# 2. 強制再起動
sudo supervisorctl restart auction-queue-countdown:*

# 3. supervisorctl で起動しない場合
sudo supervisorctl stop auction-queue-countdown:*
sleep 2
sudo supervisorctl start auction-queue-countdown:*

# 4. それでもダメなら supervisor 自体の再起動 (最終手段)
sudo systemctl restart supervisord
```

### 3-E. 4時間境界での自然終了タイミング (5/22/5/23では到達しない見込み)

```bash
# 「countdown.job.completed」が出てから 2-3分の凍結が起きる可能性
# MonitorAuctionJobs が 1分以内に新ジョブを dispatch するので待つ

# 待つ場合の確認
sudo tail -f /var/www/auction/storage/logs/laravel.log | grep -E "countdown\.job\.(completed|re_dispatched|started)"

# 待ちきれない場合、lane state cache の TTL を手動で延長 (商品の残秒数巻き戻り防止)
sudo -u ec2-user php /var/www/auction/artisan tinker <<'PHPEOF'
$lanes = App\Models\Lane::whereHas('auction', fn($q) => $q->where('status', 'live'))->get();
foreach ($lanes as $lane) {
  $key = "countdown:lane:{$lane->id}";
  $state = Cache::get($key);
  if ($state) {
    Cache::put($key, $state, 14400);
    echo "Extended TTL for lane {$lane->id}".PHP_EOL;
  }
}
PHPEOF
```

### 3-F. Reverb 死亡で価格表示が止まる (tick 自体は生きてる)

「カウントダウンが止まった」と見えるが、実は Reverb が死んでて broadcast が届いてないだけのケース:

```bash
# 1. Reverb プロセス確認
sudo supervisorctl status auction-reverb
sudo ss -tlnp | grep 6001

# 2. メモリ確認 (1GB超なら計画再起動)
ps -o pid,rss,%mem,cmd -p $(pgrep -f reverb:start)

# 3. 再起動 (数秒の broadcast 停止、フロントは自動再接続)
sudo supervisorctl restart auction-reverb

# 4. 復旧確認
sudo ss -tlnp | grep 6001
```

注意: Reverb 再起動中の broadcast はロストするが、次の tick で状態が再送されるので価格表示は数秒で復旧する。

## 4. 復旧後の確認 (必須)

復旧操作をしたら、以下を**全部**確認する:

```bash
# 1. tick ログが安定して流れているか (30秒以上観察)
sudo tail -f /var/www/auction/storage/logs/laravel.log | grep -E "countdown\.job|tick"

# 2. supervisor で全 worker が RUNNING (uptime が短い場合は再起動直後)
sudo supervisorctl status

# 3. failed_jobs が増えていないか
sudo -u ec2-user php /var/www/auction/artisan tinker --execute="echo DB::table('failed_jobs')->where('failed_at','>=', now()->subMinutes(5))->count();"

# 4. heartbeat が新鮮 (5秒以内の更新)
sudo -u ec2-user php /var/www/auction/artisan tinker <<'PHPEOF'
$auctionId = App\Models\Auction::where('status','live')->value('id');
$hb = Cache::get("countdown_job_heartbeat:auction:{$auctionId}");
$age = $hb ? (now()->timestamp - $hb) : 'null';
echo "heartbeat age: {$age}秒".PHP_EOL;
PHPEOF

# 5. ログ権限が ec2-user 所有のまま維持されているか
ls -la /var/www/auction/storage/logs/ | head -5
```

## 5. 中断判断基準

「復旧したつもりが復旧してない」を見抜くため、以下に当てはまれば**即時中断**を判断:

| 状況 | 判断 |
| --- | --- |
| 復旧操作後、5分経っても tick が再開しない | **即時中断** |
| 復旧操作を3回繰り返しても安定しない | **即時中断** |
| 全レーンが同じ商品で1分以上止まる | **即時中断** |
| failed_jobs が分単位で20件以上増加 | **5分以内に中断判断** |
| Reverb が再起動を3回繰り返しても安定しない | **即時中断** |

### 中断手順 (実害最小)

```bash
# 全レーン一時停止
sudo -u ec2-user php /var/www/auction/artisan tinker <<'PHPEOF'
$updated = App\Models\Lane::whereHas('auction', fn($q) => $q->where('status', 'live'))
  ->update(['status' => 'paused']);
echo "Paused {$updated} lanes".PHP_EOL;
PHPEOF

# その後: ビジネス側へ連絡 → 原因究明 → 再開判断
```

## 6. 5/22 完走実績から見た「平常時の参照値」

復旧操作の判断材料として、5/22 オークション (70人参加 / 200件 × 1レーン / 2:26 完走 / failed_jobs 0) の実測値を参考にする:

| 指標 | 5/22 完走時の値 | 異常判定の目安 |
| --- | --- | --- |
| tick ログ間隔 | 0.5-1秒ごと | 10秒以上空く |
| countdown worker メモリ | **100,684 KB で完全不変** | 200MB 超え |
| Reverb メモリ | **75,024 KB で完全不変** | 500MB 超え |
| failed_jobs (オークション中) | **0件** | 10件以上の急増 |
| heartbeat age | <5秒 | 30秒超え |
| supervisor worker uptime | 連続稼働 | 数十秒で再起動繰り返し |
| WS接続 | 60-73 (70人想定) | 急減 (半減以下) |
| RDS Threads_connected | ~100 | 250 超え |
| Innodb_row_lock_current_waits | 0 | 5以上 |

## 7. 5/23 オークション (200人想定) の追加注意事項

5/22 比でスケール約3倍 = 未経験ゾーン。以下を念入りに見る:

- **開催直後10分**: 200人接続時の初動が無事か (WS接続が150以上に到達するか)
- **broadcast 量2.5倍** = 商品切替時のフロント体感「やや重い」可能性 (致命的ではない)
- **load avg ピーク**: 4.5 超え 5分間継続 → §3-D 発動
- **notify queue 5,000超え** = お気に入り通知 fan-out 詰まり → §3-C (別 §) で対応

## 10. 30秒で読むフローチャート (印刷推奨)

```
[tick が止まったかも？]
        ↓
   tail -f log で
   tick 出てるか?
        ↓
    ┌─ 出てる → 誤検知、戻る
    │
    ├─ 出てない (30秒未満) → 1分待つ (MonitorAuctionJobs が dispatch するかも)
    │
    └─ 出てない (30秒以上)
            ↓
       ls -la storage/logs/
            ↓
       root 所有あり? → YES → sudo chown ec2-user:ec2-user (これだけで復旧することが多い)
                        ↓
                       NO
                        ↓
       supervisorctl status
            ↓
       worker RUNNING? → NO → restart auction-queue-countdown:*
                        ↓
                       YES
                        ↓
       Cache の heartbeat 確認
            ↓
       heartbeat 古い (>30秒)? → YES → §3-C 強制 re-dispatch
                                 ↓
                                NO
                                 ↓
                            §3-A 順番に確認
                                 ↓
       5分待っても復旧しない → §5 中断判断
```

---

**最重要メッセージ**:
> 多くの「止まった」は **1〜2分で自動回復** します。
> まずは深呼吸、ログ権限を確認、それから supervisor。
> 慌てて全部再起動すると逆にダメージが大きい。
