## 3. 後日の実装スコープ（着手時にここから）

現状コードにGMO連携は存在しない（`grep -riE "gmo|aozora"` ヒットなし）。提出後、以下を実装する。

1. **ルート**: `POST /api/gmo-aozora/webhook`、`GET /api/gmo-aozora/oauth/callback`
2. **OAuthトークン管理**: client_secret_basicでアクセストークン取得・リフレッシュ（自社口座を一度認可）。トークンは安全に永続化
3. **Webhook受信の検証（二重）**:
   - Basic認証: `hash_equals()` で `.env` の user/pass と照合 → 不一致は401（middleware推奨）
   - Signature検証: GMO付与の署名をシークレットで検証
4. **入金消込**: ペイロード（振込入金口座の入金明細）を受け、落札の入金に突合 → 支払い済み更新。支払期限「翌水曜23:59」運用（[[project_payment_deadline_policy]]）と接続
5. **冪等性**: 同一明細の再通知に備え、明細ID等でユニーク制御
6. **ネットワーク**: GMOへのアウトバウンドは本番EC2のEIP固定（IP申告済みのため経路変更時は再申告要）

## 5. GMO API 仕様の要点（仕様書 v1.8.0 から転記・2026-09-24）

### 5.1 ベース URL

| 用途 | 本番 | 開発（GMO 側の開発環境） |
|---|---|---|
| 認可/トークン | `https://api.gmo-aozora.com/ganb/api/auth/v1/` | `https://stg-api.gmo-aozora.com/ganb/api/auth/v1/` |
| 法人 API | `https://api.gmo-aozora.com/ganb/api/corporation/v1/` | `https://stg-api.gmo-aozora.com/ganb/api/corporation/v1/` |
| Webhook 制御 | `https://api.gmo-aozora.com/ganb/api/webhooks/v1/` | `https://stg-api.gmo-aozora.com/ganb/api/webhooks/v1/` |

※ sunabar（個人向けサンドボックス）とは別物。接続試験は GMO が発行する「開発環境」の client_id/secret で `stg-api` を叩く。

### 5.2 OAuth 2.0（Authorization Code）

- 認可: `GET /authorization?response_type=code&scope=...&client_id=...&state=...&redirect_uri=...`（ブラウザで口座保有者がログイン→認可）
- トークン: `POST /token`、`Content-Type: application/x-www-form-urlencoded`、`Authorization: Basic base64(client_id:client_secret)`（client_secret_basic）
  - 新規: `grant_type=authorization_code&code=...&redirect_uri=...`
  - 更新: `grant_type=refresh_token&refresh_token=...`
- 応答: `access_token` / `refresh_token` / `scope` / `token_type=Bearer` / `expires_in`（例: 2592000 秒 = 30 日）
- **API 呼び出しのヘッダは `x-access-token: {access_token}`**（`Authorization: Bearer` は userinfo のみ）
- スコープ（法人・自社口座=「その他の場合」）: `private:account` `private:transfer` `private:bulk-transfer` `private:virtual-account`

### 5.3 接続試験で叩く 4 スコープの最小エンドポイント

| スコープ | エンドポイント | 備考 |
|---|---|---|
| 口座 | `GET /accounts` | 参照のみ。accountId を得る |
| 振込/振替 | `GET /transfer/status?accountId=&queryKeyClass=2&dateFrom=&dateTo=` | 参照のみ。**`POST /transfer/request` は資金移動なので試験では叩かない** |
| 総合振込 | `GET /bulktransfer/status?accountId=&queryKeyClass=2&dateFrom=&dateTo=` | 同上。`POST /bulktransfer/request` は叩かない |
| 振込入金口座 | `POST /va/list`、`GET /va/deposit-transactions?raId=` | 参照のみ |

送金系（`/transfer/request`, `/bulktransfer/request`）はクライアントに実装するが、`Idempotency-Key`(UUID v4) 必須・config で明示的に有効化しない限り呼べないガードを置く。

### 5.4 Webhook（振込入金口座_入金明細通知）

- GMO → 当方 `POST {通知先URL}`、`Content-Type: application/json;charset=UTF-8`
- ヘッダ: `x-access-token`（通知対象ユーザーのアクセストークン）/ `x-webhook-signature`（**client_secret をキーに HMAC-SHA256(body) → Base64**）/ `Authorization: Basic`（当方が申告した user:pass）/ `x-eventType: va-deposit-transaction` / `User-Agent: GMO Aozora Net Bank Notification Service Agent`
- ボディ: `messageId`(19桁・一意) / `timestamp` / `account{raId, raBranchCode, raAccountNumber, raHolderName, baseDate, baseTime}` / `vaTransaction{vaId, transactionDate, valueDate, vaBranchCode, vaAccountNumber, vaAccountNameKana, depositAmount, remitterNameKana, paymentBankName, paymentBranchName, partnerName, remarks?, itemKey}`
- **当社の申請は Basic 認証のみ**（GMO「署名と Basic はどちらか一方」→ 6/25 NEP 回答）。署名ヘッダは来ない前提で、代わりに `x-access-token` と保存済みトークンの一致を検証する（仕様書のセキュリティ対策「アクセストークン」）。
- 応答は **200 のみ成功**。それ以外は指数バックオフで最大 1 時間リトライ → 配信停止状態へ。停止中の明細は `GET /webhooks/v1/unsentlist/va-deposit-transaction`（Basic）で取得、14 日で削除。
- 順序保証なし・重複配信あり → `messageId` で冪等化必須。
- **アクセストークンが失効すると通知も止まる**（失効中の明細は再送されない）→ トークンの定期リフレッシュが生命線。
- 配信開始/停止: `POST /webhooks/v1/subscribe`（Basic = client_id:client_secret）`{"subscribeStatus":"1","eventTypes":[{"eventType":"va-deposit-transaction"}]}`

### 6.1.1 2026-09-29 追加（GMO の接続試験条件への対応）

GMO 小林さんの 9/24 回答で示された条件に合わせて修正した。

| 条件・事実 | 対応 |
|---|---|
| Webhook のセキュリティは Basic 認証のみで申請済み | 署名検証の既定を OFF（`GMO_AOZORA_WEBHOOK_VERIFY_SIGNATURE=false`）。ON にすると全通知が 401 |

### 6.2 消込ルール

1. 通知の `vaId` → `gmo_virtual_accounts.user_id` で落札者を特定（無い/未割当 → `unmatched`）
2. 落札者の未入金（`pending`/`paid`）を **オークション単位** にまとめ、`InvoiceService::buyerTotals` の `grand_total`（税込）を請求額とする
3. 入金額が「いずれか1オークションの請求額」または「全オークション合計」と一致すれば対象確定
4. `gmo_aozora_auto_confirm_payment` ON → `WonItemPaymentService::confirmGroup(… 'bank_transfer', 取引日)` を実行（管理画面の入金確認と同一処理・落札者通知あり）。OFF → `matched` で止めて管理者が `deposits/{id}/confirm`
5. 不一致は `unmatched(amount_mismatch)` として `expected_amount` を残し、管理者が `deposits/{id}/match {won_item_id}` で手動紐付け（同時に口座も割当）

### 6.3 接続試験の手順（ステージング）

前提: GMO から受領した開発環境の client_id / client_secret、Q6 の固定IP・Q11 の redirect_uri・Q16 の通知先URL・Q21/22 の Basic 値が GMO 側に登録済み。

1. `.env`（staging）に `GMO_AOZORA_*` を設定 → `php artisan config:cache`（`sudo -u ec2-user`）
2. `php artisan migrate`
3. `php artisan route:cache`（新ルートは再生成しないと 404 → [[project_route_cache_stale_on_deploy]]）
4. `php artisan gmo-aozora:auth-url` → 表示URLをブラウザで開き、口座保有者が GMO にログイン・認可 → `/admin/settings?gmo_aozora=connected` に戻れば OK
5. `php artisan gmo-aozora:test-connection` → 4スコープすべて OK を確認（GMO 側のログ確認対象）
6. 管理画面設定で `gmo_aozora_webhook_debug=ON` → `POST /api/admin/gmo-aozora/webhook/subscribe {"start":true}` → GMO 開発環境で振込入金口座に入金 → `gmo_deposit_notifications` に行が入るか確認
7. `gmo_aozora_webhook_enabled=ON`、必要なら `gmo_aozora_auto_confirm_payment=ON`。試験後 debug は OFF に戻す
8. 試験後 `php artisan gmo-aozora:export-api-log --from=〈試験開始日〉 --to=〈終了日〉` → `storage/app/gmo-aozora/api-log_*.csv` を接続試験表と一緒に GMO へ提出

※ 事前申請（接続試験表の【事前申請】欄: 期間・実施エンドポイント・対象外項目・アクセス元 IP）をメールで済ませてから実施する（GMO 9/24 回答）。
