## 1. システム構成

### インフラ構成

| コンポーネント | 技術 | 詳細 |
|---|---|---|
| Web / API | AWS EC2 (Amazon Linux 2023) | Auto Scaling Group + ALB |
| DB | MySQL 8.0 | AWS RDS |
| Cache / Queue | Redis (AWS ElastiCache Valkey 8.0) | 3キュー: default / countdown / notifications |
| WebSocket | Laravel Reverb | Supervisor 管理プロセス |
| Storage | AWS S3 | メディアファイル・PDF |
| CDN | AWS CloudFront | 静的ファイル配信 |
| DNS / SSL | Route 53 + ACM | 自動証明書更新 |
| WAF | AWS WAF | DDoS 対策（設定手順: `docs/AWS_WAF_DDoS対策設定手順書.md`） |

### アプリケーション配置

```
/var/www/auction/          # アプリケーションルート
├── app/                   # Laravel アプリケーション
├── public/                # Web 公開ディレクトリ（nginx docroot）
├── storage/logs/          # ログファイル
│   ├── laravel.log
│   └── audit.log
└── .env                   # 環境変数（本番設定）
```

### プロセス管理（Supervisor）

本番環境のバックグラウンドプロセスは **supervisord** で管理しています。

| プロセス名 | 役割 | 設定ファイル |
|---|---|---|
| `queue-default` | 汎用ジョブキュー（メール・通知等） | `/etc/supervisor/conf.d/queue-default.conf` |
| `queue-countdown` | カウントダウン専用キュー（入札・落札） | `/etc/supervisor/conf.d/queue-countdown.conf` |
| `queue-notifications` | 通知専用キュー | `/etc/supervisor/conf.d/queue-notifications.conf` |
| `reverb` | WebSocket サーバー | `/etc/supervisor/conf.d/reverb.conf` |

```bash
# Supervisor 全体の状態確認
sudo supervisorctl status

# 個別プロセス再起動
sudo supervisorctl restart queue-default
sudo supervisorctl restart queue-countdown
sudo supervisorctl restart queue-notifications
sudo supervisorctl restart reverb

# 全プロセス再起動
sudo supervisorctl restart all
```

## 2. 日常運用

### ヘルスチェック

```bash
# ALB ヘルスチェックエンドポイント（DB + Redis 疎通確認）
curl https://medaka-auction.jp/api/health
# 期待値: {"status":"ok"}
```

### ログ確認

```bash
# アプリケーションログ
sudo tail -f /var/www/auction/storage/logs/laravel.log

# 監査ログ
sudo tail -f /var/www/auction/storage/logs/audit.log

# キューワーカーログ（Supervisor 経由）
sudo tail -f /var/log/supervisor/queue-default.log
sudo tail -f /var/log/supervisor/queue-countdown.log
sudo tail -f /var/log/supervisor/queue-notifications.log

# Reverb（WebSocket）ログ
sudo tail -f /var/log/supervisor/reverb.log

# nginx アクセスログ
sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log
```

### キュー監視

```bash
# キューの状態確認
cd /var/www/auction && php artisan queue:monitor redis:default,countdown,notifications

# 失敗ジョブの確認
php artisan queue:failed

# 失敗ジョブの再実行（全件）
php artisan queue:retry all

# 特定ジョブの再実行
php artisan queue:retry {job_id}

# 失敗ジョブの削除
php artisan queue:flush
```

### キャッシュ管理

```bash
cd /var/www/auction

# 設定キャッシュクリア（環境変数変更後に必須）
php artisan config:clear

# ルートキャッシュクリア
php artisan route:clear

# ビューキャッシュクリア
php artisan view:clear

# システム設定キャッシュクリア
php artisan cache:forget system_settings

# 全キャッシュ再構築（デプロイ後に実行）
php artisan config:cache && php artisan route:cache && php artisan view:cache
```

## 3. スケジュールタスク

crontab（`crontab -l -u nginx` または `crontab -l`）に以下が設定されています。

```cron
* * * * * cd /var/www/auction && php artisan schedule:run >> /dev/null 2>&1
```

| タスク | スケジュール | 説明 |
|---|---|---|
| `announcements:publish-scheduled` | 毎分 | お知らせ自動公開 |
| `auctions:start-scheduled` | 毎分 | オークション自動開始 |
| `auctions:monitor-jobs` | 毎分 | カウントダウンジョブ監視 |
| `SendPaymentReminderJob` | 30分毎 | 未入金リマインダー送信 |
| `SendAuctionPreviewJob` | 毎日 18:00 | 翌日開催の予告通知 |
| `reports:generate weekly` | 毎週月曜 09:00 | 週次レポート生成 |
| `reports:generate monthly` | 毎月1日 09:00 | 月次レポート生成 |

```bash
# スケジューラの手動実行（確認用）
cd /var/www/auction && php artisan schedule:run

# 次回実行予定の確認
php artisan schedule:list
```

## 4. データベース管理

### バックアップ

```bash
# 手動バックアップ（RDS の場合は AWS コンソールからスナップショット推奨）
mysqldump -h auction-db-prod.cluster-abc123xyz.ap-northeast-1.rds.amazonaws.com -u auction_admin -p auction_db > backup_$(date +%Y%m%d_%H%M%S).sql

# バックアップファイルを S3 へ保存
aws s3 cp backup_$(date +%Y%m%d).sql s3://your-backup-bucket/db/
```

## 5. デプロイ手順

```bash
# 作業ディレクトリへ移動
cd /var/www/auction

# 1. コード取得
git pull origin main

# 2. PHP 依存パッケージ更新
composer install --no-dev --optimize-autoloader

# 3. フロントエンドビルド
npm ci && npm run build

# 4. マイグレーション
php artisan migrate --force

# 5. キャッシュ最適化
php artisan config:cache
php artisan route:cache
php artisan view:cache

# 6. キューワーカー再起動
php artisan queue:restart

# 7. Reverb（WebSocket）再起動
sudo supervisorctl restart reverb

# 8. 動作確認
curl https://medaka-auction.jp/api/health
```

### ゼロダウンタイムデプロイ（推奨手順）

ALB の Target Group を切り替える Blue/Green 方式を推奨します。

1. 新 EC2 インスタンス起動 → コード・依存関係セットアップ
2. ヘルスチェック通過確認
3. ALB Target Group に新インスタンス追加
4. 旧インスタンスを Target Group から除外
5. 旧インスタンスのドレイン完了を確認後、停止

## 6. トラブルシューティング

### WebSocket 接続不可

1. Reverb プロセスの起動確認: `sudo supervisorctl status reverb`
2. ポート 8080 のセキュリティグループ設定確認
3. ALB の WebSocket（HTTP/1.1 upgrade）対応設定確認
4. ログ確認: `sudo tail -f /var/log/supervisor/reverb.log`
5. 手動起動テスト: `cd /var/www/auction && php artisan reverb:start`

### キューが滞留

1. キュー長確認: `php artisan queue:monitor redis:default,countdown,notifications`
2. ワーカープロセスの生存確認: `sudo supervisorctl status`
3. Redis 疎通確認: `redis-cli -h auction-cache-prod.abc123.ng.0001.apne1.cache.amazonaws.com ping`
4. ワーカー再起動: `sudo supervisorctl restart queue-default`
5. 失敗ジョブ確認: `php artisan queue:failed`

### 500 エラー

1. ログでエラー内容確認: `sudo tail -100 /var/www/auction/storage/logs/laravel.log`
2. `storage/` ディレクトリの書き込み権限確認: `ls -la /var/www/auction/storage/`
3. `.env` の設定確認（特に DB_HOST, REDIS_HOST）
4. 設定キャッシュクリア: `php artisan config:clear`
5. nginx エラーログ確認: `sudo tail -f /var/log/nginx/error.log`

### メール送信失敗

1. `.env` のメール設定確認（MAIL_MAILER, SMTP 設定）
2. キューワーカーの稼働確認: `sudo supervisorctl status queue-default`
3. 失敗ジョブ確認: `php artisan queue:failed`
4. 手動再実行: `php artisan queue:retry all`

### DB 接続エラー

1. RDS エンドポイントへの疎通確認: `mysql -h auction-db-prod.cluster-abc123xyz.ap-northeast-1.rds.amazonaws.com -u auction_admin -p --connect-timeout=5`
2. セキュリティグループで EC2 → RDS (3306) が許可されているか確認
3. `.env` の DB_HOST, DB_PASSWORD を確認
4. RDS の CPU / メモリ使用率を CloudWatch で確認

### ストレージ（S3）エラー

1. IAM ロール（EC2 に付与）の S3 権限確認
2. `.env` の AWS_BUCKET, AWS_DEFAULT_REGION 確認
3. `php artisan storage:link` でシンボリックリンク再作成

## 7. スケーリング

### 自動スケーリング（管理画面から）

- 管理画面 → インフラスケーリング
- **スケールアップ**: EC2 Auto Scaling Group の desired capacity を増加（Lambda 経由）
- **スケールダウン**: EC2 Auto Scaling Group の desired capacity を減少
- スケーリング実行後は Supervisor / キューワーカーの稼働を確認

### 手動スケーリング（AWS CLI）

```bash
# Auto Scaling Group の現在の desired capacity 確認
aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names {group-name} \
  --query 'AutoScalingGroups[0].DesiredCapacity'

# 手動でスケールアップ（desired を 3 に変更）
aws autoscaling set-desired-capacity \
  --auto-scaling-group-name {group-name} \
  --desired-capacity 3
```

### オークション開催時の推奨構成

| モード | EC2 台数 | 目安 |
|---|---|---|
| 通常時 | 1〜2 台 | 平常稼働 |
| オークション前後 | 2〜3 台 | 開催1時間前にスケールアップ |
| オークション本番 | 3〜4 台 | 同時接続 500 人対応 |

### 負荷テスト実績

- **同時接続 500 人**: 負荷テスト済み（レポート: `src/docs/同時接続500人_負荷耐性レポート.md`）

## 9. 監視設定

CloudWatch アラーム設定（詳細: `src/docs/CloudWatch監視設定手順書.md`）

| メトリクス | 閾値 | アクション |
|---|---|---|
| EC2 CPU 使用率 | > 80% | SNS 通知 + Auto Scaling |
| EC2 メモリ使用率 | > 85% | SNS 通知 |
| RDS CPU 使用率 | > 70% | SNS 通知 |
| ALB レスポンスタイム | > 3秒 | SNS 通知 |
| ALB 5xx エラー率 | > 1% | SNS 通知 |
| WAF ブロック数 | > 1000件/5分 | SNS 通知 |
| Redis メモリ使用率 | > 80% | SNS 通知 |
| キュー滞留数 | > 1000件 | SNS 通知 |

```bash
# CloudWatch エージェントの状態確認
sudo systemctl status amazon-cloudwatch-agent

# エージェント再起動
sudo systemctl restart amazon-cloudwatch-agent
```
