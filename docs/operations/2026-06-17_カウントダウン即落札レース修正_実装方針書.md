## 0. 一行サマリ

入札カウントダウンが **0 になる瞬間ちょうどに入る入札**で、tick の落札確定処理と入札由来の価格上昇処理が lane キャッシュ上で競合し、**freeze→bidding の新ラウンド（8秒）を飛ばして即落札**してしまう。tick の落札判定を `bid_inflight` ロック + items 行ロック下で再評価することで直列化し、全ての入札系 writer との競合を閉じる。

---

## 1. 事象（再現された実データ）

2026-06-05 11:58、lane 74 / item 1757 のログと bid_events:

```
11:58:07  Pre-bid started: item 1757
11:58:14  bidding started: item 1757, countdown=8s     ← 8秒 → 自然終了は 11:58:22 ちょうど
11:58:22  handlePriceIncrement: item=1757, 50→55, activeCount=2, lastBidder=812
11:58:22  Auto-left: item=1757, left=989, holder=812
11:58:22  Freeze countdown started: lane 74, 2s          ← freeze は 11:58:24 まで続くはず
11:58:23  Item 1757 sold                                 ← なのに freeze 中に確定
```

```
bid_participants: 812 active=Y (11:58:22〜)  /  989 active=N (11:58:17〜11:58:22 離脱)
price_events:     11:58:22 auto_increment 50→55 / 11:58:23 item_sold
bid_limit_prices: なし（指値は無関係）
```

- 期待挙動: 812 入札 → 55円 → freeze 2秒 → **bidding 8秒（誰でも応戦可）** → 無入札なら 812 落札
- 実挙動: 989 を離脱させた上、bidding 8秒の新ラウンドが丸ごと消え、**freeze 中に 812 が55円で即落札**

フロントは価格55とリセットされたカウント秒（MAX付近）を一瞬受信→直後に ItemSold を受信するため、**「秒数MAXで即終了」**に見える。

## 2. 根本原因

`CountdownService::tick()`（[bidding フェーズ L277-342](../../app/Services/CountdownService.php#L277)）の落札確定判定が、**ロックなしの lane キャッシュ read-modify-write** であることに起因する lost-update。

入札着弾が `14 + 8 = 11:58:22`（カウント0の瞬間）だったため、以下が interleave した:

```
tick:  state を読む（phase=bidding, remaining≈0）          ← 古い state
join:  handleImmediatePriceIncrement
         → 50→55 / 989 離脱 / startFreezeCountdown(freeze 2s) をキャッシュに書く / commit
tick:  remaining<=0 判定 → active を数える（L278）= 1（812のみ、989は離脱済み）
         → activeBidderCount>=2 でないので handleCountdownEnd
         → 812 を 55円で即落札。join が書いた freeze は stopCountdown で破棄
```

ポイント:
- tick の `$activeBidderCount` は **L278（bidding ブロック先頭）で1回だけ**読まれ、その後の終了分岐まで再取得されない
- tick の落札経路は join が握る `bid_inflight:item:{id}` ロック（[JoinBidAction L88](../../app/Actions/Bid/JoinBidAction.php#L88)）を**取らない**ため、HTTP 側の入札処理と直列化されない
- 指値・価格計算ロジックは正常。**カウント0ちょうどの入札という境界条件**でのみ発火する concurrency バグ

## 3. 修正方針

### 3.0 採用方式（実装確定版: Option A = Redis ロックのみ）

実装直前の精査で、当初案（Option B: tick に items 行ロックを追加）に2つの問題が判明したため、**Redis `bid_inflight` ロックのみで直列化する Option A を採用**した（2026-06-17 実装済み）。

| 当初案 Option B の問題 | 採用 Option A での回避 |
| --- | --- |
| 単一スレッドの tick が `lockForUpdate` 待ちに入ると **全レーンの tick が巻き添えで停止**しうる（150名負荷で致命的） | tick に DB ロックを一切足さない。追加は非ブロッキング Redis 操作のみ |
| `handleCountdownEnd` は意図的に `moveToNextItem` を**トランザクション外**で実行（[L946-948](../../app/Services/CountdownService.php#L946) のキャッシュ不整合防止）。外側 tx で包むと設計破壊 | finalize を tx で包まない。`handleCountdownEnd` のトランザクション構造は無改造 |

Option A でも**今回の事故（JoinBidAction のバズビーター）は完全に閉じる**。Join は `bid_inflight` を価格上昇 commit まで保持するため、tick がロックを取れた時点で Join は「完全に終わっている（freeze がキャッシュに見える）」か「まだ始まっていない（確定後に status=sold で正当拒否）」のいずれかになる。

### 3.1 基本アイデア

tick の落札確定判定を、JoinBidAction と**同一の `bid_inflight:item:{id}` Redis ロック**の下で行い、ロック取得後に lane キャッシュと active 数を読み直す。これにより Join / Leave（どちらも同ロックを取る）と直列化され、**中間状態が観測不能**になる:

- (a) 競合相手が完全に commit 済み → freeze がキャッシュに見える → tick は確定を中止
- (b) 競合相手がまだ status を見ていない → tick の確定後に status=sold を見て正当に中止
- (c) tick がロックを取れない（HTTP 側が処理中）→ 確定を見送り、次tickで再判定

> **残課題（既知）**: 指値設定の live auto-bid（[SetBidLimitAction](../../app/Actions/Bid/SetBidLimitAction.php#L104)）は `bid_inflight` を取らないため、「live 中の指値設定がカウント0ちょうどの tick に着弾」する稀ケースは Option A では直列化されない。発生頻度は極小（指値設定の commit と finalize の COUNT が同一 0.5秒に重なる必要）かつ重大度も低い（誤落札ではなく late 指値の取りこぼし）。本番投入後の follow-up とし、必要なら SetBidLimit 側に同ロックを足すか item 行ロックで対処する。

### 3.2 既存分岐は活かす（最小差分）

落札本体（`handleCountdownEnd` / `FinalizeBidAction`）は **無改造**。
[tick L312](../../app/Services/CountdownService.php#L312) の `if ($activeBidderCount >= 2)` 分岐も**そのまま活かし**、その判定の入力（active 数・lane state）を **ロック下で読み直す**だけにする。L278 の古い値を差し替える発想。

### 3.3 実装コード（適用済み）

`tick()` の bidding フェーズ、`if ($state['remaining_seconds'] <= 0) { ... }` ブロックを以下に置換した（[CountdownService.php](../../app/Services/CountdownService.php#L311)）:

```php
if ($state['remaining_seconds'] <= 0) {
    // ── ① bid_inflight 非ブロッキング取得（join/leave と同一キー）──
    //    取れない = HTTP 側が入札処理中。確定を見送り次tickで再判定。
    //    ※ block() は使わない（全レーン逐次処理ゆえ待つと他レーンが止まる）
    //    ※ 見送り時に $state を Cache::put しない（直前 freeze の破壊防止）
    $finalizeLock = Cache::lock("bid_inflight:item:{$item->id}", 5);
    if (!$finalizeLock->get()) {
        return ['action' => 'finalize_deferred', 'lane_id' => $laneId];
    }

    try {
        // ── ② ロック取得後に lane キャッシュを再読込（freeze の lost-update 検知）──
        $freshState = Cache::get($this->getCacheKey($laneId));
        if (!$freshState
            || ($freshState['phase'] ?? '') !== 'bidding'
            || ($freshState['item_id'] ?? null) !== $item->id
            || empty($freshState['is_running'])) {
            return ['action' => 'finalize_aborted_state_changed', 'lane_id' => $laneId];
        }

        // ── ③ 商品状態を最新化（他経路で確定済みなら抜ける）──
        $freshItem = $item->fresh();
        if (!$freshItem || $freshItem->status !== 'live') {
            $this->stopCountdown($laneId);
            return ['action' => 'finalize_skip_not_live', 'lane_id' => $laneId];
        }

        // ── ④ active をロック下で再カウント（L278 の古い値を破棄）──
        $freshCount = BidParticipant::forItem($freshItem->id)->active()->count();

        if ($freshCount >= 2) {
            try {
                $lastBidder = $freshState['last_bidder_user_id'] ?? null;
                $this->handlePriceIncrement($lane, $freshItem, $auction, $freshCount, $lastBidder);
            } catch (\Exception $e) {
                Log::error("Price increment FAILED lane {$laneId}: ... - starting freeze");
                $this->startFreezeCountdown($lane);
            }
            return ['action' => 'price_increment', 'lane_id' => $laneId];
        }

        try {
            return $this->handleCountdownEnd($lane, $freshItem, $auction, $freshCount);
        } catch (\Exception $e) {
            // recovery で bidding を書き戻さない（freeze 上書き防止）。
            // handleCountdownEnd は冒頭 stopCountdown 済みなので次tickの startCountdown 復旧経路が拾う。
            Log::error("Countdown end FAILED lane {$laneId}: ... - relying on next-tick recovery");
            return ['action' => 'finalize_error', 'lane_id' => $laneId];
        }
    } finally {
        $finalizeLock->release();
    }
}
```

> 注: DB トランザクションでは包まない。`handlePriceIncrement` / `handleCountdownEnd` は内部で独自に `DB::beginTransaction` + `lockForUpdate` し、`handleCountdownEnd` は `moveToNextItem` を tx 外で実行する既存構造をそのまま維持する。直列化は `bid_inflight` Redis ロックのみで担保する。

## 4. 実装ルール（違反すると逆に壊す）

| # | ルール | 破った場合に起きる不具合 |
| --- | --- | --- |
| R1 | tick 側のロックは `->get()`（非ブロッキング）。`block()` 禁止 | 単一ジョブが全レーンを逐次処理しているため、複数レーン同時バズビーターで **全レーン tick が待ち停止** |
| R2 | 中止・見送り時は **clean return**。確定失敗時の recovery で bidding を書き戻さない | 旧 recovery が bidding=8秒で **直前 freeze を上書き破壊** |
| R3 | 中止・見送り時に **古い `$state` を `Cache::put` しない** | join が書いた freeze を stale な bidding-0秒で上書き → 即落札 **再発** |
| R4 | ロックキーは `bid_inflight:item:{$item->id}` で **join/leave と完全一致** | 直列化されず修正が無意味化 |
| R5 | `release()` は必ず `finally` で。TTL 5s 維持 | 確定中の例外でロック残留 → その item への入札が最大5秒「処理中です」 |
| R6 | finalize は **DB トランザクションで包まない**（行ロックを tick に足さない） | tick が行ロック待ちで全レーン停止／`moveToNextItem` の tx 外実行が壊れる |

## 5. 影響範囲・副作用検証

| 経路 | 競合時の挙動 | 評価 |
| --- | --- | --- |
| バズビーター入札（今回） | join 先勝ち→freeze→8秒新ラウンド／tick 先勝ち→後続 join は `status!=='live'` で正当拒否 | ✅ 仕様通り |
| 通常落札／流札（競合なし） | ロック即取得 → Redis GET + COUNT 各1回追加のみ。確定は item ごと1回 | ✅ ホットパス無変更 |
| 入札離脱 LeaveBidAction | 同キー `block(0.3)`（[L45](../../app/Actions/Bid/LeaveBidAction.php#L45)）+ items 行ロック（[L59](../../app/Actions/Bid/LeaveBidAction.php#L59)）。tick 保持は数十ms | ✅ 改善（現状未同期） |
| 指値設定 auto-bid | `bid_inflight` を取らないが items 行ロックを取り `status==='live'` 再確認（[L104](../../app/Actions/Bid/SetBidLimitAction.php#L104)）→ 行ロックで直列化 | ✅ ②層で閉じる |
| count=0 流札 | 再カウントで race-safe 化。**既存の「入札者いるのに流札」バグも同時解消** | ✅ |
| 再カウントで 2+ | 価格上昇経路へ（既存ロジック） | ✅ |
| 一時停止／世代交代 | ③の `is_running` 等で中止 | ✅ 影響なし |
| デッドロック | 全経路「bid_inflight→items」順で統一。サイクルなし | ✅ |
| ロック残留（HTTP 側プロセス死） | TTL 5秒で自動解放。その間 tick は見送り（remaining=0 broadcast 継続）→ 5秒後確定 | ⚠️ 軽微・許容 |
| キャッシュ null の極稀ケース | ③で中止 → recovery（[L291](../../app/Services/CountdownService.php#L291)）が8秒再生成。誤落札なし | ⚠️ 良性 |

## 5.5 負荷影響評価（次回 ≈150名規模）

結論: **150名規模で本変更が新たなボトルネックになる可能性は低い**。根拠:

1. **追加処理はホットパスではない**: 新コードは `remaining<=0`（商品の確定 or 終端価格上昇）の瞬間のみ実行。0.5秒ごとの tick 本体（デクリメント + broadcast）は無変更。発火頻度は lane あたり数秒に1回、2〜3レーンでも毎秒数回程度で、1回あたり Redis SETNX + GET + COUNT 各1回のみ。
2. **新たな DB ロックを tick に足していない**（Option A）。よって「単一スレッド tick が行ロック待ちで全レーン停止」リスクは**構造的に存在しない**。
3. **使用ロックは既存の全入札共通ロック**。`bid_inflight:item:{id}` は JoinBidAction が今でも全入札で取得済み。tick は**非ブロッキング `get()`** で参加するため、入札処理に新たな待ち行列を作らない（取れなければ見送るだけ）。
4. **競合下の挙動はむしろ正しい**: 入札が密に飛ぶ間は tick が確定を見送り、入札が途切れた瞬間に確定 = 「混んでいる間は閉じない」望ましい挙動。
5. **150名は計画済み範囲内**: 5/22（70名・1レーン完走・failed_jobs 0）と 5/23 想定（200名・2レーン）の間。Reverb broadcast 量・notify fan-out・price increment の行ロック競合という真の律速はいずれも無変更。

### 投入前の必須確認（ステージング負荷再現）

`load-tests/` で 150〜200名相当を流し、5/22 baseline と比較する。特に:

| 指標 | 正常値（5/22） | 異常判定 |
| --- | --- | --- |
| countdown worker メモリ | 100,684 KB で不変 | 増加トレンド |
| tick ログ間隔 | 0.5–1秒 | 10秒以上の空き |
| `Innodb_row_lock_current_waits` | 0 | 5以上 |
| failed_jobs（開催中） | 0 | 急増 |
| `finalize_deferred` の連発 | 終盤に散発 | 同一 item で長時間連続（starvation 兆候） |

終盤の連続落札（複数 item が短時間で `remaining<=0`）で tick が詰まらないことを重点確認する。

## 7. テスト方針

### 7.1 ユニット／結合
- `CountdownService` の finalize 分岐に対し、`Cache::lock` をモックして以下を検証:
  - ロック取得不可 → `finalize_deferred` を返し **state を書き換えない**
  - ③で phase=freeze → `finalize_aborted_state_changed`、**Cache::put が呼ばれない**
  - ④で count=2 → `handlePriceIncrement` 呼出（finalize しない）
  - ④で count=1 → 正常落札
  - ④で count=0 → 正常流札

### 7.2 競合再現（最重要）
- bidding remaining=0 の直前に JoinBidAction を並行実行し、**落札ではなく freeze→8秒新ラウンド**になることを確認
- 逆順（先に tick 確定）で、後続 join が `status!=='live'` 拒否を返すことを確認

### 7.3 リグレッション
- 既存のカウントダウン進行・商品切替・指値・一時停止/再開のテストが全て green
- 負荷試験（`load-tests/`）で 120名規模の tick 安定（メモリ不変・failed_jobs 0）を確認
