## 0. 一行サマリ

入札カウントダウンが **0 になる瞬間ちょうどに入る入札**で、tick の落札確定処理と入札由来の価格上昇処理が lane キャッシュ上で競合し、**freeze→bidding の新ラウンド（8秒）を飛ばして即落札**してしまう。tick の落札判定を `bid_inflight` ロック + items 行ロック下で再評価することで直列化し、全ての入札系 writer との競合を閉じる。

---

## 1. 事象（再現された実データ）

2026-06-05 11:58、lane 74 / item 1757 のログと bid_events:

```
11:58:07  Pre-bid started: item 1757
11:58:14  bidding started: item 1757, countdown=8s     ← 8秒 → 自然終了は 11:58:22 ちょうど
11:58:22  handlePriceIncrement: item=1757, 50→55, activeCount=2, lastBidder=812
11:58:22  Auto-left: item=1757, left=989, holder=812
11:58:22  Freeze countdown started: lane 74, 2s          ← freeze は 11:58:24 まで続くはず
11:58:23  Item 1757 sold                                 ← なのに freeze 中に確定
```

```
bid_participants: 812 active=Y (11:58:22〜)  /  989 active=N (11:58:17〜11:58:22 離脱)
price_events:     11:58:22 auto_increment 50→55 / 11:58:23 item_sold
bid_limit_prices: なし（指値は無関係）
```

- 期待挙動: 812 入札 → 55円 → freeze 2秒 → **bidding 8秒（誰でも応戦可）** → 無入札なら 812 落札
- 実挙動: 989 を離脱させた上、bidding 8秒の新ラウンドが丸ごと消え、**freeze 中に 812 が55円で即落札**

フロントは価格55とリセットされたカウント秒（MAX付近）を一瞬受信→直後に ItemSold を受信するため、**「秒数MAXで即終了」**に見える。

---

## 2. 根本原因

`CountdownService::tick()`（[bidding フェーズ L277-342](../../app/Services/CountdownService.php#L277)）の落札確定判定が、**ロックなしの lane キャッシュ read-modify-write** であることに起因する lost-update。

入札着弾が `14 + 8 = 11:58:22`（カウント0の瞬間）だったため、以下が interleave した:

```
tick:  state を読む（phase=bidding, remaining≈0）          ← 古い state
join:  handleImmediatePriceIncrement
         → 50→55 / 989 離脱 / startFreezeCountdown(freeze 2s) をキャッシュに書く / commit
tick:  remaining<=0 判定 → active を数える（L278）= 1（812のみ、989は離脱済み）
         → activeBidderCount>=2 でないので handleCountdownEnd
         → 812 を 55円で即落札。join が書いた freeze は stopCountdown で破棄
```

ポイント:
- tick の `$activeBidderCount` は **L278（bidding ブロック先頭）で1回だけ**読まれ、その後の終了分岐まで再取得されない
- tick の落札経路は join が握る `bid_inflight:item:{id}` ロック（[JoinBidAction L88](../../app/Actions/Bid/JoinBidAction.php#L88)）を**取らない**ため、HTTP 側の入札処理と直列化されない
- 指値・価格計算ロジックは正常。**カウント0ちょうどの入札という境界条件**でのみ発火する concurrency バグ

---

## 3. 修正方針

### 3.1 基本アイデア

tick の落札確定判定を、既存の全入札系 writer が従う不変条件の上に乗せる:

> **不変条件**（全 writer で確認済み）:
> 1. 入札系 writer（Join / Leave / 指値設定 / 価格上昇）は **items 行ロックを先に取る**
> 2. freeze キャッシュは **commit 前に書く**
> 3. ロック取得後に **status==='live' を再確認**する

これにより、tick が `bid_inflight` ロック + items 行ロックを取った瞬間、競合相手は次の二択しか取り得ず、**中間状態が観測不能**になる:

- (a) 完全に commit 済み → freeze がキャッシュに見える → tick は確定を中止
- (b) まだ status を見ていない → tick の確定後に status=sold を見て正当に中止

### 3.2 既存分岐は活かす（最小差分）

落札本体（`handleCountdownEnd` / `FinalizeBidAction`）は **無改造**。
[tick L312](../../app/Services/CountdownService.php#L312) の `if ($activeBidderCount >= 2)` 分岐も**そのまま活かし**、その判定の入力（active 数・lane state）を **ロック下で読み直す**だけにする。L278 の古い値を差し替える発想。

### 3.3 擬似コード

`tick()` の bidding フェーズ、`if ($state['remaining_seconds'] <= 0) { ... }` ブロックを以下に置換:

```php
if ($state['remaining_seconds'] <= 0) {
    // ── ① bid_inflight 非ブロッキング取得（join/leave と同一キー）──
    //    取れない = HTTP 側が入札処理中。今 tick は確定を見送り、0.5秒後に再判定。
    //    ※ block() は使わない（全レーン逐次処理ゆえ待つと他レーンが止まる）
    $finalizeLock = Cache::lock("bid_inflight:item:{$item->id}", 5);
    if (!$finalizeLock->get()) {
        // state は触らずそのまま保存（remaining は 0 のまま broadcast 継続）
        Cache::put($this->getCacheKey($laneId), $state, self::CACHE_TTL);
        return ['action' => 'finalize_deferred', 'lane_id' => $laneId];
    }

    try {
        // ── ② items 行ロックを取り、最新状態を確定 ──
        $locked = Item::where('id', $item->id)->lockForUpdate()->first();
        if (!$locked || $locked->status !== 'live') {
            // 他経路が確定済み。カウントダウンを止めて抜ける（次商品は他経路が進める）
            $this->stopCountdown($laneId);
            return ['action' => 'finalize_skip_not_live', 'lane_id' => $laneId];
        }

        // ── ③ ロック取得後に lane キャッシュを再読込（freeze の lost-update 検知）──
        $freshState = Cache::get($this->getCacheKey($laneId));
        if (!$freshState
            || ($freshState['phase'] ?? '') !== 'bidding'
            || ($freshState['item_id'] ?? null) !== $item->id
            || empty($freshState['is_running'])) {
            // 直前に freeze 等が開始された／状態が変わった → 確定せず通常フローに戻す
            // ※ 古い $state を put し直さないこと（freeze を壊すため何も書かない）
            return ['action' => 'finalize_aborted_state_changed', 'lane_id' => $laneId];
        }

        // ── ④ active をロック下で再カウント（L278 の古い値を破棄）──
        $freshCount = BidParticipant::forItem($locked->id)->active()->count();

        if ($freshCount >= 2) {
            // 2人目が滑り込み済み → 確定せず価格上昇経路へ（既存ロジック）
            $lastBidder = $freshState['last_bidder_user_id'] ?? null;
            $this->handlePriceIncrement($lane, $locked, $auction, $freshCount, $lastBidder);
            return ['action' => 'price_increment', 'lane_id' => $laneId];
        }

        // ── 確定（既存の handleCountdownEnd をそのまま使用）──
        //    handleCountdownEnd 内は FinalizeBidAction が status='live' を再検査するため二重に安全
        return $this->handleCountdownEnd($lane, $locked, $auction, $freshCount);

    } catch (\Exception $e) {
        // 既存の recovery と同等。ただし freeze を壊さないため bidding 上書きはしない。
        Log::error("Finalize race-guard error lane {$laneId}: {$e->getMessage()}");
        return ['action' => 'finalize_error', 'lane_id' => $laneId];
    } finally {
        $finalizeLock->release();
    }
}
```

> 注: `handlePriceIncrement` / `handleCountdownEnd` は内部で独自に `DB::beginTransaction` + `lockForUpdate` する。②で取得した行ロックと同一接続・同一行なので savepoint ネストとなり、外側ロックは最外 commit まで保持される（正しく直列化される）。afterCommit フック（ItemSold broadcast 等）は最外 commit 後に発火する。

## 4. 実装ルール（違反すると逆に壊す）

| # | ルール | 破った場合に起きる不具合 |
| --- | --- | --- |
| R1 | tick 側のロックは `->get()`（非ブロッキング）。`block()` 禁止 | 単一ジョブが全レーンを逐次処理しているため、複数レーン同時バズビーターで **全レーン tick が行ロック待ち停止** |
| R2 | 中止・見送り時は **clean return**。例外を投げない | 既存 recovery catch（[L329-334](../../app/Services/CountdownService.php#L329)）が bidding=8秒で **freeze を上書き破壊** |
| R3 | 中止・見送り時に **古い `$state` を `Cache::put` しない** | join が書いた freeze を stale な bidding-0秒で上書き → 即落札 **再発** |
| R4 | ロックキーは `bid_inflight:item:{$item->id}` で **join/leave と完全一致** | 直列化されず修正が無意味化 |
| R5 | `release()` は必ず `finally` で。TTL 5s 維持 | 確定中の例外でロック残留 → その item への入札が最大5秒「処理中です」 |
| R6 | 行ロック取得後に **`status==='live'` を再確認** | 他経路の確定後に二重確定 |

## 7. テスト方針

### 7.1 ユニット／結合
- `CountdownService` の finalize 分岐に対し、`Cache::lock` をモックして以下を検証:
  - ロック取得不可 → `finalize_deferred` を返し **state を書き換えない**
  - ③で phase=freeze → `finalize_aborted_state_changed`、**Cache::put が呼ばれない**
  - ④で count=2 → `handlePriceIncrement` 呼出（finalize しない）
  - ④で count=1 → 正常落札
  - ④で count=0 → 正常流札

### 7.2 競合再現（最重要）
- bidding remaining=0 の直前に JoinBidAction を並行実行し、**落札ではなく freeze→8秒新ラウンド**になることを確認
- 逆順（先に tick 確定）で、後続 join が `status!=='live'` 拒否を返すことを確認

### 7.3 リグレッション
- 既存のカウントダウン進行・商品切替・指値・一時停止/再開のテストが全て green
- 負荷試験（`load-tests/`）で 120名規模の tick 安定（メモリ不変・failed_jobs 0）を確認
