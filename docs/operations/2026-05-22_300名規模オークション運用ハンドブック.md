## 0. このハンドブックの目的

本オークションは以下の点で過去最大規模:
- **同時接続 300名相当** (過去ガイドの想定は 200名)
- **1レーン構成で 1商品に入札が集中する構造** (12レーン分散ではない)
- **200出品 × 推定2.5-4時間** (過去最長は 58分台)

これらに対応するため事前にインフラ・アプリ設定を強化済み (§1)、当日は監視と即応で残リスクを吸収する (§2)、何かあれば §3 のプレイブックで復旧する。

## 2. 当日監視体制

### 2-1. 監視 5窓 (開催開始前から終了まで常時表示)

別端末 (tmux / 複数ターミナル) で同時に開く。

#### 窓 1: tick 心拍 (最重要)
```bash
sudo tail -f /var/www/auction/storage/logs/laravel.log | grep -E "countdown\.job|ProcessAuctionCountdown|tick"
```
- **正常**: 数秒おきに何らかの出力
- **異常**: 10秒以上ログが途切れる → §3-A プレイブック発動

#### 窓 2: notify キュー深さ
```bash
watch -n 5 'redis-cli -h <valkey-endpoint> LLEN queues:notify'
```
- **正常**: 100以下で推移
- **警戒**: 2,000超
- **異常**: 5,000超 → §3-C プレイブック発動

#### 窓 3: failed_jobs
```bash
watch -n 10 'sudo -u ec2-user php /var/www/auction/artisan queue:failed | head -20'
```
- **正常**: `No failed jobs!`
- **異常**: countdown 系が積まれる → §3-A プレイブック発動

#### 窓 4: Reverb プロセスメモリ
```bash
watch -n 60 'ps -o pid,rss,%mem,etime,cmd -p $(pgrep -f reverb:start) | head -3'
```
- **正常**: RSS 200MB以下で推移
- **警戒**: RSS 500MB超
- **異常**: RSS 1GB超 → §3-B プレイブック (再起動)

#### 窓 5: php-fpm アクティブ worker 数
```bash
watch -n 5 'ps aux | grep "php-fpm: pool" | grep -v grep | wc -l'
```
- **正常**: 25-80 で推移
- **警戒**: 90以上が10秒以上継続
- **異常**: 100張り付き継続 → §3-E プレイブック発動

### 2-2. 警戒シグナルと初動マトリクス

| シグナル | 検知窓 | 初動 |
| --- | --- | --- |
| tick ログ10秒以上途切れ | 窓1 | §3-A |
| failed_jobs に countdown 系積まれた | 窓3 | §3-A |
| notify キュー 5,000超 | 窓2 | §3-C |
| Reverb メモリ 1GB超 | 窓4 | §3-B |
| Reverb プロセス消失 | 窓4 (空欄) | §3-B |

| 「価格が更新されました」エラー多発 (ユーザー報告) | - | §3-D |

## 3. 障害時の復旧プレイブック

> **大原則**: 止まったライブオークションは「再起動」より「気づくこと」が9割。
> 検知が早ければほとんどの故障は1-3分で復旧できる。

### 3-A. tick が止まった (countdown 全停止)

最頻原因: ログ書き込み権限破壊 / countdown worker ハング

```bash
# Step 1: countdown ジョブの状態確認
sudo -u ec2-user php /var/www/auction/artisan queue:failed | grep -i countdown

# Step 2: supervisor で countdown worker の状態確認
sudo supervisorctl status | grep countdown

# Step 3: ログ権限確認 (典型原因) / root所有ファイルがあれば即修正
ls -la /var/www/auction/storage/logs/
sudo chown -R ec2-user:ec2-user /var/www/auction/storage/logs/

# Step 4: 詰まっていれば worker のみ再起動 (Reverb は触らない)
sudo supervisorctl restart auction-queue-countdown:*

# Step 5: 失敗ジョブを retry
sudo -u ec2-user php /var/www/auction/artisan queue:retry all

# Step 6: 復旧確認 (新しい tick ログが流れるはず)
sudo tail -20 /var/www/auction/storage/logs/laravel.log | grep -E "countdown|tick"
```

MonitorAuctionJobs が 1分以内に自動再ディスパッチするので、慌てて手で叩く必要はない。**ただしログ権限が原因の場合は手で直さないと無限ループ**になる。

### 3-B. WebSocket 全断 (Reverb 死亡 / メモリ枯渇)

```bash
# Step 1: Reverb プロセス確認
sudo supervisorctl status auction-reverb

# Step 2: ポート確認 (6001 が listen していない = Reverb 落ち)
sudo ss -tlnp | grep 6001

# Step 3: .env のポート確認 (8080 を指していたら最も多い致命的誤り)
grep REVERB_PORT /var/www/auction/.env

# Step 4: メモリ確認 (1GB超なら計画再起動)
ps -o pid,rss,%mem,cmd -p $(pgrep -f reverb:start)

# Step 5: Reverb 再起動 (数秒の broadcast 停止、フロントは自動再接続)
sudo supervisorctl restart auction-reverb

# Step 6: 復旧確認
sudo ss -tlnp | grep 6001
sudo tail -20 /var/log/supervisor/reverb.log
```

**ライブ中に Reverb を再起動するとその瞬間の broadcast は失われる**。再起動後は CountdownService が次 tick で状態を再送するので価格表示は数秒で復旧するが、それまでの数秒間は「止まったように見える」点をモニタリング担当に共有しておく。

### 3-C. notify キュー詰まり

```bash
# Step 1: 深さ確認
redis-cli -h <endpoint> LLEN queues:notify

# Step 2: LINE API 側のエラーか確認
sudo tail -100 /var/www/auction/storage/logs/laravel.log | grep -iE "line|notify"

# Step 3: countdown には影響しないので、LINE が回復するまで待つのが基本
# Step 4: どうしても捌けないなら notify worker を一時的に増やす
sudo supervisorctl restart auction-queue-notify:*
```

LINE API レート制限が原因なら、待つ以外の対処はない。**countdown は別キューなので影響を受けない**ことを覚えておく。

### 3-D. デッドロック / 「価格が更新されました」エラー多発

```bash
# Step 1: ロック中トランザクションの確認
sudo -u ec2-user php /var/www/auction/artisan tinker
>>> DB::select('SHOW ENGINE INNODB STATUS');
>>> exit

# Step 2: bid_inflight lock の状態
redis-cli -h <endpoint> KEYS 'bid_inflight:item:*'

# Step 3: 単発なら Laravel のリトライ (3回設定済み) で吸収される
# Step 4: 連鎖的に発生 → 直近変更コードがロック順違反していないか確認 (items 先行ロック必須)
```

「価格が更新されました」エラーは**設計上の挙動** (silent=true)。商品切替の瞬間に数人が見るのは正常。**連続して同じユーザーが10回以上見るなら異常**。

### 3-E. php-fpm worker 100張り付き (周辺操作が詰まる)

```bash
# Step 1: 何で詰まっているか確認
ps aux | grep "php-fpm: pool" | head -30
# CMD 末尾でリクエスト URL が見える

# Step 2: slow log 確認
sudo tail -50 /var/log/php-fpm/www-slow.log 2>/dev/null

# Step 3: 詰まり原因が DB なら process list
sudo -u ec2-user php /var/www/auction/artisan tinker
>>> DB::select('SHOW PROCESSLIST');

# Step 4: 緊急なら php-fpm reload (一瞬遅延あるが安全)
sudo systemctl reload php-fpm
```

100張り付きが10分以上続くなら、原因特定するまでは reload を繰り返さない。一時的なバースト (商品切替の瞬間) なら 30秒以内に解消する。

### 3-F. メモリ枯渇 (OOM 兆候)

```bash
# Step 1: メモリ確認
free -h

# Step 2: 大きいプロセス特定
ps aux --sort=-rss | head -10

# Step 3: 該当プロセスがリーカーなら個別再起動
# Reverb なら: sudo supervisorctl restart auction-reverb
# countdown worker なら: sudo supervisorctl restart auction-queue-countdown:*

# Step 4: 全体swap確認 (AL2023 は swap=0 デフォルト、OOM Killer 直行)
swapon --show
```

**OOM Killer が動くと予測不能なプロセスが落ちる**。free -h で available 2GB を切ったら即座にリーカー特定。

### 3-G. countdown ジョブが 4-5時間境界で凍結 (低確率)

supervisor --timeout=18000 (5時間) は当てたが、Job 内 `maxIterations=28800` (4時間) で自然終了する仕様は残っている。

4時間ちょうどで「2-3分の凍結 → MonitorAuctionJobs が新ジョブ dispatch → 自動回復」が起きる可能性。

```bash
# 4時間に近づいたら手動で cache TTL 延長 (tinker)
sudo -u ec2-user php /var/www/auction/artisan tinker
>>> $lanes = App\Models\Lane::whereHas('auction', fn($q) => $q->where('status', 'live'))->get();
>>> foreach ($lanes as $lane) { $key = "countdown:lane:{$lane->id}"; $state = Cache::get($key); if ($state) Cache::put($key, $state, 14400); }
>>> exit

# 4時間境界 (3:55-4:05) のログ追跡
sudo tail -f /var/www/auction/storage/logs/laravel.log | grep -E "countdown\.job\.(completed|re_dispatched|started)"
```

復旧時、商品の残秒数が初期値 (例: 8秒) に巻き戻る可能性がある。これはUI上の見た目だけで、入札処理は正しく動く。

### 3-H. 全レーン unsold 化 (最悪ケース)

兆候: 商品が一切売れず、全部 unsold で進行する

```bash
# Step 1: .env REVERB_PORT が 8080 になっていないか即確認 (最頻原因)
grep REVERB_PORT /var/www/auction/.env

# Step 2: bidホットパスで例外多発していないか
sudo tail -200 /var/www/auction/storage/logs/laravel.log | grep -iE "error|exception" | head -30

# Step 3: 解決不能と判断したら開催一時停止 (admin UI)
# Step 4: ビジネス側と中断判断
```

## 4. 事前変更のロールバック手順

### 4-A. php-fpm 設定のロールバック

```bash
# バックアップ確認
ls -la /etc/php-fpm.d/www.conf.bak-*

# 戻す
sudo cp /etc/php-fpm.d/www.conf.bak-<タイムスタンプ> /etc/php-fpm.d/www.conf
sudo php-fpm -t
sudo systemctl reload php-fpm

# 確認
grep -E "^pm" /etc/php-fpm.d/www.conf
```

### 4-B. supervisor countdown timeout のロールバック

```bash
# バックアップ確認
ls -la /etc/supervisord.d/auction.ini.bak-*

# 戻す
sudo cp /etc/supervisord.d/auction.ini.bak-<タイムスタンプ> /etc/supervisord.d/auction.ini
sudo supervisorctl reread
sudo supervisorctl update

# 確認 (countdown worker が --timeout=7200 に戻っているか)
ps -ef | grep "queue:work" | grep countdown | head -3
```

## 5. 中断判断基準と連絡フロー

### 5-A. 即座に中断を判断すべき状況

| 事象 | 中断判断 |
| --- | --- |
| tick が 5分以上停止 (復旧操作後も) | **即時中断** |
| 全レーン unsold 化が継続 | **即時中断** |
| Reverb が再起動を3回繰り返しても安定しない | **即時中断** |
| DB デッドロックが分単位で連発 | **5分以内に中断判断** |
| failed_jobs が分間100件超で増加 | **5分以内に中断判断** |

### 5-B. 中断手順

```bash
# Step 1: 全レーン一時停止 (admin UI or artisan)
sudo -u ec2-user php /var/www/auction/artisan tinker
>>> App\Models\Lane::whereHas('auction', fn($q) => $q->where('status', 'live'))->update(['status' => 'paused']);
>>> exit

# Step 2: ユーザーへの通知 (管理画面または手動)
# Step 3: 原因究明
# Step 4: 復旧判断 → 再開 or 当日中止
```

### 5-C. 再開判断

中断後の再開は **以下の全条件を満たす場合のみ**:
1. 原因が特定された
2. 同じ事象が再発しないことが確認できた
3. ユーザーへの再開アナウンス手段がある
4. tick / failed_jobs / Reverb が全て健全
5. ビジネス側の承認

```bash
# 1. failed_jobs 全件確認 (未送信通知があれば再投入)

>>> echo App\Models\WonItem::where('auction_id', <id>)->count();
>>> exit

# 3. ピーク時メトリクス記録 (CloudWatch から)
#    - Reverb CPU / メモリ

#    - EC2 CPU / Memory / NetworkOut
#    - notify キュー最大深さ

# 4. 異常があった時系列を Slack に時刻入りで残す
```
