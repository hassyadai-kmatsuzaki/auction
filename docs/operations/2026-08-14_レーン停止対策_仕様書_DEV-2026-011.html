1. 結論 — 金曜日までに「完璧に安全な修正」は可能か

「今回の原因経路が原理的に再発しない修正」は、金曜日までに余裕をもって入れられます。変更は復旧分岐だけで、カウントダウン・入札・落札の通常経路は1行も変えません。ロールバックは2ファイルを戻して1分です。

一方で「レーンが止まる事象がゼロになる保証」は、この修正ではできません。tick 側は不一致を検知しても自己修復せず「スキップ」するだけなので、別の経路で汚染が起きれば止まります。そこは復旧手順書（60秒復旧）と監視で担保し、根治は計画済みのCAS化で行います。

できる 金曜までに保証できること

  • 復旧パスが古い商品でキャッシュを上書きすることは構造的に不可能になる（atomic add）
  • 通常経路は無変更（差分は追加のみ・挙動変更なし）
  • 決定的に再現できるユニットテスト付き
  • ステージング E2E ①〜④ 合格を Go 条件にする

できない この修正の範囲外

  • tick 側の自己修復（不一致を見つけたら自分で直す）— ホットパス改修になるためCAS化と一緒に
  • 未知の別経路による汚染の根絶
  • 「次の商品へ」「AdjustPrice」など既知の未保護操作

2. 今回の原因 — 何が起きたか

11:03:39、レーンC（lane 113）で商品 3140 が落札され、次商品 3196 へ切り替わる同じ秒に、参加者のブラウザからの状態取得（getLiveState）が割り込みました。復旧パスは「キャッシュが空なら再生成する」保護機能ですが、そのリクエストは切替前の古い lane 情報（current_item = 3140）を持ったまま Cache::put（無条件上書き）で書き戻したため、tick が書いた次商品の Pre-bid 状態を潰しました。

なぜ「遷移の一瞬」にリクエストが来るのか

常時ポーリングはしていません（WS接続中はOFF）。ただしフロントは LaneChanged イベントを受けると 0〜1.5 秒の jitter 後に必ず1回 getLiveState を取りに行く設計です（WSイベントに載らない自分の入札状態・指値・auto-bid 結果を取るため）。つまり「落札直後に120人が順番に取りに来る」のは仕様であり、jitter を小さく引いたクライアントは遷移窓（1秒未満）の中に着弾します。

止まる時と流れる時の違い

差は復旧パスが「コミット前（旧商品）」を読んだか「コミット後（現商品）」を読んだかです。現商品で再生成した場合は無害（11:17 / 11:23）。旧商品で書いた場合、それを直せるのは tick の Pre-bid put がその後に着弾した時だけで、入札による freeze/bid 書込みは既存 state の item_id を引き継ぐため直りません（11:04:25 の入札で一時的に動いたが確定時に再停止）。つまり汚染＝ほぼ停止、と考えるのが正確です。

3. 仕様 — 修正が満たすべき要件

ID要件根拠
R1復旧パスは、復旧を実行する時点のDB（$lane->refresh() 後）の current_item で再生成する古い lane モデルを信じたのが直接原因
R2current_item が live でなければ何も書かない落札済み商品での再生成を禁止
R3キャッシュ書込は Cache::add（存在すれば書かない・アトミック）で行う。put は禁止「最後に書いた人が勝つ」を構造的に排除。R1/R2 をすり抜けても上書きは起きない
R4startCountdown / startPreBidCountdown / tick / 入札の通常経路は変更しない。差分は追加のみホットパスの回帰リスク回避・レビュー容易性・1分ロールバック
R5復旧ログに recovered=true/false と対象 item_id を出す次回開催で「add が拒否した回数」＝防いだ回数が見える
R6（フロント・補助）LaneChanged 後の再取得 jitter を 1500〜3000ms にする遷移窓への着弾を避ける。JSビルドが必要なので別便でも可
対象外tick 側の自己修復、CAS化、「次の商品へ」等の既知未保護操作別計画（CAS恒久解）で扱う

4. 実装方針

4-1. バックエンド（2ファイル・追加のみ）

CountdownService.php — 復旧専用メソッドを追加。startCountdown は触らない（通常経路の put は正しい）。

/**
 * getLiveState の cache-miss 復旧専用。
 * 通常経路(startCountdown)と違い、①今のDBで読み直し ②live のみ ③add(存在すれば書かない)。
 * @return bool true=書いた / false=書かなかった(既に存在 or live でない)
 */
public function recoverCountdownIfMissing(Lane $lane): bool
{
    $lane->refresh();                               // R1: current_item_id を今のDBで取り直す
    $lane->load(['currentItem', 'auction']);
    $item    = $lane->currentItem;
    $auction = $lane->auction;

    if ($lane->status !== 'active' || !$item || $item->status !== 'live' || !$auction) {
        return false;                               // R2: live でなければ何も書かない
    }

    $seconds = $auction->calculateCountdownSeconds($item->current_price);
    $cacheData = [
        'lane_id' => $lane->id,
        'item_id' => $item->id,
        'auction_id' => $auction->id,
        'phase' => 'bidding',
        'remaining_seconds' => $seconds['bid_countdown_seconds'],
        'started_at' => now()->timestamp,
        'bid_countdown_seconds' => $seconds['bid_countdown_seconds'],
        'freeze_countdown_seconds' => $seconds['freeze_countdown_seconds'],
        'is_running' => true,
        'pre_bid_remaining_seconds' => 0,
        'last_bidder_user_id' => null,
    ];

    // R3: Redis SET NX。既に誰かが書いていれば false で戻る（上書き能力を持たない）
    return Cache::add($this->getCacheKey($lane->id), $cacheData, self::CACHE_TTL);
}

BidService.php:172-186 — 呼び先とログを差し替え（R5）。

if (!$countdownState && $lane->status === 'active' && $lane->currentItem && $lane->currentItem->status === 'live') {
    try {
        $recovered      = app(\App\Services\CountdownService::class)->recoverCountdownIfMissing($lane);
        $countdownState = Cache::get("countdown:lane:{$lane->id}");
        Log::warning('getLiveState: countdown cache miss recovered', [
            'lane_id'    => $lane->id,
            'item_id'    => $countdownState['item_id'] ?? null,   // 実際にキャッシュにある商品
            'recovered'  => $recovered,                           // false = 誰かが先に書いていた(防いだ)
            'auction_id' => $auction->id,
        ]);
    } catch (\Throwable $e) { /* 既存のまま */ }
}

配列を startCountdown と重複させているのは意図的です。共通化すると通常経路にも差分が入り「追加のみ」（R4）が崩れるため、レビューとロールバックの単純さを優先します。CAS化の際に統合します。

7. 残るリスク（正直に）

  • 修正そのもの: getLiveState は全ポーリングが通るホットパス。コードミスは既存 try/catch で握られるが、ステージング実走なしでの本番投入はしない。
  • 別経路の汚染: tick は不一致を自己修復しない。止まったら手順書で60秒復旧。根治はCAS化。
  • WS切断中の5秒ポーリング: R6 では制御できない着弾だが、R3 により無害化される。
  • 既知の未保護操作: 「次の商品へ」「AdjustPrice」「残り数秒の指値」は引き続き運用ルールで回避。
