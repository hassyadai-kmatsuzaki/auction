# レーン単独停止（cache汚染）復旧手順

| 項目 | 内容 |
| --- | --- |
| 文書番号 | OPS-2026-005 |
| 版数 | 1.0 |
| 作成日 | 2026-08-14（第7回開催中に実発生・実復旧した手順を文書化） |
| 対象 | **1レーンだけ**カウントダウンが「残りN秒のまま」固まる事象 |
| 対象外 | **全レーン同時停止** → [カウントダウン停止対応プレイブック (OPS-2026-004)](2026-06-05_カウントダウン停止対応プレイブック.md) へ（ログ権限破壊の典型） |
| 実績 | 2026-08-14 11:03 レーンC(113)で発生 → 本手順で60秒復旧・金銭影響ゼロ |

> **原因の要約**: 落札→次商品の遷移の一瞬に、ユーザーのポーリングが「古い商品」で countdown cache を再生成してしまい（`getLiveState: countdown cache miss recovered` 警告が痕跡）、tick が cache と DB の商品不一致でそのレーンだけスキップし続ける。**入札状態・価格・落札結果は一切壊れない**。慌てなくてよい。

## 1. 症状（どれか1つでも該当したら §2 へ）

- 1レーンだけカウントダウンが「残りN秒のまま」動かない（他レーンは正常に売れている）
- ログに `getLiveState: countdown cache miss recovered` が出て、その **item_id が直前に sold になった商品**を指している
  - ※開始直後(11:00)の recovered は正常な自己修復。**開催中盤に出たものだけ**疑う

---

## 2. 診断（10秒・コピペ1発）

```bash
sudo -u ec2-user php /var/www/auction/artisan tinker --execute="foreach([111,112,113] as \$id){\$l=App\Models\Lane::find(\$id); echo 'lane '.\$id.': DB item='.\$l->current_item_id.' ('.(\$l->currentItem?->status ?? '-').')'; \$c=Cache::get('countdown:lane:'.\$id); echo ' / cache item='.(\$c['item_id'] ?? 'MISS').' phase='.(\$c['phase'] ?? '-').' remain='.(\$c['remaining_seconds'] ?? '-').PHP_EOL;}"
```

| 出力パターン | 判定 | 対応 |
| --- | --- | --- |
| DB item と cache item が**不一致**（DB=live） | 🔴 cache汚染 | §3 の該当レーンの復旧コマンド |
| cache=**MISS** かつ DB item が live | 🔴 cache消失 | 同じく §3 |
| DB item が **live 以外**（sold等）のまま動かない | ⚠️ 別事象（finalize停滞） | **§3を打たない**。§4の禁止事項を守り、ログを保全して開発へ |
| 全部一致して remain が動いている | 🟢 誤検知 | 様子見 |

---

## 3. 復旧コマンド（該当レーンのものをそのままコピペ）

実行前提: §2 で「DB item が live なのに cache が不一致 or MISS」を確認済みであること。
価格・ホルダー・入札状態は変わらない。現商品のカウントダウンが10秒から再開するだけ。

### レーンA（lane 111）が止まった場合

```bash
sudo -u ec2-user php /var/www/auction/artisan tinker --execute="\$l=App\Models\Lane::find(111); app(App\Services\CountdownService::class)->startCountdown(\$l); print_r(Cache::get('countdown:lane:111'));"
```

### レーンB（lane 112）が止まった場合

```bash
sudo -u ec2-user php /var/www/auction/artisan tinker --execute="\$l=App\Models\Lane::find(112); app(App\Services\CountdownService::class)->startCountdown(\$l); print_r(Cache::get('countdown:lane:112'));"
```

### レーンC（lane 113）が止まった場合

```bash
sudo -u ec2-user php /var/www/auction/artisan tinker --execute="\$l=App\Models\Lane::find(113); app(App\Services\CountdownService::class)->startCountdown(\$l); print_r(Cache::get('countdown:lane:113'));"
```

### 復旧確認（30秒以内）

1. コマンド出力の `[item_id]` が §2 の **DB item と一致**していること
2. 画面で該当レーンのカウントが動き出すこと
3. ログが流れ出すこと:

```bash
sudo tail -20 /var/www/auction/storage/logs/laravel-$(date +%F).log | grep "lane 111\|lane 112\|lane 113"
```

**注意（入札では直らない）**: 汚染中に誰かが入札すると freeze→カウントが一時的に動き出すが、freeze/bid の書込みは古い item_id を引き継ぐため、確定時に不一致で再び止まる（8/14 11:04:25→11:04:27 で実証）。**復旧は §3 のコマンドが必須**。

## 4. やってはいけないこと

| 禁止 | 理由 |
| --- | --- |
| **「次の商品へ」ボタンで強制復旧** | finalize失敗を握り潰す既知の穴。入札者がいる商品でロスト事故に直行 |
| queue worker / Reverb の再起動 | チェーンは生きている（他レーンが動いている）。無関係な数秒断を作るだけ |
| live 中の AdjustPrice | ロック無しの素update。状態をさらに壊す |
| §2 で DB item が live 以外なのに §3 を打つ | 遷移中 or finalize停滞。上書きすると本当に壊れる可能性 |

## 6. 背景と恒久対処（開発向けメモ）

- 発生機序: `BidService::getLiveState` の cache-miss 復旧パス（BidService.php:166-176）が、リクエスト冒頭にロードした古い `lane->currentItem`（=売却済み商品）を信じて `startCountdown` を実行し、moveToNextItem が書いた Pre-bid キャッシュを上書きする TOCTOU。B4 の事前 warmup は遷移中の窓をカバーしていない。DEV-2026-008（tickクロバー）系の新変種。
- 発生率実測: 第7回の序盤 約10遷移で1回。
- 暫定パッチ候補（次回開催前・要ステージング+E2E）: 復旧パスで `$lane->refresh()` + currentItem 再読込し、item が live でなければ復旧しない（1ハンク）。
- 恒久解: CAS 化（計画済み）でこの系統ごと閉じる。
